쿠버네티스는 단일 클러스터에서 다중 스케줄러를 실행할 수 있도록 지원한다.

이 페이지는 클러스터에서 다중 스케줄러를 실행할 때의 일반적인 원칙을 설명하며, 이 중 최소 하나의 스케줄러는 기본 `kube-scheduler`라고 가정한다. 만약 사용자 정의 스케줄러나 서드파티 스케줄러만 실행한다면 해당 스케줄러의 문서를 참고한다.

<!-- body -->

## 배포 전략

다중 스케줄러를 실행할 때는 스케줄러 간에, 그리고 스케줄러와 클러스터 노드 간에 어떻게 상호 작용할지 결정해야 한다. 일반적인 배포 시나리오는 다음 세 가지이다.

### 고가용성(대기 레플리카)

하나의 논리적 스케줄러(예: `kube-scheduler`)를 실행하면서 장애가 발생하더라도 가용성을 유지하려면 스케줄러의 레플리카를 여러 개 실행하고 **리더 선출(leader election)** 을 활성화해야 한다.

리더 선출이 활성화되면 하나의 레플리카(리더)만 활성 상태로 파드를 스케줄링하고, 나머지 레플리카는 대기 상태로 남는다. 활성 리더에 장애가 발생하면 대기 중인 레플리카 중 하나가 자동으로 새 리더로 선출되어 스케줄링 작업을 이어받는다.

구성 방법에 대한 자세한 내용은 [리더 선출 활성화](/docs/tasks/extend-kubernetes/configure-multiple-schedulers/#리더-선출-활성화)를 참고한다.

### 여러 스케줄러 프로파일 또는 인스턴스

워크로드마다 서로 다른 구성이나 스케줄링 규칙을 사용하려면, 단일 `kube-scheduler` 인스턴스에 여러 스케줄링 프로파일을 구성하거나 `kube-scheduler` 인스턴스를 여러 개 따로 실행할 수 있다.

* **하나의 인스턴스에서 여러 프로파일 사용:** 단일 `kube-scheduler` 프로세스는 여러 프로파일(각각 고유한 스케줄러 이름을 가짐)을 실행할 수 있다. 이러한 프로파일은 같은 프로세스에서 실행되며 동일한 스케줄링 큐와 캐시를 공유하기 때문에 서로 충돌하는 스케줄링 결정을 내리지 않는다. 각 프로파일이 특정 노드 풀에서만 동작하도록 하여 워크로드를 분리하고 싶다면 [노드 어피니티](/docs/concepts/scheduling-eviction/assign-pod-node/#node-affinity-per-scheduling-profile)를 사용할 수 있다.
* **여러 개의 개별 인스턴스 사용:** 여러 개의 개별 `kube-scheduler` 프로세스(배포)를 실행하는 경우, 각 프로세스는 서로 조율하지 않으므로 스케줄링 결정이 충돌할 수도 있다(예: 노드의 리소스가 오버커밋되는 경우). 이를 방지하려면 [노드 어피니티](/docs/concepts/scheduling-eviction/assign-pod-node/#node-affinity-per-scheduling-profile)를 사용하여 각 스케줄러 인스턴스가 담당하는 노드가 서로 겹치지 않도록 해야 한다.

### kube-scheduler와 사용자 정의 스케줄러 함께 사용하기

`kube-scheduler`를 사용자 정의 스케줄러나 서드파티 스케줄러와 함께 실행하는 경우, 리소스 충돌을 피하기 위해 각 스케줄러가 서로 겹치지 않는 노드 풀에서 동작하도록 한다. 사용자 정의 스케줄러의 설계 방식에 따라 액티브-액티브(active-active) 구성으로 실행할 수도 있고, 자체적인 리더 선출 메커니즘이 필요할 수도 있다. 항상 해당 사용자 정의 스케줄러의 문서를 확인한다.
