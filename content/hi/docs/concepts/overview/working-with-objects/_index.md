यह पृष्ठ बताता है कि कुबेरनेट्स API में कुबेरनेट्स ऑब्जेक्ट्स को कैसे दर्शाया जाता है, और आप उन्हें
`.yaml` फ़ॉर्मेट में कैसे लिख सकते हैं।

<!-- body -->

## कुबेरनेट्स ऑब्जेक्ट्स को समझना {#kubernetes-objects}

*कुबेरनेट्स ऑब्जेक्ट्स* कुबेरनेट्स सिस्टम में स्थायी एंटिटी हैं। कुबेरनेट्स इन एंटिटी का उपयोग
आपके क्लस्टर की स्थिति को दर्शाने के लिए करता है। ख़ास तौर पर, ये बता सकते हैं:

* कौन से कंटेनरीकृत एप्लिकेशन चल रहे हैं (और किन नोड्स पर)
* उन एप्लिकेशन के लिए उपलब्ध संसाधन
* वे नीतियाँ जो तय करती हैं कि वे एप्लिकेशन कैसे व्यवहार करेंगे, जैसे रीस्टार्ट नीतियाँ, अपग्रेड और फ़ॉल्ट-टॉलरेंस

एक कुबेरनेट्स ऑब्जेक्ट एक "इरादे का रिकॉर्ड" (record of intent) है--एक बार जब आप ऑब्जेक्ट बना
देते हैं, तो कुबेरनेट्स सिस्टम लगातार यह सुनिश्चित करने के लिए काम करेगा कि वह ऑब्जेक्ट मौजूद रहे।
ऑब्जेक्ट बनाकर, आप असल में कुबेरनेट्स सिस्टम को बता रहे होते हैं कि आप अपने क्लस्टर का वर्कलोड
कैसा दिखना चाहते हैं; यही आपके क्लस्टर की *वांछित स्थिति* (desired state) है।

कुबेरनेट्स ऑब्जेक्ट्स के साथ काम करने के लिए--चाहे उन्हें बनाना हो, बदलना हो या हटाना हो--आपको
[कुबेरनेट्स API](/docs/concepts/overview/kubernetes-api/) का उपयोग करना होगा। उदाहरण के लिए, जब आप
`kubectl` कमांड-लाइन इंटरफ़ेस का उपयोग करते हैं, तो CLI आपके लिए ज़रूरी कुबेरनेट्स API कॉल करता है।
आप [क्लाइंट लाइब्रेरी](/docs/reference/using-api/client-libraries/) में से किसी एक का उपयोग करके अपने
प्रोग्राम में सीधे कुबेरनेट्स API का उपयोग भी कर सकते हैं।

### ऑब्जेक्ट का spec और status

लगभग हर कुबेरनेट्स ऑब्जेक्ट में दो नेस्टेड ऑब्जेक्ट फ़ील्ड होते हैं जो ऑब्जेक्ट के कॉन्फ़िगरेशन को
नियंत्रित करते हैं: ऑब्जेक्ट का *`spec`* और ऑब्जेक्ट का *`status`*।
जिन ऑब्जेक्ट्स में `spec` होता है, उनके लिए आपको ऑब्जेक्ट बनाते समय इसे सेट करना होता है, और इसमें
उन विशेषताओं का विवरण देना होता है जो आप उस रिसोर्स में चाहते हैं: यानी उसकी _वांछित स्थिति_।

`status` ऑब्जेक्ट की _वर्तमान स्थिति_ (current state) को बताता है, जिसे कुबेरनेट्स सिस्टम और उसके
घटक भरते और अपडेट करते हैं। कुबेरनेट्स
{{< glossary_tooltip text="कंट्रोल प्लेन" term_id="control-plane" >}} लगातार और सक्रिय रूप से हर
ऑब्जेक्ट की वास्तविक स्थिति को आपकी दी गई वांछित स्थिति से मिलाने के लिए उसका प्रबंधन करता है।

उदाहरण के लिए: कुबेरनेट्स में, Deployment एक ऑब्जेक्ट है जो आपके क्लस्टर पर चल रहे किसी
एप्लिकेशन को दर्शा सकता है। जब आप Deployment बनाते हैं, तो आप Deployment के `spec` में यह तय कर
सकते हैं कि आप एप्लिकेशन की तीन रेप्लिका चलाना चाहते हैं। कुबेरनेट्स सिस्टम Deployment का spec
पढ़ता है और आपके एप्लिकेशन के तीन इंस्टेंस शुरू करता है--और status को आपके spec के अनुसार अपडेट
करता है। अगर उनमें से कोई भी इंस्टेंस विफल हो जाए (यानी status में बदलाव), तो कुबेरनेट्स सिस्टम
spec और status के बीच के अंतर पर प्रतिक्रिया देते हुए सुधार करता है--इस मामले में, एक नया
इंस्टेंस शुरू करके।

ऑब्जेक्ट के spec, status और metadata के बारे में अधिक जानकारी के लिए,
[कुबेरनेट्स API कन्वेंशन](https://git.k8s.io/community/contributors/devel/sig-architecture/api-conventions.md) देखें।

### कुबेरनेट्स ऑब्जेक्ट का वर्णन करना

जब आप कुबेरनेट्स में कोई ऑब्जेक्ट बनाते हैं, तो आपको ऑब्जेक्ट का spec देना होता है जो उसकी
वांछित स्थिति बताता है, साथ ही ऑब्जेक्ट के बारे में कुछ बुनियादी जानकारी (जैसे नाम) भी देनी होती है।
जब आप ऑब्जेक्ट बनाने के लिए कुबेरनेट्स API का उपयोग करते हैं (सीधे या `kubectl` के ज़रिए), तो उस
API अनुरोध की बॉडी में यह जानकारी JSON के रूप में होनी चाहिए।
अधिकतर, आप यह जानकारी `kubectl` को एक फ़ाइल में देते हैं जिसे _मैनिफ़ेस्ट_ (manifest) कहा जाता है।
परंपरा के अनुसार, मैनिफ़ेस्ट YAML में होते हैं (आप JSON फ़ॉर्मेट का भी उपयोग कर सकते हैं)।
`kubectl` जैसे टूल HTTP पर API अनुरोध करते समय मैनिफ़ेस्ट की जानकारी को JSON या किसी अन्य समर्थित
सीरियलाइज़ेशन फ़ॉर्मेट में बदल देते हैं।

यहाँ एक उदाहरण मैनिफ़ेस्ट है जो कुबेरनेट्स Deployment के लिए ज़रूरी फ़ील्ड और ऑब्जेक्ट spec दिखाता है:

{{% code_sample file="application/deployment.yaml" %}}

ऊपर दी गई मैनिफ़ेस्ट फ़ाइल जैसी फ़ाइल से Deployment बनाने का एक तरीका `kubectl` कमांड-लाइन
इंटरफ़ेस में [`kubectl apply`](/docs/reference/generated/kubectl/kubectl-commands#apply) कमांड का
उपयोग करना है, जिसमें `.yaml` फ़ाइल को आर्ग्युमेंट के रूप में दिया जाता है। यहाँ एक उदाहरण है:

```shell
kubectl apply -f https://k8s.io/examples/application/deployment.yaml
```

आउटपुट कुछ इस तरह का होगा:

```
deployment.apps/nginx-deployment created
```

### ज़रूरी फ़ील्ड

जिस कुबेरनेट्स ऑब्जेक्ट को आप बनाना चाहते हैं, उसकी मैनिफ़ेस्ट (YAML या JSON फ़ाइल) में आपको
इन फ़ील्ड के मान सेट करने होंगे:

* `apiVersion` - इस ऑब्जेक्ट को बनाने के लिए आप कुबेरनेट्स API के किस वर्ज़न का उपयोग कर रहे हैं
* `kind` - आप किस तरह का ऑब्जेक्ट बनाना चाहते हैं
* `metadata` - वह डेटा जो ऑब्जेक्ट की विशिष्ट पहचान में मदद करता है, जिसमें `name` स्ट्रिंग, `UID` और वैकल्पिक `namespace` शामिल हैं
* `spec` - आप ऑब्जेक्ट की कौन सी स्थिति चाहते हैं

ऑब्जेक्ट `spec` का सटीक फ़ॉर्मेट हर कुबेरनेट्स ऑब्जेक्ट के लिए अलग होता है, और इसमें उस ऑब्जेक्ट से
जुड़े नेस्टेड फ़ील्ड होते हैं। [कुबेरनेट्स API रेफ़रेंस](/docs/reference/kubernetes-api/) की मदद से
आप उन सभी ऑब्जेक्ट्स के spec का फ़ॉर्मेट ढूंढ सकते हैं जिन्हें आप कुबेरनेट्स का उपयोग करके बना सकते हैं।

उदाहरण के लिए, Pod API रेफ़रेंस में
[`spec` फ़ील्ड](/docs/reference/kubernetes-api/workload-resources/pod-v1/#PodSpec) देखें।
हर Pod के लिए, `.spec` फ़ील्ड पॉड और उसकी वांछित स्थिति को बताता है (जैसे उस पॉड के हर कंटेनर के
लिए कंटेनर इमेज का नाम)।
ऑब्जेक्ट spec का एक और उदाहरण StatefulSet API का
[`spec` फ़ील्ड](/docs/reference/kubernetes-api/workload-resources/stateful-set-v1/#StatefulSetSpec) है।
StatefulSet के लिए, `.spec` फ़ील्ड StatefulSet और उसकी वांछित स्थिति को बताता है।
StatefulSet के `.spec` के अंदर Pod ऑब्जेक्ट्स के लिए एक [टेम्पलेट](/docs/concepts/workloads/pods/#pod-templates)
होता है। यह टेम्पलेट उन पॉड्स का वर्णन करता है जिन्हें StatefulSet कंट्रोलर, StatefulSet के spec को
पूरा करने के लिए बनाएगा।
अलग-अलग तरह के ऑब्जेक्ट्स का `.status` भी अलग हो सकता है; यहाँ भी, API रेफ़रेंस पृष्ठ हर तरह के
ऑब्जेक्ट के लिए उस `.status` फ़ील्ड की संरचना और उसकी सामग्री का विवरण देते हैं।

YAML कॉन्फ़िगरेशन फ़ाइलें लिखने के बारे में अतिरिक्त जानकारी के लिए
[कुबेरनेट्स कॉन्फ़िगरेशन के सर्वोत्तम तरीके](/blog/2025/11/25/configuration-good-practices/) देखें।

## सर्वर साइड फ़ील्ड वैलिडेशन

कुबेरनेट्स v1.25 से, API सर्वर सर्वर साइड
[फ़ील्ड वैलिडेशन](/docs/reference/using-api/api-concepts/#field-validation) देता है, जो किसी ऑब्जेक्ट
में पहचाने न गए या दोहराए गए फ़ील्ड का पता लगाता है। यह सर्वर साइड पर `kubectl --validate` की
सारी कार्यक्षमता प्रदान करता है।

`kubectl` टूल फ़ील्ड वैलिडेशन का स्तर सेट करने के लिए `--validate` फ़्लैग का उपयोग करता है। यह
`ignore`, `warn` और `strict` मान स्वीकार करता है, साथ ही `true` (`strict` के बराबर) और `false`
(`ignore` के बराबर) मान भी स्वीकार करता है। `kubectl` के लिए डिफ़ॉल्ट वैलिडेशन सेटिंग `--validate=true` है।

`Strict`
: सख़्त फ़ील्ड वैलिडेशन, वैलिडेशन विफल होने पर एरर

`Warn`
: फ़ील्ड वैलिडेशन किया जाता है, लेकिन अनुरोध को विफल करने के बजाय एरर को चेतावनी के रूप में दिखाया जाता है

`Ignore`
: कोई सर्वर साइड फ़ील्ड वैलिडेशन नहीं किया जाता

जब `kubectl` किसी ऐसे API सर्वर से कनेक्ट नहीं हो पाता जो फ़ील्ड वैलिडेशन को सपोर्ट करता हो, तो यह
क्लाइंट-साइड वैलिडेशन का उपयोग करने लगता है। कुबेरनेट्स 1.27 और उसके बाद के वर्ज़न हमेशा फ़ील्ड
वैलिडेशन देते हैं; पुराने कुबेरनेट्स रिलीज़ में यह हो भी सकता है और नहीं भी। अगर आपका क्लस्टर v1.27
से पुराना है, तो अपने कुबेरनेट्स वर्ज़न का प्रलेखन देखें।
