*कस्टम रिसोर्स* कुबरनेट्स API के एक्सटेंशन हैं। यह पेज बताता है कि अपने कुबरनेट्स क्लस्टर में कस्टम
रिसोर्स कब जोड़ना चाहिए और कब स्टैंडअलोन सेवा का उपयोग करना चाहिए। यह कस्टम रिसोर्स जोड़ने के दो तरीकों
और उनके बीच चुनाव करने के तरीके का वर्णन करता है।

<!-- body -->
## कस्टम रिसोर्स

एक *रिसोर्स* [कुबरनेट्स API](/docs/concepts/overview/kubernetes-api/) में एक एंडपॉइंट होता है जो किसी
खास kind के {{< glossary_tooltip text="API ऑब्जेक्ट" term_id="object" >}} का संग्रह स्टोर करता है;
उदाहरण के लिए, इनबिल्ट *pods* रिसोर्स में Pod ऑब्जेक्ट का संग्रह होता है।

एक *कस्टम रिसोर्स* कुबरनेट्स API का एक एक्सटेंशन है जो डिफ़ॉल्ट कुबरनेट्स इंस्टॉलेशन में हमेशा उपलब्ध
नहीं होता। यह किसी विशेष कुबरनेट्स इंस्टॉलेशन के कस्टमाइज़ेशन का प्रतिनिधित्व करता है। हालाँकि, अब कई
कोर कुबरनेट्स फ़ंक्शन कस्टम रिसोर्स का उपयोग करके बनाए जाते हैं, जिससे कुबरनेट्स अधिक मॉड्यूलर बनता है।

कस्टम रिसोर्स डायनामिक रजिस्ट्रेशन के माध्यम से किसी चल रहे क्लस्टर में दिखाई और गायब हो सकते हैं, और
क्लस्टर एडमिन क्लस्टर से स्वतंत्र रूप से कस्टम रिसोर्स को अपडेट कर सकते हैं। एक बार कस्टम रिसोर्स
इंस्टॉल हो जाने पर, यूज़र {{< glossary_tooltip text="kubectl" term_id="kubectl" >}} का उपयोग करके
उसके ऑब्जेक्ट बना और एक्सेस कर सकते हैं, ठीक वैसे ही जैसे वे *Pods* जैसे इनबिल्ट रिसोर्स के लिए करते हैं।

## कस्टम नियंत्रक

अपने आप में, कस्टम रिसोर्स आपको स्ट्रक्चर्ड डेटा स्टोर और रिट्रीव करने देते हैं। जब आप किसी कस्टम रिसोर्स
को *कस्टम नियंत्रक* के साथ जोड़ते हैं, तो कस्टम रिसोर्स एक सही मायने में _डिक्लेरेटिव API_ प्रदान करते
हैं।

कुबरनेट्स का [डिक्लेरेटिव API](/docs/concepts/overview/kubernetes-api/) जिम्मेदारियों का बँटवारा लागू
करता है। आप अपने रिसोर्स की इच्छित स्थिति घोषित करते हैं। कुबरनेट्स नियंत्रक कुबरनेट्स ऑब्जेक्ट की मौजूदा
स्थिति को आपकी घोषित इच्छित स्थिति के साथ सिंक रखता है। यह एक इम्परेटिव API के विपरीत है, जिसमें आप किसी
सर्वर को *निर्देश देते हैं* कि क्या करना है।

आप किसी चल रहे क्लस्टर पर कस्टम नियंत्रक को क्लस्टर के लाइफ़साइकल से स्वतंत्र रूप से डिप्लॉय और अपडेट कर
सकते हैं। कस्टम नियंत्रक किसी भी प्रकार के रिसोर्स के साथ काम कर सकते हैं, लेकिन ये कस्टम रिसोर्स के साथ
जोड़े जाने पर विशेष रूप से प्रभावी होते हैं।
[ऑपरेटर पैटर्न](/docs/concepts/extend-kubernetes/operator/) कस्टम रिसोर्स और कस्टम नियंत्रक को जोड़ता
है। आप विशिष्ट एप्लिकेशन के लिए डोमेन नॉलेज को कुबरनेट्स API के एक एक्सटेंशन में एनकोड करने के लिए कस्टम
नियंत्रक का उपयोग कर सकते हैं।

## क्या मुझे अपने कुबरनेट्स क्लस्टर में कस्टम रिसोर्स जोड़ना चाहिए?

नई API बनाते समय, यह विचार करें कि
[अपनी API को कुबरनेट्स क्लस्टर API के साथ एग्रीगेट करें](/docs/concepts/extend-kubernetes/api-extension/apiserver-aggregation/)
या अपनी API को स्टैंडअलोन रहने दें।

| API एग्रीगेशन पर विचार करें अगर: | स्टैंडअलोन API को प्राथमिकता दें अगर: |
| ---------------------------- | ---------------------------- |
| आपकी API [डिक्लेरेटिव](#declarative-apis) है। | आपकी API [डिक्लेरेटिव](#declarative-apis) मॉडल में फ़िट नहीं होती। |
| आप चाहते हैं कि आपके नए type `kubectl` का उपयोग करके पढ़े और लिखे जा सकें। | `kubectl` सपोर्ट आवश्यक नहीं है |
| आप अपने नए type को किसी कुबरनेट्स UI, जैसे डैशबोर्ड, में इनबिल्ट type के साथ देखना चाहते हैं। | कुबरनेट्स UI सपोर्ट आवश्यक नहीं है। |
| आप एक नई API डेवलप कर रहे हैं। | आपके पास पहले से ही एक प्रोग्राम है जो आपकी API को सर्व करता है और अच्छी तरह काम करता है। |
| आप उस फ़ॉर्मेट प्रतिबंध को स्वीकार करने के लिए तैयार हैं जो कुबरनेट्स REST रिसोर्स पाथ, जैसे API ग्रुप और नेमस्पेस, पर लगाता है। (देखें [API ओवरव्यू](/docs/concepts/overview/kubernetes-api/)।) | आपको किसी पहले से परिभाषित REST API के साथ कॉम्पेटिबल रहने के लिए विशेष REST पाथ की आवश्यकता है। |
| आपके रिसोर्स स्वाभाविक रूप से किसी क्लस्टर या क्लस्टर के नेमस्पेस तक सीमित हैं। | क्लस्टर या नेमस्पेस स्कोप्ड रिसोर्स सही फ़िट नहीं हैं; आपको रिसोर्स पाथ के विवरण पर नियंत्रण चाहिए। |
| आप [कुबरनेट्स API सपोर्ट फ़ीचर](#common-features) को फिर से उपयोग करना चाहते हैं। | आपको उन फ़ीचर की आवश्यकता नहीं है। |

### डिक्लेरेटिव API {#declarative-apis}

एक डिक्लेरेटिव API में, आमतौर पर:

- आपकी API में सापेक्षिक रूप से कम संख्या में सापेक्षिक रूप से छोटे ऑब्जेक्ट (रिसोर्स) होते हैं।
- ऑब्जेक्ट एप्लिकेशन या इंफ्रास्ट्रक्चर के कॉन्फ़िगरेशन को परिभाषित करते हैं।
- ऑब्जेक्ट को सापेक्षिक रूप से कम बार अपडेट किया जाता है।
- इंसानों को अक्सर ऑब्जेक्ट को पढ़ने और लिखने की आवश्यकता होती है।
- ऑब्जेक्ट पर मुख्य ऑपरेशन CRUD-नुमा (क्रिएट करना, पढ़ना, अपडेट करना और डिलीट करना) होते हैं।
- ऑब्जेक्ट के बीच ट्रांज़ैक्शन आवश्यक नहीं होते: API एक इच्छित स्थिति दर्शाता है, न कि कोई सटीक स्थिति।

इम्परेटिव API डिक्लेरेटिव नहीं होते।
यह इशारा करने वाले संकेत कि आपकी API शायद डिक्लेरेटिव नहीं है:

- क्लाइंट कहता है "यह करो", और फिर इसके पूरा होने पर उसे एक सिंक्रोनस रिस्पॉन्स मिलता है।
- क्लाइंट कहता है "यह करो", और फिर उसे एक ऑपरेशन ID मिलती है, और रिक्वेस्ट के पूरा होने का पता लगाने
  के लिए उसे एक अलग Operation ऑब्जेक्ट देखना पड़ता है।
- आप रिमोट प्रोसीजर कॉल (RPC) की बात करते हैं।
- बड़ी मात्रा में डेटा को सीधे स्टोर करना; उदाहरण के लिए, प्रति ऑब्जेक्ट कुछ kB से अधिक, या 1000 से अधिक
  ऑब्जेक्ट।
- हाई बैंडविड्थ एक्सेस (लगातार प्रति सेकंड दहाई की संख्या में रिक्वेस्ट) की आवश्यकता है।
- एंड-यूज़र डेटा (जैसे इमेज, PII, आदि) या एप्लिकेशन द्वारा प्रोसेस किए जाने वाले अन्य बड़े स्तर के डेटा
  को स्टोर करना।
- ऑब्जेक्ट पर स्वाभाविक ऑपरेशन CRUD-नुमा नहीं हैं।
- API को ऑब्जेक्ट के रूप में मॉडल करना आसान नहीं है।
- आपने पेंडिंग ऑपरेशन को किसी ऑपरेशन ID या ऑपरेशन ऑब्जेक्ट के साथ दर्शाने का चुनाव किया है।

## क्या मुझे ConfigMap या कस्टम रिसोर्स का उपयोग करना चाहिए?

अगर निम्नलिखित में से कोई भी लागू होता है, तो ConfigMap का उपयोग करें:

* कोई मौजूदा, अच्छी तरह डॉक्यूमेंटेड कॉन्फ़िगरेशन फ़ाइल फ़ॉर्मेट है, जैसे `mysql.cnf` या `pom.xml`।
* आप पूरे कॉन्फ़िगरेशन को ConfigMap की एक ही key में रखना चाहते हैं।
* कॉन्फ़िगरेशन फ़ाइल का मुख्य उपयोग यह है कि आपके क्लस्टर में किसी पॉड में चल रहा प्रोग्राम खुद को
  कॉन्फ़िगर करने के लिए इस फ़ाइल का उपयोग करे।
* फ़ाइल का उपयोग करने वाले किसी पॉड में फ़ाइल के रूप में, या पॉड में एनवायरनमेंट वेरिएबल के रूप में
  इसे उपयोग करना पसंद करते हैं, न कि कुबरनेट्स API के माध्यम से।
* आप चाहते हैं कि फ़ाइल अपडेट होने पर Deployment आदि के माध्यम से रोलिंग अपडेट किया जाए।

{{< note >}}
संवेदनशील डेटा के लिए {{< glossary_tooltip text="सीक्रेट" term_id="secret" >}} का उपयोग करें, जो
ConfigMap के समान है लेकिन अधिक सुरक्षित है।
{{< /note >}}

अगर निम्नलिखित में से अधिकतर लागू होता है, तो कस्टम रिसोर्स (CRD या एग्रीगेटेड API) का उपयोग करें:

* आप नए रिसोर्स को बनाने और अपडेट करने के लिए कुबरनेट्स क्लाइंट लाइब्रेरी और CLI का उपयोग करना चाहते हैं।
* आप `kubectl` से टॉप-लेवल सपोर्ट चाहते हैं; उदाहरण के लिए, `kubectl get my-object object-name`।
* आप नया ऑटोमेशन बनाना चाहते हैं जो नए ऑब्जेक्ट पर अपडेट के लिए वॉच करे, और फिर अन्य ऑब्जेक्ट पर CRUD
  करे, या इसके उलट।
* आप ऐसा ऑटोमेशन लिखना चाहते हैं जो ऑब्जेक्ट में अपडेट को हैंडल करे।
* आप `.spec`, `.status`, और `.metadata` जैसी कुबरनेट्स API परंपराओं का उपयोग करना चाहते हैं।
* आप चाहते हैं कि ऑब्जेक्ट नियंत्रित रिसोर्स के किसी संग्रह पर एक एब्स्ट्रैक्शन हो, या अन्य रिसोर्स का
  सारांश हो।

## कस्टम रिसोर्स जोड़ना

कुबरनेट्स आपके क्लस्टर में कस्टम रिसोर्स जोड़ने के दो तरीके प्रदान करता है:

- CRD सरल हैं और इन्हें बिना किसी प्रोग्रामिंग के बनाया जा सकता है।
- [API एग्रीगेशन](/docs/concepts/extend-kubernetes/api-extension/apiserver-aggregation/) के लिए
  प्रोग्रामिंग आवश्यक है, लेकिन यह API व्यवहार, जैसे डेटा कैसे स्टोर किया जाता है और API वर्शन के बीच
  कन्वर्ज़न, पर अधिक नियंत्रण देता है।

कुबरनेट्स अलग-अलग यूज़र की आवश्यकताओं को पूरा करने के लिए ये दोनों विकल्प प्रदान करता है, ताकि न तो
उपयोग में आसानी और न ही फ़्लेक्सिबिलिटी से समझौता हो।

एग्रीगेटेड API सबऑर्डिनेट API सर्वर होते हैं जो प्राइमरी API सर्वर के पीछे बैठते हैं, जो एक प्रॉक्सी के
रूप में काम करता है। इस व्यवस्था को
[API एग्रीगेशन](/docs/concepts/extend-kubernetes/api-extension/apiserver-aggregation/)(AA) कहा जाता
है। यूज़र को कुबरनेट्स API एक्सटेंडेड दिखाई देती है।

CRD यूज़र को किसी अन्य API सर्वर को जोड़े बिना नए प्रकार के रिसोर्स बनाने देते हैं। CRD का उपयोग करने के
लिए आपको API एग्रीगेशन समझने की आवश्यकता नहीं है।

चाहे इन्हें कैसे भी इंस्टॉल किया जाए, इनबिल्ट कुबरनेट्स रिसोर्स (जैसे pods) से अलग दिखाने के लिए नए
रिसोर्स को कस्टम रिसोर्स कहा जाता है।

{{< note >}}
एप्लिकेशन, एंड यूज़र, या मॉनिटरिंग डेटा के लिए डेटा स्टोरेज के रूप में कस्टम रिसोर्स का उपयोग करने से
बचें: ऐसे आर्किटेक्चर डिज़ाइन जो एप्लिकेशन डेटा को कुबरनेट्स API के भीतर स्टोर करते हैं, आमतौर पर एक
ऐसा डिज़ाइन दर्शाते हैं जो बहुत अधिक टाइटली कपल्ड है।

आर्किटेक्चरल रूप से, [क्लाउड नेटिव](https://www.cncf.io/about/faq/#what-is-cloud-native) एप्लिकेशन
आर्किटेक्चर कॉम्पोनेंट के बीच लूज़ कपलिंग को प्राथमिकता देते हैं। अगर आपके वर्कलोड के किसी हिस्से को
अपने रूटीन ऑपरेशन के लिए किसी बैकिंग सेवा की आवश्यकता है, तो उस बैकिंग सेवा को एक कॉम्पोनेंट के रूप में
चलाएँ या किसी बाह्य सेवा के रूप में उपयोग करें। इस तरह, आपका वर्कलोड अपने सामान्य ऑपरेशन के लिए
कुबरनेट्स API पर निर्भर नहीं रहता।
{{< /note >}}

## CustomResourceDefinitions {#customresourcedefinitions}

[CustomResourceDefinition](/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definitions/)
API रिसोर्स आपको कस्टम रिसोर्स परिभाषित करने देता है।
एक CRD ऑब्जेक्ट परिभाषित करने से आपके द्वारा बताए गए नाम और स्कीमा के साथ एक नया कस्टम रिसोर्स बनता है।
कुबरनेट्स API आपके कस्टम रिसोर्स को सर्व करता है और उसके स्टोरेज को हैंडल करता है।
CRD ऑब्जेक्ट के नाम को स्वयं परिभाषित रिसोर्स नाम और उसके API ग्रुप से बना एक मान्य
[DNS सबडोमेन नेम](/docs/concepts/overview/working-with-objects/names#dns-subdomain-names) होना चाहिए;
अधिक विवरण के लिए [CRD कैसे बनाएं](/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definitions#create-a-customresourcedefinition)
देखें। साथ ही, ऐसे ऑब्जेक्ट का नाम भी, जिसका kind/resource किसी CRD द्वारा परिभाषित किया गया है, एक
मान्य DNS सबडोमेन नेम होना चाहिए।

इससे आपको कस्टम रिसोर्स को हैंडल करने के लिए अपना स्वयं का API सर्वर लिखने की आवश्यकता नहीं रहती, लेकिन
इम्प्लीमेंटेशन की जेनेरिक प्रकृति का अर्थ है कि आपके पास
[API सर्वर एग्रीगेशन](#api-server-aggregation) की तुलना में कम फ़्लेक्सिबिलिटी है।

किसी नए कस्टम रिसोर्स को रजिस्टर करने, अपने नए रिसोर्स type के इंस्टेंस के साथ काम करने, और इवेंट को
हैंडल करने के लिए किसी नियंत्रक का उपयोग करने के उदाहरण के लिए
[कस्टम नियंत्रक उदाहरण](https://github.com/kubernetes/sample-controller) देखें।

## API सर्वर एग्रीगेशन {#api-server-aggregation}

आमतौर पर, कुबरनेट्स API में हर रिसोर्स के लिए ऐसा कोड आवश्यक होता है जो REST रिक्वेस्ट को हैंडल करे और
ऑब्जेक्ट के पर्सिस्टेंट स्टोरेज को मैनेज करे। मुख्य कुबरनेट्स API सर्वर *pods* और *services* जैसे
इनबिल्ट रिसोर्स को हैंडल करता है, और [CRD](#customresourcedefinitions) के माध्यम से कस्टम रिसोर्स को
भी सामान्य रूप से हैंडल कर सकता है।

[एग्रीगेशन लेयर](/docs/concepts/extend-kubernetes/api-extension/apiserver-aggregation/) आपको अपना
स्वयं का API सर्वर लिखकर और डिप्लॉय करके अपने कस्टम रिसोर्स के लिए विशेष इम्प्लीमेंटेशन प्रदान करने की
अनुमति देती है। मुख्य API सर्वर आपके द्वारा हैंडल किए जाने वाले कस्टम रिसोर्स के लिए रिक्वेस्ट को आपके
API सर्वर पर डेलिगेट करता है, और उन्हें अपने सभी क्लाइंट के लिए उपलब्ध बनाता है।

## कस्टम रिसोर्स जोड़ने का तरीका चुनना

CRD का उपयोग करना आसान है। एग्रीगेटेड API अधिक फ़्लेक्सिबल हैं। जो तरीका आपकी आवश्यकताओं को सबसे अच्छी
तरह पूरा करे, उसे चुनें।

आमतौर पर, CRD एक अच्छा फ़िट हैं अगर:

* आपके पास कुछ ही फ़ील्ड हैं
* आप इस रिसोर्स का उपयोग अपनी कंपनी के भीतर, या किसी छोटे ओपन-सोर्स प्रोजेक्ट के हिस्से के रूप में कर
  रहे हैं (किसी कमर्शियल प्रोडक्ट के विपरीत)

### उपयोग में आसानी की तुलना

CRD बनाना एग्रीगेटेड API की तुलना में आसान है।

| CRD                        | एग्रीगेटेड API |
| --------------------------- | -------------- |
| प्रोग्रामिंग की आवश्यकता नहीं है। यूज़र CRD नियंत्रक के लिए कोई भी भाषा चुन सकते हैं। | प्रोग्रामिंग की आवश्यकता है और बाइनरी और इमेज बनाना पड़ता है। |
| कोई अतिरिक्त सेवा नहीं चलानी पड़ती; CRD को API सर्वर द्वारा हैंडल किया जाता है। | बनाने के लिए एक अतिरिक्त सेवा जो फ़ेल भी हो सकती है। |
| CRD बन जाने के बाद कोई ऑनगोइंग सपोर्ट आवश्यक नहीं है। कोई भी बग फ़िक्स सामान्य कुबरनेट्स मास्टर अपग्रेड के हिस्से के रूप में मिल जाता है। | अपस्ट्रीम से समय-समय पर बग फ़िक्स लेने और एग्रीगेटेड API सर्वर को फिर से बनाने और अपडेट करने की आवश्यकता हो सकती है। |
| अपनी API के कई वर्शन हैंडल करने की आवश्यकता नहीं; उदाहरण के लिए, जब आप इस रिसोर्स के क्लाइंट को नियंत्रित करते हैं, तो आप इसे API के साथ सिंक में अपग्रेड कर सकते हैं। | अपनी API के कई वर्शन हैंडल करने की आवश्यकता है; उदाहरण के लिए, जब दुनिया के साथ शेयर करने के लिए कोई एक्सटेंशन डेवलप कर रहे हों। |

### एडवांस्ड फ़ीचर और फ़्लेक्सिबिलिटी

एग्रीगेटेड API अधिक एडवांस्ड API फ़ीचर और अन्य फ़ीचर, जैसे स्टोरेज लेयर, का कस्टमाइज़ेशन प्रदान करते
हैं।

| फ़ीचर | विवरण | CRD | एग्रीगेटेड API |
| ------- | ----------- | ---- | -------------- |
| वैलिडेशन | यूज़र को गलतियों से बचाने में मदद करता है और आपको अपने क्लाइंट से स्वतंत्र रूप से अपनी API को विकसित करने देता है। ये फ़ीचर तब सबसे उपयोगी होते हैं जब बहुत सारे क्लाइंट हों जो एक साथ अपडेट नहीं हो सकते। | हाँ। अधिकतर वैलिडेशन [OpenAPI v3.0 वैलिडेशन](/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definitions/#validation) का उपयोग करके CRD में बताया जा सकता है। [CRDValidationRatcheting](/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definitions/#validation-ratcheting) फ़ीचर गेट OpenAPI का उपयोग करके बताए गए फ़ेल हो रहे वैलिडेशन को भी अनदेखा करने देता है अगर रिसोर्स का फ़ेल हो रहा हिस्सा नहीं बदला हो। कोई अन्य वैलिडेशन [वैलिडेटिंग वेबहुक](/docs/reference/access-authn-authz/admission-controllers/#validatingadmissionwebhook-alpha-in-1-8-beta-in-1-9) जोड़कर सपोर्ट किया जाता है। | हाँ, मनमाने वैलिडेशन चेक |
| डिफ़ॉल्टिंग | ऊपर देखें | हाँ, या तो [OpenAPI v3.0 वैलिडेशन](/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definitions/#defaulting) के `default` कीवर्ड के माध्यम से (1.17 में GA), या [म्यूटेटिंग वेबहुक](/docs/reference/access-authn-authz/admission-controllers/#mutatingadmissionwebhook) के माध्यम से (हालाँकि पुराने ऑब्जेक्ट के लिए etcd से पढ़ते समय यह नहीं चलेगा)। | हाँ |
| मल्टी-वर्शनिंग | एक ही ऑब्जेक्ट को दो API वर्शन के माध्यम से सर्व करने देता है। फ़ील्ड का नाम बदलने जैसे API बदलावों को आसान बनाने में मदद कर सकता है। अगर आप अपने क्लाइंट वर्शन को नियंत्रित करते हैं तो यह कम महत्वपूर्ण है। | [हाँ](/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definition-versioning) | हाँ |
| कस्टम स्टोरेज | अगर आपको अलग परफ़ॉर्मेंस मोड वाला स्टोरेज (उदाहरण के लिए, key-value स्टोर के बजाय टाइम-सीरीज़ डेटाबेस) या सिक्योरिटी के लिए आइसोलेशन (उदाहरण के लिए, संवेदनशील जानकारी की एन्क्रिप्शन, आदि) चाहिए | नहीं | हाँ |
| कस्टम बिज़नेस लॉजिक | किसी ऑब्जेक्ट को बनाते, पढ़ते, अपडेट करते या डिलीट करते समय मनमाने चेक या एक्शन करें | हाँ, [वेबहुक](/docs/reference/access-authn-authz/extensible-admission-controllers/#admission-webhooks) का उपयोग करके। | हाँ |
| स्केल सबरिसोर्स | HorizontalPodAutoscaler और PodDisruptionBudget जैसे सिस्टम को आपके नए रिसोर्स के साथ इंटरैक्ट करने देता है | [हाँ](/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definitions/#scale-subresource) | हाँ |
| स्टेटस सबरिसोर्स | फ़ाइन-ग्रेन्ड एक्सेस कंट्रोल देता है जहाँ यूज़र spec सेक्शन लिखता है और नियंत्रक status सेक्शन लिखता है। कस्टम रिसोर्स डेटा में बदलाव पर ऑब्जेक्ट Generation को बढ़ाने देता है (रिसोर्स में अलग spec और status सेक्शन आवश्यक हैं) | [हाँ](/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definitions/#status-subresource) | हाँ |
| अन्य सबरिसोर्स | CRUD के अलावा अन्य ऑपरेशन जोड़ें, जैसे "logs" या "exec"। | नहीं | हाँ |
| strategic-merge-patch | नए एंडपॉइंट `Content-Type: application/strategic-merge-patch+json` के साथ PATCH को सपोर्ट करते हैं। ऐसे ऑब्जेक्ट को अपडेट करने के लिए उपयोगी है जिन्हें लोकली और सर्वर द्वारा, दोनों तरह से बदला जा सकता है। अधिक जानकारी के लिए देखें ["kubectl patch का उपयोग करके API ऑब्जेक्ट को अपडेट करें"](/docs/tasks/manage-kubernetes-objects/update-api-object-kubectl-patch/) | नहीं | हाँ |
| प्रोटोकॉल बफ़र्स | नया रिसोर्स ऐसे क्लाइंट को सपोर्ट करता है जो प्रोटोकॉल बफ़र्स का उपयोग करना चाहते हैं | नहीं | हाँ |
| OpenAPI स्कीमा | क्या उन types के लिए कोई OpenAPI (swagger) स्कीमा है जिसे सर्वर से डायनामिक रूप से फ़ेच किया जा सकता है? क्या यह सुनिश्चित करके यूज़र को फ़ील्ड नाम गलत लिखने से बचाया जाता है कि केवल अनुमति प्राप्त फ़ील्ड सेट की जा सकें? क्या types लागू किए जाते हैं (यानी, किसी `string` फ़ील्ड में `int` न डालें?) | हाँ, [OpenAPI v3.0 वैलिडेशन](/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definitions/#validation) स्कीमा के आधार पर (1.16 में GA)। | हाँ |
| इंस्टेंस नेम | क्या यह एक्सटेंशन मैकेनिज़्म उन ऑब्जेक्ट के नामों पर कोई प्रतिबंध लगाता है जिनका kind/resource इस तरीके से परिभाषित किया गया है? | हाँ, ऐसे ऑब्जेक्ट का नाम एक मान्य DNS सबडोमेन नेम होना चाहिए। | नहीं |

### सामान्य फ़ीचर {#common-features}

जब आप कोई कस्टम रिसोर्स बनाते हैं, चाहे CRD के माध्यम से हो या AA के माध्यम से, आपको कुबरनेट्स प्लेटफ़ॉर्म
के बाहर इसे इम्प्लीमेंट करने की तुलना में अपनी API के लिए कई फ़ीचर मिलते हैं:

| फ़ीचर | यह क्या करता है |
| ------- | ------------ |
| CRUD | नए एंडपॉइंट HTTP और `kubectl` के माध्यम से बेसिक CRUD ऑपरेशन को सपोर्ट करते हैं |
| Watch | नए एंडपॉइंट HTTP के माध्यम से कुबरनेट्स Watch ऑपरेशन को सपोर्ट करते हैं |
| डिस्कवरी | `kubectl` और डैशबोर्ड जैसे क्लाइंट आपके रिसोर्स पर लिस्ट, डिस्प्ले, और फ़ील्ड एडिट ऑपरेशन स्वचालित रूप से देते हैं |
| json-patch | नए एंडपॉइंट `Content-Type: application/json-patch+json` के साथ PATCH को सपोर्ट करते हैं |
| merge-patch | नए एंडपॉइंट `Content-Type: application/merge-patch+json` के साथ PATCH को सपोर्ट करते हैं |
| HTTPS | नए एंडपॉइंट HTTPS का उपयोग करते हैं |
| इनबिल्ट ऑथेंटिकेशन | एक्सटेंशन तक एक्सेस ऑथेंटिकेशन के लिए कोर API सर्वर (एग्रीगेशन लेयर) का उपयोग करता है |
| इनबिल्ट ऑथराइज़ेशन | एक्सटेंशन तक एक्सेस कोर API सर्वर द्वारा उपयोग किए जाने वाले ऑथराइज़ेशन का फिर से उपयोग कर सकता है; उदाहरण के लिए, RBAC। |
| फ़ाइनलाइज़र | एक्सटेंशन रिसोर्स के डिलीशन को तब तक ब्लॉक करता है जब तक बाह्य क्लीनअप न हो जाए। |
| एडमिशन वेबहुक | किसी भी क्रिएट/अपडेट/डिलीट ऑपरेशन के दौरान डिफ़ॉल्ट वैल्यू सेट करें और एक्सटेंशन रिसोर्स को वैलिडेट करें। |
| UI/CLI डिस्प्ले | Kubectl, डैशबोर्ड एक्सटेंशन रिसोर्स को दिखा सकते हैं। |
| अनसेट बनाम खाली | क्लाइंट अनसेट फ़ील्ड को ज़ीरो-वैल्यू फ़ील्ड से अलग बता सकते हैं। |
| क्लाइंट लाइब्रेरी जनरेशन | कुबरनेट्स जेनेरिक क्लाइंट लाइब्रेरी, साथ ही type-specific क्लाइंट लाइब्रेरी जनरेट करने के टूल प्रदान करता है। |
| लेबल और एनोटेशन | ऑब्जेक्ट में सामान्य मेटाडेटा जिसे टूल कोर और कस्टम रिसोर्स दोनों के लिए एडिट करना जानते हैं। |

## कस्टम रिसोर्स इंस्टॉल करने की तैयारी

अपने क्लस्टर में कोई कस्टम रिसोर्स जोड़ने से पहले ध्यान देने वाली कई बातें हैं।

### थर्ड पार्टी कोड और फ़ेल्योर के नए बिंदु

हालाँकि CRD बनाने से अपने आप कोई नया फ़ेल्योर पॉइंट नहीं जुड़ता (उदाहरण के लिए, आपके API सर्वर पर थर्ड
पार्टी कोड चलाने के कारण), पैकेज (उदाहरण के लिए, Charts) या अन्य इंस्टॉलेशन बंडल में अक्सर CRD के साथ
नए कस्टम रिसोर्स के लिए बिज़नेस लॉजिक इम्प्लीमेंट करने वाले थर्ड-पार्टी कोड का एक Deployment भी शामिल
होता है।

एग्रीगेटेड API सर्वर इंस्टॉल करने में हमेशा एक नया Deployment चलाना शामिल होता है।

### स्टोरेज

कस्टम रिसोर्स उसी तरह स्टोरेज स्पेस का उपयोग करते हैं जैसे ConfigMap करते हैं। बहुत अधिक कस्टम रिसोर्स
बनाने से आपके API सर्वर का स्टोरेज स्पेस ओवरलोड हो सकता है।

कस्टम रिसोर्स को CRD स्पेक में परिभाषित रिसोर्स के मौजूदा स्टोरेज वर्शन के आधार पर स्टोरेज में रखा जाता
है। किसी कस्टम रिसोर्स में कोई भी अपडेट रिसोर्स को स्टोर करने के लिए मौजूदा परिभाषित स्टोरेज वर्शन का
उपयोग करेगा। अन्य सभी वर्शन को सही ढंग से काम करने के लिए उस वर्शन के सभी फ़ील्ड होने चाहिए या कन्वर्ज़न
परिभाषित करना चाहिए।

एग्रीगेटेड API सर्वर मुख्य API सर्वर के समान स्टोरेज का उपयोग कर सकते हैं, जिस स्थिति में वही चेतावनी
लागू होती है।

### ऑथेंटिकेशन, ऑथराइज़ेशन, और ऑडिटिंग

CRD हमेशा आपके API सर्वर के इनबिल्ट रिसोर्स की तरह ही ऑथेंटिकेशन, ऑथराइज़ेशन, और ऑडिट लॉगिंग का उपयोग
करते हैं।

अगर आप ऑथराइज़ेशन के लिए RBAC का उपयोग करते हैं, तो अधिकतर RBAC रोल नए रिसोर्स तक एक्सेस नहीं देंगे
(cluster-admin रोल या वाइल्डकार्ड नियमों के साथ बनाए गए किसी भी रोल को छोड़कर)। आपको नए रिसोर्स तक
एक्सेस स्पष्ट रूप से देना होगा। CRD और एग्रीगेटेड API अक्सर उनके द्वारा जोड़े गए types के लिए नए रोल
डेफ़िनिशन के साथ बंडल होकर आते हैं।

एग्रीगेटेड API सर्वर प्राइमरी API सर्वर के समान ऑथेंटिकेशन, ऑथराइज़ेशन, और ऑडिटिंग का उपयोग कर सकते हैं
या नहीं भी कर सकते।

## किसी कस्टम रिसोर्स को एक्सेस करना

कस्टम रिसोर्स को एक्सेस करने के लिए कुबरनेट्स [क्लाइंट लाइब्रेरी](/docs/reference/using-api/client-libraries/)
का उपयोग किया जा सकता है। सभी क्लाइंट लाइब्रेरी कस्टम रिसोर्स को सपोर्ट नहीं करती। _Go_ और _Python_
क्लाइंट लाइब्रेरी करती हैं।

जब आप कोई कस्टम रिसोर्स जोड़ते हैं, तो आप इसे इनका उपयोग करके एक्सेस कर सकते हैं:

- `kubectl`
- कुबरनेट्स डायनामिक क्लाइंट।
- एक REST क्लाइंट जो आप स्वयं लिखते हैं।
- [कुबरनेट्स क्लाइंट जनरेशन टूल](https://github.com/kubernetes/code-generator) का उपयोग करके
  जनरेट किया गया क्लाइंट (एक जनरेट करना एक एडवांस्ड काम है, लेकिन कुछ प्रोजेक्ट CRD या AA के साथ
  क्लाइंट भी प्रदान कर सकते हैं)।


## कस्टम रिसोर्स फ़ील्ड सिलेक्टर

[फ़ील्ड सिलेक्टर](/docs/concepts/overview/working-with-objects/field-selectors/) क्लाइंट को एक या
अधिक रिसोर्स फ़ील्ड की वैल्यू के आधार पर कस्टम रिसोर्स चुनने देते हैं।

सभी कस्टम रिसोर्स `metadata.name` और `metadata.namespace` फ़ील्ड सिलेक्टर को सपोर्ट करते हैं।

{{< glossary_tooltip term_id="CustomResourceDefinition" text="CustomResourceDefinition" >}} में
घोषित फ़ील्ड को भी फ़ील्ड सिलेक्टर के साथ उपयोग किया जा सकता है जब उन्हें
{{< glossary_tooltip term_id="CustomResourceDefinition" text="CustomResourceDefinition" >}} के
`spec.versions[*].selectableFields` फ़ील्ड में शामिल किया गया हो।

### कस्टम रिसोर्स के लिए सिलेक्ट करने योग्य फ़ील्ड {#crd-selectable-fields}

{{< feature-state feature_gate_name="CustomResourceFieldSelectors" >}}

किसी {{< glossary_tooltip term_id="CustomResourceDefinition" text="CustomResourceDefinition" >}} के
`spec.versions[*].selectableFields` फ़ील्ड का उपयोग यह बताने के लिए किया जा सकता है कि किसी कस्टम
रिसोर्स के कौन-से अन्य फ़ील्ड फ़ील्ड सिलेक्टर में उपयोग किए जा सकते हैं।

नीचे दिया गया उदाहरण `.spec.color` और `.spec.size` फ़ील्ड को सिलेक्ट करने योग्य फ़ील्ड के रूप में
जोड़ता है।

{{% code_sample file="customresourcedefinition/shirt-resource-definition.yaml" %}}

फ़ील्ड सिलेक्टर का उपयोग फिर केवल उन रिसोर्स को पाने के लिए किया जा सकता है जिनका `color` `blue` है:

```shell
kubectl get shirts.stable.example.com --field-selector spec.color=blue
```

आउटपुट कुछ इस तरह होना चाहिए:

```
NAME       COLOR  SIZE
example1   blue   S
example2   blue   M
```
