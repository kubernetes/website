<!-- body -->

## Общие сведения {#background}

Kubernetes спроектирован так, чтобы один кластер мог работать в нескольких зонах отказа,
обычно входящих в логическую группу, называемую _регионом_. Крупные облачные провайдеры
определяют регион как набор зон отказа (также называемых _зонами доступности_),
предоставляющих одинаковый набор возможностей: в пределах региона каждая зона
предоставляет одни и те же API и сервисы.

Типичная облачная архитектура стремится минимизировать вероятность того, что отказ
в одной зоне также нарушит работу сервисов в другой.

## Поведение управляющего слоя {#control-plane-behavior}

Все [компоненты управляющего слоя](/ru/docs/concepts/overview/components/#компоненты-управляющего-слоя)
поддерживают работу в виде пула взаимозаменяемых ресурсов с репликацией каждого компонента.

При развёртывании управляющего слоя кластера размещайте реплики его компонентов
в нескольких зонах отказа. Если доступность важна, выберите не менее трёх зон отказа
и реплицируйте каждый отдельный компонент управляющего слоя (сервер API, планировщик,
etcd, менеджер контроллеров кластера) как минимум в трёх зонах отказа.
Если вы используете диспетчер облачных контроллеров, его также следует реплицировать
во всех выбранных зонах отказа.

{{< note >}}
Kubernetes не обеспечивает устойчивость конечных точек сервера API к отказам зон.
Для повышения доступности сервера API кластера можно использовать различные методы,
включая DNS round-robin, записи SRV или стороннюю балансировку нагрузки с проверкой работоспособности.
{{< /note >}}

## Поведение узлов {#node-behavior}

Kubernetes автоматически распределяет поды ресурсов рабочих нагрузок
(таких как [Deployment](/docs/concepts/workloads/controllers/deployment/)
или [StatefulSet](/docs/concepts/workloads/controllers/statefulset/))
между разными узлами кластера. Такое распределение помогает уменьшить влияние отказов.

При запуске узлов kubelet на каждом из них автоматически добавляет
{{< glossary_tooltip text="метки" term_id="label" >}} к объекту Node,
представляющему этот kubelet в API Kubernetes. Эти метки могут содержать
[сведения о зоне](/docs/reference/labels-annotations-taints/#topologykubernetesiozone).

Если кластер охватывает несколько зон или регионов, можно использовать метки узлов вместе с
[ограничениями на топологию распределения подов](/docs/concepts/scheduling-eviction/topology-spread-constraints/),
чтобы управлять распределением подов между доменами отказа: регионами, зонами и даже отдельными узлами.
Эти указания позволяют [планировщику](/docs/reference/command-line-tools-reference/kube-scheduler/)
размещать поды с расчётом на более высокую доступность, уменьшая риск того,
что связанный отказ затронет всю рабочую нагрузку.

Например, можно задать ограничение, чтобы три реплики StatefulSet по возможности
работали в разных зонах. Это можно описать декларативно, не указывая явно,
какие именно зоны доступности используются для каждой рабочей нагрузки.

### Распределение узлов между зонами {#distributing-nodes-across-zones}

Ядро Kubernetes не создаёт узлы: это нужно делать самостоятельно или с помощью инструмента,
такого как [Cluster API](https://cluster-api.sigs.k8s.io/), который управляет узлами от вашего имени.

Инструменты вроде Cluster API позволяют определить наборы машин, которые будут рабочими узлами
кластера в нескольких доменах отказа, и правила автоматического восстановления кластера
при нарушении работы сервисов в целой зоне.

## Назначение зоны подам вручную {#manual-zone-assignment-for-pods}

К создаваемым подам, а также к шаблонам подов в ресурсах рабочих нагрузок, таких как Deployment,
StatefulSet или Job, можно применять
[ограничения выбора узла](/docs/concepts/scheduling-eviction/assign-pod-node/#nodeselector).

## Доступ к хранилищу в зонах {#storage-access-for-zones}

При создании постоянных томов Kubernetes автоматически добавляет метки зоны
ко всем PersistentVolume, привязанным к определённой зоне.
Затем [планировщик](/docs/reference/command-line-tools-reference/kube-scheduler/)
с помощью предиката `NoVolumeZoneConflict` гарантирует, что поды, запрашивающие
данный PersistentVolume, будут размещены только в той же зоне, что и этот том.

Способ добавления меток зоны может зависеть от облачного провайдера и используемого
средства предоставления хранилища. Всегда сверяйтесь с документацией вашей среды,
чтобы обеспечить правильную настройку.

Для PersistentVolumeClaim можно указать
[StorageClass](/docs/concepts/storage/storage-classes/),
определяющий домены отказа (зоны), в которых может находиться хранилище этого класса.
О настройке StorageClass с учётом доменов отказа или зон см. раздел
[Допустимые топологии](/docs/concepts/storage/storage-classes/#allowed-topologies).

## Сеть {#networking}

Сам по себе Kubernetes не включает сетевые средства с учётом зон. Для настройки сети кластера
можно использовать [сетевой плагин](/docs/concepts/extend-kubernetes/compute-storage-net/network-plugins/),
и выбранное сетевое решение может содержать элементы, учитывающие зоны.
Например, если облачный провайдер поддерживает сервисы с `type=LoadBalancer`,
балансировщик нагрузки может направлять трафик только к подам в той же зоне,
где находится обрабатывающий соединение элемент балансировщика.
Подробности см. в документации облачного провайдера.

Аналогичные соображения применимы к пользовательским развёртываниям и развёртываниям
на собственной инфраструктуре. Поведение [Service](/docs/concepts/services-networking/service/)
и [Ingress](/docs/concepts/services-networking/ingress/), включая обработку разных зон отказа,
зависит от конкретной настройки кластера.

## Восстановление после отказа {#fault-recovery}

При настройке кластера также может понадобиться продумать, сможет ли он восстановить работу,
если все зоны отказа в регионе одновременно станут недоступны, и как именно.
Например, полагаетесь ли вы на наличие хотя бы одного узла в зоне, способного запускать поды?
Убедитесь, что критически важные операции восстановления не зависят от наличия хотя бы
одного исправного узла в кластере. Например, если все узлы неисправны, может понадобиться
запустить задание Job для восстановления со специальным
[допуском](/docs/concepts/scheduling-eviction/taint-and-toleration/), чтобы восстановление
смогло продвинуться достаточно далеко для возврата хотя бы одного узла в работу.

Kubernetes не предоставляет готового решения этой задачи, но её следует учитывать.
