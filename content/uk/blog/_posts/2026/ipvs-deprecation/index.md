Бекенд `ipvs` для kube-proxy був експериментом зі створення реалізації проксі для Service із кращою продуктивністю, ніж у бекенда `iptables`. Цієї мети вдалося досягти, але API IPVS ядра виявився невдалим відповідником API Services Kubernetes, і бекенд `ipvs` так і не зміг коректно реалізувати всі граничні випадки функціональності API Service Kubernetes.

У Kubernetes 1.29 проєкт представив бекенд `nftables` для kube-proxy, який у версії 1.33 отримав статус GA. План появи бекенда `nftables` передбачав, що з часом він замінить і бекенди `iptables`, і `ipvs`. Оскільки бекенд `ipvs` особливо складний, не має повної функціональності та архітектурно суттєво відрізняється від двох інших бекендів, його підтримка потребує більше зусиль. Тому SIG Network Kubernetes вирішила офіційно оголосити його застарілим, починаючи з Kubernetes 1.35. Хоча зараз він іще доступний у kube-proxy (із попередженням про застарівання), ми (SIG Network Kubernetes) плануємо повністю видалити його у версії 1.40. Отже, усім користувачам `ipvs` слід планувати перехід на бекенд `nftables` або `iptables`.

## Навіщо створили бекенд `ipvs`? {#why-was-the-ipvs-backend-written}

Бекенд `ipvs` спочатку розробили для усунення двох різних проблем продуктивності бекенда `iptables`:

- По-перше, `iptables` мав проблеми із затримкою _площини даних_ (швидкістю, з якою клієнти можуть встановлювати нові зʼєднання з Services), оскільки kube-proxy записував окреме правило iptables для кожної IP-адреси Service. Тому кожне нове зʼєднання доводилося перевіряти за довгою послідовністю правил, кількість яких зростала як **O(n)** від кількості Services у кластері.

- По-друге, проблема із затримкою на панелі управління була ще серйознішою: kube-proxy повністю переписував набір правил iptables щоразу, коли змінювався будь-який обʼєкт Service або endpoint. Хоча сам список правил зростав лише як **O(n)** від загальної кількості endpoints, час, памʼять і процесорний ресурс, потрібні для обробки оновленого набору, зростали швидше. У дуже великих кластерах kube-proxy постійно використовував 100% одного ядра процесора лише для обробки оновлень iptables. (Насправді проблема масштабування панелі управління була настільки серйозною, що більшість користувачів навіть не могла збільшити кластер до розміру, за якого ставала помітною проблема масштабування площини даних.)

Бекенд `ipvs` розвʼязав обидві проблеми масштабування. Проблема площини даних розвʼязалася майже автоматично, адже підсистема IPVS ядра використовує хеш-таблиці замість лінійного пошуку. Проблему панелі управління розвʼязали тим, що більше не переписували весь набір правил під час кожного оновлення. (У API IPVS ядра все одно немає можливості пакетного оновлення, тож фактично іншого варіанта не було.)

## Чому бекенд `ipvs` тепер застаріває? {#why-is-the-ipvs-backend-now-being-deprecated}

Проблеми в бекенда `ipvs` були майже від самого початку.

Перша версія не була повністю сумісна з бекендом `iptables`, але очікувалося, що з часом цю проблему усунуть. На жаль, початкові автори перейшли до інших справ поза екосистемою Kubernetes (таке неминуче трапляється у відкритих проєктах), і знадобився час, щоб знайти людей, зацікавлених у підтримці коду.

Тим часом зі зростанням кластерів, у яких використовували бекенд `ipvs`, почали проявлятися його власні проблеми масштабування. Зокрема, через відсутність пакетних операцій оновлення в API IPVS бекенд `ipvs` був швидшим за `iptables` під час невеликої кількості змін, але міг працювати повільніше під час одночасного внесення великої кількості змін. Крім того, через обмежені можливості API IPVS бекенду `ipvs` у kube-proxy доводилося використовувати iptables для реалізації різних функцій служб Kubernetes, що виходять за межі базового «балансування навантаження». У результаті виникали ті самі проблеми масштабування, що й у бекенда `iptables`. Бекенд `ipvs` намагався помʼякшити їх, використовуючи `ipset` для деяких правил, але це знову впиралося у відсутність API пакетного оновлення.

Крім того, оскільки бекенд `ipvs` використовує iptables, він має ту саму проблему довгострокової підтримки, що й бекенд `iptables`: план Red Hat повністю прибрати API iptables із Red Hat Enterprise Linux означає, що користувачі Kubernetes на RHEL також більше не зможуть використовувати бекенд `ipvs` у kube-proxy.

### А як щодо планувальників IPVS? {#what-about-ipvs-schedulers}

Окрім продуктивності, деяких користувачів приваблювала можливість вибирати серед різних «планувальників» IPVS для розподілу трафіку між кінцевими точками замість простого випадкового вибору, який використовують `iptables` та `nftables`.

На жаль, спосіб використання IPVS у kube-proxy не дає змоги _корисно_ застосовувати більшість планувальників IPVS. Проблема полягає в тому, що kube-proxy — розподілена служба, яка працює на всіх вузлах кластера, але процеси kube-proxy на різних вузлах не діляться станом планувальника IPVS. Тому кожен вузол вибирає кінцеві точки, не знаючи, що відбувається з клієнтами на інших вузлах. Навіть планувальники, розроблені для розподіленої роботи, зазвичай не працюють у контексті kube-proxy краще за випадковий вибір. Наприклад, планувальник `mh` використовує хешування Maglev для вибору кінцевих точок, що теоретично дає змогу надзвичайно ефективно балансувати навантаження розподіленим способом. Але ця ефективність можлива лише в контексті [певного типу дворівневої архітектури балансувальника навантаження], а архітектура kube-proxy не дає змоги виконувати функції _жодного_ з цих двох рівнів.

[певного типу дворівневої архітектури балансувальника навантаження]: https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/44824.pdf

## Перехід з `ipvs` {#switching-away-from-ipvs}

### Перехід на `nftables` {#switching-to-nftables}

Якщо ви використовуєте Kubernetes версії 1.36 або новішої, дистрибутив Linux на вузлах із ядром версії 5.13 або новішої, а режим проксі `ipvs`, Kubernetes рекомендує перейти на режим `nftables` у kube-proxy. (Хоча бекенд `nftables` отримав статус GA — і повністю придатний до використання — у Kubernetes 1.33, після цього зʼявилися виправлення продуктивності та масштабування, які не було перенесено до випусків раніше за 1.36.)

Бекенд `nftables` повністю підтримується, має всю необхідну функціональність і навіть _трохи_ перевершує `ipvs` за продуктивністю:

{{< figure src="ipvs-vs-nftables.svg" alt="Затримка першого пакета для kube-proxy у режимах ipvs та nftables на різних процентилях і в кластерах різного розміру" >}}

(Вищі стовпчики відповідають більшій затримці. Група «p50» показує середню затримку встановлення зʼєднання. Зверніть увагу, що навіть найбільші значення на графіку дуже малі; мета не в тому, щоб стверджувати, що `nftables` помітно швидший за `ipvs`, а лише показати, що він, на відміну від `iptables`, не повільніший.)

Перехід простий: змініть конфігурацію kube-proxy та перезапустіть його. Наприклад, у кластерах, розгорнутих за допомогою kubeadm, змініть `mode: ipvs` на `mode: nftables` у ConfigMap `kube-proxy`, а потім перезапустіть поди kube-proxy, як описано в документації про [переналаштування кластера kubeadm]. (Якщо ви перевизначали інші параметри конфігурації kube-proxy, специфічні для `ipvs`, їх також потрібно змінити на [відповідні параметри `nftables`].)

### Перехід на `iptables`: «Він не такий повільний, як ви думаєте!» {#switching-to-iptables}

Якщо ви не можете перейти на `nftables` — через старішу версію Kubernetes або старий дистрибутив Linux, що не підтримує бекенд `nftables`, — можливо, варто просто перейти на бекенд `iptables`. Від часу створення бекенда `ipvs` у 2017 році `iptables` значно покращився:

- Створюваний набір правил оптимізували, щоб вилучити надлишкові та нерелевантні правила ([#57461], [#60306], [#96959], [#108251]), що зменшило затримку площини даних.

- Код генерації набору правил оптимізували: він виконує менше виділень памʼяті та уникає повторного непотрібного обчислення тієї самої інформації ([#65755], [#65902], [#67948], [#85617], [#90103], [#97238]), що зменшує використання процесора та памʼяті під час повторної синхронізації.

- Замість підходу «перевірити поточний стан правил, а потім оновити його» kube-proxy з `iptables` тепер використовує підхід «вважати поточний стан правильним, оновити його до нового стану на основі цього припущення та явно перевіряти поточний стан лише в разі невдалого оновлення». Це значно пришвидшує повторну синхронізацію, адже виявилося, що навіть _читання_ набору правил iptables у великих кластерах надзвичайно повільне ([#81517], [#110334], [#114181]).

- Наскільки це можливо з огляду на обмеження API iptables, бекенд `iptables` у kube-proxy тепер оновлює правила лише для обʼєктів Service та endpoints, що змінилися після останньої синхронізації, а не переписує весь набір правил щоразу ([#110268] / [KEP-3453]).

У результаті `iptables` у 2026 році, хоч і поступається `ipvs`, значно кращий за `iptables` 2017 року. Багато користувачів, які раніше не могли використовувати `iptables`, тепер не матимуть із ним проблем.

Як і у випадку з переходом на `nftables`, для переходу на `iptables` переважно потрібно оновити конфігурацію kube-proxy. Однак з технічних причин у цьому випадку рекомендуємо перезавантажити кожен вузол після зміни конфігурації kube-proxy, а не лише перезапустити kube-proxy.
