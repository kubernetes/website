Kubernetes непомітно став стандартною платформою для AI та машинного навчання. Незалежно від того, чи ви запускаєте сервери notebook для дослідників даних, плануєте розподілені тренувальні завдання, налаштовуєте гіперпараметри чи керуєте багатоступеневими ML-пайплайнами, ці навантаження дедалі частіше потрапляють в кластер Kubernetes. [Kubeflow](https://www.kubeflow.org/) — одна з найпопулярніших платформ для складання такого стеку, і вона робить це природним для Kubernetes способом: кожна можливість надається як Custom Resource Definition (CRD).

Такий дизайн є подарунком для операторів кластерів, оскільки це означає, що за ML-навантаженнями можна спостерігати та керувати ними тими ж примітивами, що й усіма іншими в кластері. Але на практиці спеціалізовані ML-інфопанелі, що постачаються з цими платформами, приховують Kubernetes-рівень під собою. Коли notebook застрягає або тренувальний запуск завершується невдало, оператор часто змушений повернутися до `kubectl`, щоб дізнатися, що насправді сталося на рівні Podʼа.

Тут представлено **втулок Headlamp для Kubeflow**, який усуває цю прогалину, показуючи власні ресурси Kubeflow безпосередньо в універсальному інтерфейсі Kubernetes. Це наочний приклад підходу, якого може дотримуватися будь-яка платформа, що активно використовує CRD: взаємодіяти з операторами там, де вони вже працюють, і надавати їм достовірну інформацію на рівні кластера.

Сам Headlamp — це розширюваний веб-інтерфейс Kubernetes, що підтримується [Kubernetes SIG UI](https://github.com/kubernetes-sigs/headlamp) та ліцензований за ліцензією Apache 2.0. Він працює як десктоп-застосунок або в кластері, а його система втулків дозволяє будь-кому додавати першокласні представлення для власних ресурсів.

## Чому операторам потрібне інше представлення {#why-operators-need-a-different-view}

Спеціалізовані ML-інфопанелі допомагають дослідникам даних подавати експерименти, пайплайни та notebookʼи. Оператори кластерів та інженери надійності сайтів (SRE) шукають несправності в Kubernetes-ресурсах, що лежать в їх основі, і вони задають інші запитання:

- Чому notebook застряг? Чи це `ImagePullBackOff`, `OOMKilled` чи Pod, що очікує PersistentVolumeClaim?
- Які ресурси Run нещодавно завершилися невдало в різних просторах імен?
- Який набір параметрів Katib Experiment визнає оптимальним?
- Чи посилаються ресурси TrainJob на очікувані ресурси TrainingRuntime?
- Які пакетні навантаження виконуються та який стан показує Kubernetes?

Втулок Headlamp Kubeflow допомагає відповісти на ці запитання, зчитуючи дані безпосередньо з API-сервера Kubernetes. Він показує умови Podʼів, причини збоїв в Kubernetes та ресурси в різних просторах імен без необхідності посередницького ML-сервісу чи бази даних.

## Що охоплює цей втулок {#what-the-plugin-covers}

Kubeflow є модульним, і команди часто встановлюють лише ті компоненти, які їм потрібні. Втулок виявляє API-групи Kubeflow у кластері та показує лише відповідні розділи.

Втулок підтримує такі родини компонентів та API-ресурси:

{{< table caption="Компоненти Kubeflow та API-ресурси, підтримувані втулком Headlamp" >}}
| Компонент | Призначення | API-ресурси |
| :--- | :--- | :--- |
| **Notebooks** | Надає середовища розробки, такі як Jupyter, VS Code та RStudio | Notebook, Profile, PodDefault |
| **Pipelines** | Визначає та відстежує пайплайни, версії, експерименти, запуски та розклади | Pipeline, PipelineVersion, Run, RecurringRun, Experiment |
| **Katib** | Автоматизує налаштування гіперпараметрів та пошук нейронних архітектур | Experiment, Trial, Suggestion |
| **Training** | Виконує розподілені тренувальні навантаження, такі як завдання PyTorch та TensorFlow | TrainJob, TrainingRuntime, ClusterTrainingRuntime |
| **Spark** | Виконує масштабну обробку даних за допомогою Apache Spark | SparkApplication, ScheduledSparkApplication |
{{< /table >}}

## Що ви можете побачити {#what-you-can-see}

### Інспектуйте Podʼи notebook {#inspect-notebook-pods}

Детальний вигляд Notebook показує умови Podʼів та їхні поля `reason` та `message`. Він також показує запити та обмеження CPU, памʼяті та GPU; монтування томів та їхні типи, такі як PersistentVolumeClaim, ConfigMap, Secret чи `emptyDir`; змінні середовища, що посилаються на Secret чи ConfigMap обʼєкти; sidecar-контейнери; та toleration вузлів. Цей вигляд консолідує інформацію, яка в іншому випадку вимагала б кількох команд `kubectl describe`.

### Інспектуйте налаштування гіперпараметрів {#inspect-hyperparameter-tuning}

Представлення Katib показують алгоритм налаштування, простір пошуку, кожен Trial з його поточним статусом та поточний найкращий Trial з його метричними значеннями та призначеннями параметрів. Вони також показують конфігурацію раннього зупинення та кількість ресурсів Trial, що зупинилися рано, щоб ви могли слідкувати за пошуком, не виходячи з UI кластера.

### Інспектуйте стан пайплайну без бази даних бекенду {#inspect-pipeline-state-without-the-backend-database}

Представлення Pipelines зчитують Kubernetes-ресурси API безпосередньо та не запитують Kubeflow Pipelines API-сервіс чи базу даних бекенду. Ви можете інспектувати збережений стан пайплайну навіть коли цей сервіс недоступний. Детальний вигляд Pipeline надає порівняння останньої та попередньої версій PipelineVersion у вигляді паралельного порівняння у форматі YAML. Представлення Run показують стан та тривалість, представлення RecurringRun показують зрозумілі розклади, а представлення artifacts агрегує значення `pipelineRoot` з останніх ресурсів Run.

### Мапа ML-ресурсів {#map-ml-resources}

Втулок реєструє [Headlamp map source](https://headlamp.dev/docs/latest/development/plugins/functionality/extending-the-map/), що показує ресурси Notebook, Profile, PodDefault, Experiment, Pipeline, SparkApplication та TrainJob як вузли графа. Він малює ребра між підтримуваними ресурсами на основі `.metadata.ownerReferences`. Headlamp також показує вбудовані зведення для цих типів ресурсів, коли ви наводите на них курсор.

## Спробуйте {#try-it}

[README втулка Kubeflow](https://github.com/headlamp-k8s/plugins/blob/main/kubeflow/README.md) пояснює встановлення та налаштування локального кластера, включаючи полегшений варіант лише з CRD для ознайомлення. Оскільки втулок виявляє встановлені API-групи, ви можете використовувати його з наявною модульною інсталяцією Kubeflow чи створити кластер для ознайомлення лише з CRD та зразковими ресурсами.

## Застосуйте шаблон до інших платформ {#apply-the-pattern-to-other-platforms}

Kubeflow ілюструє ширший шаблон. Платформи часто моделюють предметно-орієнтовані робочі процеси за допомогою власних ресурсів. Їхні інфопанелі зосереджені на цих робочих процесах, тоді як Kubernetes-оператори також потребують стану базових API-ресурсів та Podʼів. Втулок, що працює на основі CRD, у загальному Kubernetes UI може показувати цей стан, не змушуючи операторів перемикатися між незвʼязаними інструментами.

Втулок використовує ліцензію Apache 2.0 та розробляється під егідою Kubernetes SIG UI. Щоб повідомити про проблему чи зробити покращення, скористайтеся [issue tracker](https://github.com/headlamp-k8s/plugins/issues) чи [pull requests](https://github.com/headlamp-k8s/plugins/pulls) репозиторію втулків Headlamp.
