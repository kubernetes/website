Підтримка Podʼів із _просторами імен користувачів_ стала загальнодоступною (GA) у Kubernetes v1.36. Ця можливість забезпечує додаткову межу ізоляції, зіставляючи ідентифікатори користувачів і груп усередині Podʼа з іншими ідентифікаторами на вузлі. Докладніше про це читайте в [документації про простори імен користувачів](/docs/concepts/workloads/pods/user-namespaces/).

У звичайному контейнері Linux процес, що працює від імені `root` усередині контейнера, також вважається `root` з погляду вузла. Якщо ввімкнено підтримку просторів імен користувачів, натомість `root` усередині контейнера можна зіставити з непривілейованим користувачем на вузлі.

Pod може ввімкнути цю ізоляцію, встановивши:

```yaml
hostUsers: false
```

Це дає змогу процесу залишатися UID 0 усередині контейнера, водночас з погляду вузла його буде зіставлено з іншим, непривілейованим діапазоном UID.

Однак для розробників локальне тестування цієї можливості може виявитися напрочуд складним.

Pod із `hostUsers: false` може успішно працювати в одній конфігурації Minikube й завершуватися помилкою в іншій. Причина не обовʼязково в самому Kubernetes. Вона може залежати від способу запуску вузла Kubernetes і середовища, доступного для середовища виконання контейнерів.

Важливі такі рівні:

**Вузол Kubernetes → середовище виконання контейнерів → середовище виконання OCI → ядро Linux**

У середовищі Minikube є ще один важливий чинник: драйвер Minikube визначає, як саме запускається вузол Kubernetes. Це, своєю чергою, впливає на середовище, доступне для середовища виконання контейнерів і середовища виконання OCI.

У цій статті розглянуто дві конфігурації Minikube, які завершилися помилками під час тестування, визначено рівень, відповідальний за кожну помилку, і показано, як драйвер на основі віртуальної машини може створити робоче середовище для локального тестування `hostUsers: false`.

## Що потрібно знати перед тестуванням {#what-you-need-to-understand-before-testing}

Перш ніж шукати причину проблеми з `hostUsers: false`, перевірте дві складові локального середовища Kubernetes:

1. **Драйвер Minikube:** як саме запущено вузол Kubernetes.
2. **Середовище виконання контейнерів:** програмне забезпечення, що створює контейнери всередині цього вузла та керує ними.

### Драйвер Minikube визначає, де запускається вузол Kubernetes {#the-minikube-driver-determines-where-the-kubernetes-node-runs}

Під час запуску Minikube ви обираєте драйвер.

Наприклад:

```bash
minikube start --driver=docker
```

З драйвером Docker Minikube створює вузол Kubernetes як **контейнер Docker на вашому хості**.

Отже, сам вузол Kubernetes працює всередині контейнера.

Спрощена схема має такий вигляд:

{{< figure src="docker-driver-node.svg" alt="Драйвер Docker і вузол Kubernetes" >}}

Ця додаткова межа контейнера має значення, оскільки середовищу виконання контейнерів усередині вузла Minikube можуть знадобитися операції з просторами імен Linux і монтуванням під час створення Podʼа.

Інший варіант — драйвер `kvm2`:

```bash
minikube start --driver=kvm2
```

З `kvm2` Minikube запускає вузол (або вузли) Kubernetes у _віртуальній машині_, а не як контейнер.

Віртуальна машина має власну гостьову операційну систему й ядро Linux, тому вузол Kubernetes більше не є контейнером, вкладеним у контейнерне середовище хоста.

Середовище виглядає приблизно так:

{{< figure src="kvm2-driver-node.svg" alt="Драйвер KVM2 і вузол Kubernetes" >}}

Ця різниця в межі вузла є ключовою для поведінки, яку спостерігали під час тестів.

### Що таке KVM і libvirt? {#what-are-kvm-and-libvirt}

**KVM (Kernel-based Virtual Machine)** — технологія віртуалізації Linux, що дає змогу системі запускати віртуальні машини за допомогою апаратної підтримки віртуалізації.

**libvirt** — рівень керування та набір інструментів для створення віртуальних машин і керування ними та їхніми ресурсами.

Для цього тесту не потрібно керувати віртуальною машиною вручну. Minikube використовує ці компоненти через драйвер `kvm2`, щоб запустити вузол Kubernetes у віртуальній машині.

Важливо те, що `kvm2` ізолює вузол Kubernetes у віртуальній машині, а не запускає його як контейнер Docker.

### Середовище виконання контейнерів створює контейнери Podʼа {#the-container-runtime-creates-the-pod-containers}

Усередині вузла Kubernetes `kubelet` потрібне середовище виконання контейнерів для створення Podʼів і керування ними.

Kubernetes взаємодіє із середовищем виконання контейнерів через _Container Runtime Interface_ (CRI).

Наприклад, вузол Minikube може використовувати containerd:

```bash
minikube start --driver=kvm2 --container-runtime=containerd
```

Взаємодія рівнів виглядає так:
{{< figure src="cri-integration-flow.svg" alt="Потік взаємодії через Container Runtime Interface" >}}

Різниця між рівнями важлива, оскільки інтеграція просторів імен користувачів залежить від підтримки середовища виконання контейнерів і середовища виконання OCI, а ці середовища, зрештою, залежать від середовища Linux, у якому вони працюють.

Тож локальне тестування просторів імен користувачів (і навіть їх використання у промисловому середовищі) — це не лише перевірка підтримки цієї можливості самим Kubernetes.

Ви тестуєте такий ланцюжок:

**Kubernetes → kubelet → CRI → середовище виконання контейнерів → середовище виконання OCI → ядро Linux**

Обмеження на будь-якому з відповідних рівнів може вплинути на створення Podʼа з `hostUsers: false`.

## Що відбувається, коли `hostUsers: false` не працює? {#what-happens-when-hostusers-false-fails}

Під час тестування дві конфігурації з драйвером Docker спричинили різні помилки.

Важливо не запамʼятовувати точні повідомлення про помилки: вони залежать від конкретного тестового середовища.

Натомість ці помилки допомагають визначити, **який рівень перешкоджає створенню пісочниці Podʼа**.

### Сценарій збою 1: драйвер Docker із середовищем виконання Docker {#failure-mode-1-docker-driver-with-docker-runtime}

Першою була така конфігурація:

```bash
minikube start --driver=docker --container-runtime=docker
```

У ній вузол Kubernetes є контейнером Docker, а Docker також вибрано середовищем виконання контейнерів усередині цього вузла.

Коли Pod використовує:

```yaml
hostUsers: false
```

`kubelet` просить середовище виконання контейнерів створити пісочницю Podʼа з ізоляцією простору імен користувачів.

У протестованій конфігурації створення пісочниці не вдалося, оскільки середовище виконання не підтримувало запитану конфігурацію просторів імен користувачів.

Спостережувана подія:

```none
Warning  FailedCreatePodSandBox  3s (x3 over 29s)  kubelet
Failed to create pod sandbox: can't set `spec.hostUsers: false`, runtime does not support user namespaces
```

**Що сталося:**

Pod не дійшов до запуску контейнера застосунку. Спершу не вдалося створити пісочницю.

**Чому:**

Вибране середовище виконання контейнерів відхилило запитану конфігурацію просторів імен користувачів.

**Відповідальний рівень:**

Можливості середовища виконання контейнерів, доступні Kubernetes у цій конфігурації.

Це **не** означає, що простори імен користувачів Kubernetes не підтримуються. Це означає, що саме ця конфігурація середовища виконання не могла виконати запит.

### Сценарій збою 2: драйвер Docker із containerd {#failure-mode-2-docker-driver-with-containerd}

У наступному тесті змінили середовище виконання контейнерів:

```bash
minikube start --driver=docker --container-runtime=containerd
```

Вузол Minikube і далі був контейнером Docker, але всередині вузла використовувався containerd.

Цього разу запит пройшов далі. Однак створення пісочниці зрештою завершилося помилкою в середовищі виконання OCI під час операції монтування.

Спостережувана помилка:

```none
Warning  FailedCreatePodSandBox  12s  kubelet
Failed to create pod sandbox: rpc error: code = Unknown desc = failed to start sandbox "...": failed to create containerd task: failed to create shim task: OCI runtime create failed: runc create failed: unable to start container process: error during container init: error mounting "sysfs" to rootfs at "/sys": mount src=sysfs, dst=/sys, ...: operation not permitted
```

**Що сталося:**

containerd прийняв запит, але середовище виконання OCI не змогло ініціалізувати пісочницю.

**Чому:**

Середовище виконання OCI все ще працювало всередині контейнера Docker, у якому розміщувався вузол Minikube. У протестованому середовищі вкладена конфігурація контейнерів обмежила операцію монтування, потрібну під час ініціалізації пісочниці.

**Відповідальний рівень:**

Середовище виконання OCI та можливості ядра, доступні через середовище вузла на основі Docker.

Це показує, чому простої зміни середовища виконання контейнерів може бути недостатньо.

Ви змінили:

**середовище виконання Docker → containerd**

але не змінили:

**вузол Kubernetes на основі Docker → вузол Kubernetes у віртуальній машині**

Середовище виконання все ще працювало всередині контейнера Docker.

## Порівняння конфігурацій {#comparing-the-configurations}

Конфігурації, які було протестовано в цій статті, можна описати так:

| Конфігурація Minikube | Середовище виконання контейнерів | Результат | Збій або поведінка |
| --- | --- | --- | --- |
| `--driver=docker --container-runtime=docker` | Docker | ❌ Збій | Середовище виконання відхилило запитану конфігурацію просторів імен користувачів |
| `--driver=docker --container-runtime=containerd` | containerd | ❌ Збій у протестованому середовищі | `runc` не зміг ініціалізувати пісочницю через помилку монтування `sysfs` |
| `--driver=kvm2 --container-runtime=containerd` | containerd | ✅ Працювало в протестованому середовищі | Вузол Kubernetes працював у віртуальній машині, а не в контейнері Docker |

Отже, важлива зміна в робочій конфігурації — не лише вибір середовища виконання контейнерів.

Це **межа ізоляції навколо вузла Kubernetes**.

## Запуск просторів імен користувачів із драйвером Minikube на основі віртуальної машини {#running-user-namespaces-with-a-vm-backed-minikube-driver}

Драйвер на основі віртуальної машини розміщує вузол Kubernetes у віртуальній машині, а не в контейнері на хості.

Для Linux Minikube надає драйвер `kvm2`, який використовує KVM і libvirt.

Так вузол отримує власне гостьове ядро, а додатковий рівень вкладеності контейнерів, що виникає, коли сам вузол Kubernetes є контейнером Docker, зникає.

### Крок 1. Запустіть кластер Minikube у віртуальній машині {#step-1-start-a-vm-backed-minikube-cluster}

Для цього тесту використайте драйвер `kvm2` із containerd. Так вузол Minikube працюватиме у віртуальній машині, а не в контейнері Docker.

Запустіть Minikube:

```bash
minikube start --driver=kvm2 --container-runtime=containerd --nodes=2 -p userns-dev
```

### Крок 2. Розгорніть Pod із просторами імен користувачів {#step-2-deploy-a-pod-with-user-namespaces-enabled}

Створіть файл `userns-pod.yaml`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: userns-nginx
  namespace: default
spec:
  hostUsers: false
  containers:
  - name: web
    image: busybox:1.36
    command: ["sleep", "infinity"]
    securityContext:
      allowPrivilegeEscalation: false
      capabilities:
        drop:
        - ALL
```

Застосуйте маніфест:

```bash
kubectl apply -f userns-pod.yaml
```

Дочекайтеся, поки Pod перейде в стан `Running`:

```bash
kubectl get pod userns-nginx
```

### Крок 3. Перевірте зіставлення просторів імен користувачів {#step-3-verify-the-user-namespace-mapping}

Перевірити зіставлення UID зсередини контейнера можна так:

```bash
kubectl exec userns-nginx -- cat /proc/self/uid_map
```

Результат матиме приблизно такий вигляд:

```none
0 2144206848      65536
```

Важливе не точне значення UID хоста, наведене вище. Це зіставлення показує, що UID 0 усередині контейнера відповідає іншому, непривілейованому діапазону UID з погляду вузла.

Також можна перевірити процес на вузлі Minikube:

```bash
minikube ssh -p userns-dev --node userns-dev-m02 ps aux | grep sleep
```

Вивід:

```none
1947205632    2128  0.0  0.0   4552  2432 ?        Ss   15:00   0:00 sleep infinity
```

Таблиця процесів вузла підтверджує, що `root` контейнера (UID 0) працює як непривілейований UID 1947205632 на вузлі-віртуальній машині, ізольований від привілеїв `root`.

Це ще один спосіб перевірити, що зіставлення просторів імен користувачів працює.

## Поширена проблема: можливості всередині просторів імен користувачів {#capabilities}

Якщо простір імен користувачів працює, це ще не означає, що кожен застосунок зможе успішно запуститися.

Простори імен користувачів змінюють область дії ідентифікаторів користувачів і можливостей. Під час запуску деякі застосунки виконують такі операції, як зміна власника файлу або перемикання ідентифікатора користувача.

Прикладом можуть бути образи баз даних.

Якщо застосунку потрібні такі можливості, як `CHOWN`, `SETUID`, `SETGID` або `FOWNER`, видалення всіх можливостей може спричинити збій застосунку, навіть якщо простори імен користувачів працюють правильно.

Наприклад:

```yaml
securityContext:
  capabilities:
    add:
      - CHOWN
      - SETUID
      - SETGID
      - FOWNER
    drop:
      - ALL
```

Потрібні можливості залежать від застосунку.

Тому збій під час запуску застосунку не варто автоматично вважати проблемою просторів імен користувачів. Спершу переконайтеся, що простір імен працює, а потім зʼясуйте вимоги застосунку до можливостей.

## Перелік кроків для усунення несправностей {#troubleshooting-checklist}

Якщо `hostUsers: false` не працює в локальному середовищі Kubernetes, перевіряйте рівні по черзі, а не припускайте, що проблема в самому Kubernetes.

- Перевірте версію Kubernetes і переконайтеся, що в ній доступна підтримка просторів імен користувачів для Podʼів.
- Перевірте драйвер Minikube за допомогою `minikube profile list` або перегляньте конфігурацію, використану для запуску кластера.
- Зʼясуйте, чи працює вузол Kubernetes безпосередньо у віртуальній машині, чи всередині іншого контейнера.
- Перевірте, яке середовище виконання контейнерів використовує вузол Minikube.
- Визначте середовище виконання OCI, яке використовує це середовище, наприклад `runc`.
- Перегляньте події Podʼа й визначте, на якому етапі виникає збій: у середовищі виконання, середовищі OCI чи під час ініціалізації пісочниці.
- Відрізніть помилку можливостей середовища виконання від обмежень простору імен або монтування.
- Якщо використовується драйвер Minikube на основі контейнера, перевірте, чи змінюється результат із драйвером на основі віртуальної машини.
- Після запуску Podʼа перевірте `/proc/self/uid_map`, щоб переконатися, що зіставлення просторів імен користувачів працює.
- Якщо простір імен працює, але застосунок завершується з помилкою, перевірте потрібні йому можливості та поведінку під час запуску.

Мета — визначити, **який рівень не може надати потрібну можливість**, а не вважати кожен збій `hostUsers: false` обмеженням функціональності Kubernetes.

## Висновок {#conclusion}

Podʼи можуть використовувати простір імен користувачів, якщо встановити `hostUsers: false`, але локальне тестування цієї можливості залежить не лише від API Kubernetes і середовища виконання контейнерів.

Важливе також середовище, у якому працює вузол Kubernetes.

Якщо вузол Minikube запущено на основі Docker, середовище виконання контейнерів саме вкладене в інше контейнерне середовище. Це може спричинити обмеження монтування й просторів імен, яких немає, коли вузол працює у віртуальній машині.

Тому конфігурації дають різні результати:

- **Docker і середовище виконання Docker:** обмеження можливостей CRI або середовища виконання.
- **Docker і containerd:** вкладене середовище виконання, а потім обмеження монтування середовищем OCI або ядром.
- **KVM2 і containerd:** вузол Kubernetes у віртуальній машині, де Pod із простором імен користувачів може запуститися.

Для локального тестування драйвер на основі віртуальної машини, наприклад `kvm2`, створює практичне середовище для перевірки `hostUsers: false` без додаткового рівня вкладеності контейнерів, який виникає з драйвером Docker. У документації Minikube наведено відомості і про драйвер `kvm2`, і про явний вибір середовища виконання контейнерів.

Докладніше про простори імен користувачів, вимоги, обмеження та поле `hostUsers` читайте в [документації Kubernetes про простори імен користувачів](/docs/concepts/workloads/pods/user-namespaces/) і [інструкції з використання простору імен користувачів у Podʼі](/docs/tasks/configure-pod-container/user-namespaces/).
