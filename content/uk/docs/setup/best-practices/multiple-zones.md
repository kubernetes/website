<!-- overview -->

Ця сторінка описує запуск Kubernetes у кількох зонах відмов.

<!-- body -->

## Контекст {#background}

Kubernetes створено так, щоб один кластер Kubernetes міг працювати в кількох зонах відмов, зазвичай коли ці зони входять до логічної групи, яку називають _регіоном_. Основні хмарні провайдери визначають регіон як набір зон відмов (їх також називають _зонами доступності_), що надають узгоджений набір можливостей: у межах регіону кожна зона пропонує ті самі API та сервіси.

Типові хмарні архітектури спрямовані на мінімізацію ймовірності того, що відмова в одній зоні також призведе до порушення роботи сервісів в іншій зоні.

## Поведінка панелі управління {#control-plane-behavior}

Усі [компоненти панелі управління](/docs/concepts/architecture/#control-plane-components) підтримують роботу як пул взаємозамінних ресурсів, реплікованих для кожного компонента.

Під час розгортання панелі управління кластера розміщуйте репліки компонентів панелі управління в кількох зонах відмов. Якщо доступність важлива, виберіть щонайменше три зони відмов і реплікуйте кожен окремий компонент панелі управління (API-сервер, планувальник, etcd, менеджер контролерів кластера) щонайменше в трьох зонах відмов. Якщо ви використовуєте cloud controller manager, його також слід реплікувати в усіх вибраних зонах відмов.

{{< note >}}
Kubernetes не забезпечує міжзонної стійкості для точок доступу API-сервера. Для підвищення доступності API-сервера кластера можна використовувати різні методи, зокрема DNS round-robin, записи SRV або стороннє рішення для балансування навантаження з перевіркою справності.
{{< /note >}}

## Поведінка вузла {#node-behavior}

Kubernetes автоматично розподіляє Podʼи ресурсів робочих навантажень (як-от {{< glossary_tooltip text="Deployment" term_id="deployment" >}} чи {{< glossary_tooltip text="StatefulSet" term_id="statefulset" >}}) між різними вузлами кластера. Такий розподіл допомагає зменшити вплив відмов.

Під час запуску вузлів kubelet на кожному вузлі автоматично додає {{< glossary_tooltip text="мітки" term_id="label" >}} до обʼєкта Node, який представляє цей kubelet в API Kubernetes. Ці мітки можуть містити [інформацію про зону](/docs/reference/labels-annotations-taints/#topologykubernetesiozone).

Якщо ваш кластер охоплює кілька зон або регіонів, ви можете використовувати мітки вузлів разом з [обмеженнями топології розміщення Podʼів](/docs/concepts/scheduling-eviction/topology-spread-constraints/), щоб керувати тим, як Podʼи розподіляються у вашому кластері між доменами відмов: регіонами, зонами і навіть конкретними вузлами. Ці підказки дають змогу {{< glossary_tooltip text="планувальнику" term_id="kube-scheduler" >}} розміщувати Podʼи для кращої очікуваної доступності, зменшуючи ризик того, що корельована відмова вплине на все ваше робоче навантаження.

Наприклад, ви можете задати обмеження, щоб 3 репліки StatefulSet працювали в різних зонах, коли це можливо. Це можна визначити декларативно, не вказуючи явно, які зони доступності використовуються для кожного робочого навантаження.

### Розподіл вузлів по зонах {#distributing-nodes-across-zones}

Ядро Kubernetes не створює вузли за вас; вам потрібно зробити це самостійно або використати інструмент, як-от [Cluster API](https://cluster-api.sigs.k8s.io/), щоб керувати вузлами від вашого імені.

За допомогою інструментів, як-от Cluster API, ви можете визначити набори машин, що працюватимуть як робочі вузли вашого кластера в кількох доменах відмов, і правила для автоматичного відновлення кластера в разі порушення обслуговування всієї зони.

## Ручне призначення зон для Podʼів {#manual-zone-assignment-for-pods}

Ви можете застосовувати [обмеження селектора вузла](/docs/concepts/scheduling-eviction/assign-pod-node/#nodeselector) до Podʼів, які створюєте, а також до шаблонів Podʼів у ресурсах робочих навантажень, як-от Deployment, StatefulSet або Job.

## Доступ до сховища для зон {#storage-access-for-zones}

Коли створюються постійні томи, Kubernetes автоматично додає мітки зони до всіх PersistentVolume, повʼязаних з конкретною зоною. Потім {{< glossary_tooltip text="планувальник" term_id="kube-scheduler" >}} за допомогою свого предиката `NoVolumeZoneConflict` гарантує, що Podʼи, які заявляють (claim) певний PersistentVolume, розміщуються лише в тій самій зоні, що й цей том.

Зауважте, що спосіб додавання міток зон може залежати від вашого хмарного провайдера та provisioner сховища, який ви використовуєте. Завжди звертайтеся до документації вашого середовища, щоб забезпечити правильну конфігурацію.

Ви можете вказати {{< glossary_tooltip text="StorageClass" term_id="storage-class" >}} для PersistentVolumeClaim, який визначає домени відмов (зони), що може використовувати сховище цього класу. Щоб дізнатися, як налаштувати StorageClass, що враховує домени відмов або зони, див. [Дозволені топології](/docs/concepts/storage/storage-classes/#allowed-topologies).

## Мережа {#networking}

Сам по собі Kubernetes не має мережі з урахуванням зон. Ви можете використовувати [мережевий втулок](/docs/concepts/extend-kubernetes/compute-storage-net/network-plugins/) для налаштування мережі кластера, і це мережеве рішення може мати елементи, специфічні для зон. Наприклад, якщо ваш хмарний провайдер підтримує Service з `type=LoadBalancer`, балансувальник навантаження може надсилати трафік лише до Podʼів, що працюють у тій самій зоні, що й елемент балансувальника, який обробляє певне зʼєднання. Подробиці див. у документації вашого хмарного провайдера.

Для власних розгортань або розгортань на власних серверах (on-premises) діють подібні міркування. Поведінка {{< glossary_tooltip text="Service" term_id="service" >}} та {{< glossary_tooltip text="Ingress" term_id="ingress" >}}, зокрема обробка різних зон відмов, відрізняється залежно від того, як саме налаштовано ваш кластер.

## Відновлення після відмов {#fault-recovery}

Налаштовуючи кластер, вам також може знадобитися подумати, чи зможе ваше налаштування відновити обслуговування, якщо всі зони відмов у регіоні одночасно вийдуть з ладу, і як саме. Наприклад, чи покладаєтеся ви на те, що в зоні є принаймні один вузол, здатний запускати Podʼи? Переконайтеся, що будь-які критичні для кластера ремонтні роботи не залежать від наявності принаймні одного справного вузла у вашому кластері. Наприклад: якщо всі вузли несправні, вам може знадобитися запустити ремонтний Job з особливим {{< glossary_tooltip text="toleration" term_id="toleration" >}}, щоб ремонт зміг завершитися настільки, щоб принаймні один вузол повернувся в роботу.

Kubernetes не має готової відповіді на цей виклик; однак це варто враховувати.
