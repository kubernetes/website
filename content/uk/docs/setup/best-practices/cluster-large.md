Кластер — це набір {{< glossary_tooltip text="вузлів" term_id="node" >}} (фізичних або віртуальних машин), на яких працюють агенти Kubernetes і якими керує {{< glossary_tooltip text="панель управління" term_id="control-plane" >}}. Kubernetes {{< param "version" >}} підтримує кластери розміром до 5000 вузлів. Точніше, Kubernetes розроблено для конфігурацій, які відповідають *усім* таким критеріям:

* Не більше 110 Podʼів на вузол
* Не більше 5000 вузлів
* Не більше 150 000 Podʼів загалом
* Не більше 300 000 контейнерів загалом

Ви можете масштабувати свій кластер, додаючи чи видаляючи вузли. Спосіб залежить від того, як ваш кластер розгорнутий.

## Квоти ресурсів хмарних провайдерів {#quota-issues}

Щоб уникнути проблем із квотами хмарного провайдера під час створення кластера з багатьма вузлами, врахуйте таке:

* Запит на збільшення квот для хмарних ресурсів, як-от:
  * Обчислювальні екземпляри
  * CPU
  * Томи сховища
  * Використані IP-адреси
  * Набори правил фільтрації пакетів
  * Кількість балансувальників навантаження
  * Підмережі
  * Потоки логів
* Обмеження дій масштабування кластера, щоб додавати нові вузли партіями з паузою між партіями, оскільки деякі хмарні провайдери обмежують швидкість створення нових екземплярів.

## Компоненти панелі управління {#control-plane-components}

Для великого кластера вам потрібна панель управління з достатніми обчислювальними та іншими ресурсами.

Зазвичай ви запускаєте один чи два екземпляри панелі управління у кожній зоні відмов, спочатку масштабуючи ці екземпляри вертикально, а потім горизонтально після досягнення точки спаду ефективності вертикального масштабування.

Вам слід запускати принаймні один екземпляр у кожній зоні відмов для забезпечення стійкості до відмов. Вузли Kubernetes автоматично не спрямовують трафік до точок доступу панелі управління, що перебувають у тій самій зоні відмов; однак ваш хмарний провайдер може мати власні механізми для цього.

Наприклад, використовуючи керований балансувальник навантаження, ви налаштовуєте його так, щоб трафік, який надходить від kubelet і Podʼів у зоні відмов _A_, спрямовувався лише до хостів панелі управління, які також перебувають у зоні _A_. Якщо єдиний хост або точка доступу панелі управління в зоні відмов _A_ виходить з ладу, увесь трафік панелі управління для вузлів у зоні _A_ тепер надсилається між зонами. Запуск кількох хостів панелі управління в кожній зоні робить такий результат менш імовірним.

### Сховище etcd {#etcd-storage}

Для покращення продуктивності великих кластерів ви можете зберігати обʼєкти Event в окремому виділеному екземплярі etcd.

Під час створення кластера ви можете (за допомогою власних інструментів):

* запускати та налаштовувати додаткові екземпляри etcd
* налаштовувати {{< glossary_tooltip term_id="kube-apiserver" text="API-сервер" >}} на використання його для зберігання подій

Докладніше про налаштування та керування etcd для великого кластера див. [Управління кластерами etcd для Kubernetes](/docs/tasks/administer-cluster/configure-upgrade-etcd/) і [Налаштування високодоступного кластера etcd за допомогою kubeadm](/docs/setup/production-environment/tools/kubeadm/setup-ha-etcd-with-kubeadm/).

## Ресурси надбудов {#addon-resources}

[Обмеження ресурсів](/docs/concepts/configuration/manage-resources-containers/) Kubernetes допомагають мінімізувати вплив витоків памʼяті та інших способів, якими Podʼи й контейнери можуть впливати на інші компоненти. Ці обмеження ресурсів застосовуються до ресурсів {{< glossary_tooltip text="надбудов" term_id="addons" >}} так само, як і до робочих навантажень застосунків.

Наприклад, ви можете встановити обмеження CPU та памʼяті для компонента логування:

```yaml
  ...
  containers:
  - name: fluentd-cloud-logging
    image: fluent/fluentd-kubernetes-daemonset:v1
    resources:
      limits:
        cpu: 100m
        memory: 200Mi
```

Стандартні обмеження надбудов, як правило, базуються на даних, зібраних під час роботи кожної надбудови на невеликих або середніх кластерах Kubernetes. На великих кластерах надбудови часто споживають деяких ресурсів більше, ніж дозволяють їхні стандартні обмеження. Якщо великий кластер розгорнути без налаштування цих значень, надбудови можуть постійно примусово завершуватися, бо раз у раз досягають обмеження памʼяті. Або ж надбудова може працювати, але з поганою продуктивністю через обмеження квантів часу CPU.

Щоб уникнути проблем із ресурсами надбудов кластера під час створення кластера з багатьма вузлами, врахуйте таке:

* Деякі надбудови масштабуються вертикально — є одна репліка надбудови для кластера або для всієї зони відмов. Для таких надбудов збільшуйте запити та обмеження під час масштабування кластера.
* Багато надбудов масштабуються горизонтально — ви додаєте потужність, запускаючи більше Podʼів, — але в дуже великому кластері вам також може знадобитися трохи збільшити обмеження CPU чи памʼяті. [Vertical Pod Autoscaler](https://github.com/kubernetes/autoscaler/tree/master/vertical-pod-autoscaler#readme) може працювати в режимі _recommender_, щоб пропонувати значення для запитів і обмежень.
* Деякі надбудови працюють як одна копія на вузол, керована {{< glossary_tooltip text="DaemonSet" term_id="daemonset" >}}: наприклад, агрегатор логів рівня вузла. Як і у випадку горизонтально масштабованих надбудов, вам також може знадобитися трохи збільшити обмеження CPU чи памʼяті.

## Пріоритетність компонентів, необхідних для кластера {#prioritizing-cluster-essential-components}

Щоб компоненти, необхідні для кластера (як-от CoreDNS, metrics-server та інші критичні надбудови), планувалися раніше за інші робочі навантаження і не витіснялися Podʼами з нижчим пріоритетом, запускайте їх із системним [PriorityClass](/docs/concepts/scheduling-eviction/pod-priority-preemption/), як-от `system-cluster-critical` або `system-node-critical`.
