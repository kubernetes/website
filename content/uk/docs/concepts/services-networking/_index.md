## Мережева модель Kubernetes {#the-kubernetes-network-model}

Мережева модель Kubernetes складається з кількох частин:

* Кожен [Pod](/docs/concepts/workloads/pods/) у кластері отримує власну унікальну в межах кластера IP-адресу.

  * Pod має власний приватний мережевий простір імен, який спільно використовують усі контейнери в цьому Podʼі. Процеси, що працюють у різних контейнерах одного Podʼа, можуть взаємодіяти між собою через `localhost`.

* _Мережа Podʼів_ (також називається мережею кластера) забезпечує взаємодію між Podʼами. Вона гарантує, що (за відсутності навмисної сегментації мережі):

  * Усі Podʼи можуть взаємодіяти з усіма іншими Podʼами, незалежно від того, чи перебувають вони на одному [вузлі](/docs/concepts/architecture/nodes/), чи на різних. Podʼи можуть взаємодіяти безпосередньо, без використання проксі-серверів чи трансляції адрес (NAT).

    У Windows це правило не застосовується до Podʼів із мережею хоста.

  * Агенти на вузлі (такі як системні демони чи kubelet) можуть взаємодіяти з усіма Podʼами на цьому вузлі.

* API [Service](/docs/concepts/services-networking/service/) дозволяє надати стабільну (довговічну) IP-адресу або імʼя хоста для сервісу, реалізованого одним або кількома Podʼами-бекендами, при цьому окремі Podʼи, що складають сервіс, можуть змінюватися з часом.

  * Kubernetes автоматично керує обʼєктами [EndpointSlice](/docs/concepts/services-networking/endpoint-slices/), щоб надавати інформацію про Podʼи, які наразі обслуговують Service.

  * Реалізація проксі сервісів відстежує набір обʼєктів Service та EndpointSlice і програмує площину даних для маршрутизації трафіку сервісу до його бекендів, використовуючи API операційної системи або хмарного провайдера для перехоплення чи переписування пакетів.

* API [Gateway](/docs/concepts/services-networking/gateway/) (або його попередник [Ingress](/docs/concepts/services-networking/ingress/)) дозволяє зробити Services доступними для клієнтів поза кластером.

  * Простіший, але менш гнучкий механізм вхідного трафіку кластера доступний через [`type: LoadBalancer`](/docs/concepts/services-networking/service/#loadbalancer) в API Service, якщо ви використовуєте підтримуваного {{< glossary_tooltip term_id="cloud-provider" text="хмарного провайдера" >}}.

* [NetworkPolicy](/docs/concepts/services-networking/network-policies) — це вбудований API Kubernetes, який дозволяє контролювати трафік між Podʼами або між Podʼами та зовнішнім світом.

У старіших контейнерних системах не було автоматичного звʼязку між контейнерами на різних хостах, тому часто доводилося явно створювати посилання між контейнерами або зіставляти порти контейнерів із портами хоста, щоб контейнери на інших хостах могли до них звертатися. У Kubernetes це не потрібно: модель Kubernetes передбачає, що Podʼи можна розглядати подібно до віртуальних машин або фізичних хостів з погляду виділення портів, іменування, виявлення сервісів, балансування навантаження, налаштування застосунків та міграції.

Лише кілька частин цієї моделі реалізовані безпосередньо в Kubernetes. Для решти Kubernetes визначає API, але відповідну функціональність надають зовнішні компоненти, деякі з яких є необовʼязковими:

* Налаштування мережевого простору імен Podʼа виконує системне програмне забезпечення, яке реалізує [Container Runtime Interface](/docs/concepts/containers/cri/).

* Мережею Podʼів керує [реалізація мережі Podʼів](/docs/concepts/cluster-administration/addons/#networking-and-network-policy). У Linux більшість середовищ виконання контейнерів використовують {{< glossary_tooltip text="Container Networking Interface (CNI)" term_id="cni" >}}, щоб взаємодіяти з реалізацією мережі Podʼів, тому ці реалізації часто називають _втулками CNI_.

* Kubernetes надає стандартну реалізацію проксіювання сервісів, яка називається {{< glossary_tooltip term_id="kube-proxy" >}}, але деякі реалізації мережі Podʼів використовують власний проксі сервісів, тісніше інтегрований з рештою реалізації.

* NetworkPolicy зазвичай також реалізується реалізацією мережі Podʼів. (Деякі простіші реалізації мережі Podʼів не реалізують NetworkPolicy, або адміністратор може налаштувати мережу Podʼів без підтримки NetworkPolicy. У таких випадках API буде присутній, але не матиме жодного ефекту.)

* Існує багато [реалізацій Gateway API](https://gateway-api.sigs.k8s.io/implementations/): деякі специфічні для певних хмарних середовищ, деякі більше орієнтовані на середовища bare metal, а інші є більш універсальними.

## {{% heading "whatsnext" %}} {#whats-next}

Навчальний матеріал [Підключення застосунків за допомогою Services](/docs/tutorials/services/connect-applications-service/) дає змогу дізнатися про Services та мережу Kubernetes на практичному прикладі.

Стаття [Мережа кластера](/docs/concepts/cluster-administration/networking/) пояснює, як налаштувати мережу для вашого кластера, а також надає огляд задіяних технологій.

Щоб дізнатися про конкретні концепції мережі, дивіться:

* [Service](/docs/concepts/services-networking/service/) — надання доступу до застосунку через одну зовнішню точку доступу
* [Ingress](/docs/concepts/services-networking/ingress/) — маршрутизація HTTP/HTTPS з урахуванням протоколу за допомогою URI, імен хостів та шляхів
* [Gateway API](/docs/concepts/services-networking/gateway/) — динамічне надання інфраструктури та розширена маршрутизація трафіку
* [Network Policies](/docs/concepts/services-networking/network-policies/) — контроль потоку трафіку на рівні IP-адрес або портів (рівень OSI 3 або 4)
* [DNS для Services та Podʼів](/docs/concepts/services-networking/dns-pod-service/) — виявлення сервісів у вашому кластері за допомогою DNS
