Вузли мають локальне тимчасове сховище, яке підтримується локально підключеними пристроями з можливістю запису або, інколи, оперативною памʼяттю. «Тимчасове» означає, що немає довгострокової гарантії щодо довговічності.

Podʼи використовують тимчасове локальне сховище як робочий простір, для кешування та для логів. kubelet може надавати Podʼам робочий простір, використовуючи локальне тимчасове сховище для монтування {{< glossary_tooltip term_id="volume" text="томів" >}} [`emptyDir`](/docs/concepts/storage/volumes/#emptydir) у контейнери.

kubelet також використовує цей тип сховища для зберігання [логів контейнерів на рівні вузла](/docs/concepts/cluster-administration/logging/#logging-at-the-node-level), образів контейнерів і шарів запущених контейнерів, доступних для запису.

{{< caution >}}
Якщо вузол виходить з ладу, дані в його тимчасовому сховищі можуть бути втрачені. Ваші застосунки не можуть очікувати жодних SLA щодо продуктивності (наприклад, дискових IOPS) від локального тимчасового сховища.
{{< /caution >}}

{{< note >}}
Щоб квота ресурсів працювала для ephemeral-storage, потрібно виконати дві дії:

* Адміністратор встановлює квоту ресурсів для ephemeral-storage в просторі імен.
* Користувач повинен вказати обмеження для ресурсу ephemeral-storage у специфікації Podʼа.

Якщо користувач не вказав обмеження ресурсу ephemeral-storage у специфікації Podʼа, квота ресурсів не застосовується до ephemeral-storage.

{{< /note >}}

Kubernetes дозволяє відстежувати, резервувати та обмежувати обсяг тимчасового локального сховища, яке може використовувати Pod.

## Конфігурації для локального тимчасового сховища {#configurations}

Kubernetes підтримує такі способи налаштування локального тимчасового сховища на вузлі:

{{< tabs name="local_storage_configurations" >}}
{{% tab name="Одна файлова система" %}}
У цій конфігурації ви розміщуєте всі різні типи тимчасових локальних даних (томи `emptyDir`, шари, доступні для запису, образи контейнерів, логи) в одній файловій системі.

kubelet також записує [логи контейнерів на рівні вузла](/docs/concepts/cluster-administration/logging/#logging-at-the-node-level) і обробляє їх аналогічно тимчасовому локальному сховищу.

kubelet записує логи у файли всередині налаштованої теки логів (стандартно `/var/log`) і має базову теку для інших локально збережених даних (стандартно `/var/lib/kubelet`).

Зазвичай і `/var/lib/kubelet`, і `/var/log` розташовані в кореневій файловій системі, і kubelet розроблено з урахуванням такого розташування.

Ваш вузол може мати скільки завгодно інших файлових систем, які не використовуються для Kubernetes.
{{% /tab %}}
{{% tab name="Файлова система середовища виконання" %}}
Ви використовуєте на вузлі одну файлову систему для тимчасових даних запущених Podʼів, таких як логи та томи `emptyDir`. Цю файлову систему також можна використовувати для інших даних, наприклад, для системних логів, не повʼязаних із Kubernetes; вона може бути навіть кореневою файловою системою.

kubelet також записує [логи контейнерів на рівні вузла](/docs/concepts/cluster-administration/logging/#logging-at-the-node-level) у першу файлову систему і обробляє їх аналогічно тимчасовому локальному сховищу.

Ви також використовуєте окрему файлову систему на іншому логічному пристрої зберігання. У цій конфігурації середовище виконання контейнерів зберігає і шари образів контейнерів, і шари, доступні для запису, у цій другій файловій системі. Налаштуйте це місце зберігання в середовищі виконання контейнерів, а не в kubelet.

Перша файлова система не містить жодних шарів образів або шарів, доступних для запису.

Ваш вузол може мати скільки завгодно інших файлових систем, які не використовуються для Kubernetes.
{{% /tab %}}
{{% tab name="Окрема файлова система для образів" %}}
У цій конфігурації шари образів контейнерів розташовані в окремій файловій системі, а шари контейнерів, доступні для запису, — у тій самій файловій системі, що й тимчасові дані kubelet, такі як логи та томи `emptyDir`.

Ця конфігурація вимагає підтримки сигналів виселення `containerfs`. Докладніше про функціональну можливість і середовища виконання контейнерів, які підтримують цю конфігурацію, дивіться у [виселенні внаслідок тиску на вузол](/docs/concepts/scheduling-eviction/node-pressure-eviction/#filesystem-signals).
{{% /tab %}}
{{< /tabs >}}

На сторінці [Виселення внаслідок тиску на вузол](/docs/concepts/scheduling-eviction/node-pressure-eviction/#filesystem-signals) ці файлові системи, за якими ведеться спостереження, позначаються як `nodefs`, `imagefs` та `containerfs`. Ці назви не завжди означають окремі точки монтування.

kubelet може вимірювати використання локального сховища, якщо ви налаштовуєте вузол за однією з підтримуваних конфігурацій локального тимчасового сховища.

Якщо у вас інша конфігурація, kubelet не застосовує обмеження ресурсів для тимчасового локального сховища.

{{< note >}}
kubelet відстежує томи `emptyDir` типу `tmpfs` як використання памʼяті контейнера, а не як локальне тимчасове сховище.
{{< /note >}}

{{< note >}}
kubelet може відстежувати тимчасове сховище лише у файлових системах, які він спостерігає через підтримувані схеми розташування. Якщо ви монтуєте додаткові файлові системи за такими шляхами, як `/var/lib/kubelet`, `/var/log` або тека сховища середовища виконання контейнерів, поза цими схемами, kubelet може неправильно повідомляти про тимчасове сховище.
{{< /note >}}

## Встановлення запитів та обмежень для локального тимчасового сховища {#requests-limits}

Ви можете вказати `ephemeral-storage` для керування локальним тимчасовим сховищем. Кожен контейнер Podʼа може вказати одне або обидва з такого:

* `spec.containers[].resources.limits.ephemeral-storage`
* `spec.containers[].resources.requests.ephemeral-storage`

Обмеження та запити для `ephemeral-storage` вимірюються в байтах. Ви можете виразити обсяг сховища як просте ціле число або як число з фіксованою комою, використовуючи один із таких суфіксів: E, P, T, G, M, k. Ви також можете використовувати еквіваленти степеня двійки: Ei, Pi, Ti, Gi, Mi, Ki. Наприклад, усі наведені нижче величини мають приблизно однакове значення:

- `128974848`
- `129e6`
- `129M`
- `123Mi`

Зверніть увагу на регістр суфіксів. Якщо ви запитуєте `400m` тимчасового сховища, це запит на 0,4 байта. Той, хто це ввів, мабуть, мав на увазі 400 мебібайтів (`400Mi`) або 400 мегабайтів (`400M`).

У наведеному нижче прикладі Pod має два контейнери. Кожен контейнер має запит на 2GiB локального тимчасового сховища. Кожен контейнер має обмеження в 4GiB локального тимчасового сховища. Отже, Pod має запит на 4GiB локального тимчасового сховища та обмеження у 8GiB локального тимчасового сховища. 500Mi цього обмеження може використати том `emptyDir`.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: frontend
spec:
  containers:
  - name: app
    image: images.my-company.example/app:v4
    resources:
      requests:
        ephemeral-storage: "2Gi"
      limits:
        ephemeral-storage: "4Gi"
    volumeMounts:
    - name: ephemeral
      mountPath: "/tmp"
  - name: log-aggregator
    image: images.my-company.example/log-aggregator:v6
    resources:
      requests:
        ephemeral-storage: "2Gi"
      limits:
        ephemeral-storage: "4Gi"
    volumeMounts:
    - name: ephemeral
      mountPath: "/tmp"
  volumes:
    - name: ephemeral
      emptyDir:
        sizeLimit: 500Mi
```

## Як плануються Podʼи із запитами ephemeral-storage {#how-pods-with-ephemeral-storage-requests-are-scheduled}

Коли ви створюєте Pod, планувальник Kubernetes вибирає вузол, на якому працюватиме Pod. Кожен вузол має максимальний обсяг локального тимчасового сховища, який він може надати для Podʼів. Докладнішу інформацію дивіться в розділі [Node Allocatable](/docs/tasks/administer-cluster/reserve-compute-resources/#node-allocatable).

Планувальник гарантує, що сума запитів на ресурси запланованих контейнерів буде меншою за місткість вузла.

## Керування споживанням тимчасового сховища {#resource-emphemeralstorage-consumption}

Якщо kubelet керує локальним тимчасовим сховищем як ресурсом, то kubelet вимірює використання сховища в:

- томах `emptyDir`, за винятком томів _tmpfs_ `emptyDir`
- теках, що містять логи на рівні вузла
- шарах контейнерів, доступних для запису

Якщо Pod використовує більше тимчасового сховища, ніж ви дозволяєте, kubelet встановлює сигнал виселення, який запускає виселення Podʼа.

Для ізоляції на рівні контейнера, якщо використання шару контейнера, доступного для запису, та логів перевищує його обмеження сховища, kubelet позначає Pod для виселення.

Для ізоляції на рівні Podʼа kubelet обчислює загальне обмеження сховища Podʼа, підсумовуючи обмеження контейнерів цього Podʼа. У цьому випадку, якщо сума використання локального тимчасового сховища всіма контейнерами, а також томами `emptyDir` Podʼа перевищує загальне обмеження сховища Podʼа, kubelet також позначає Pod для виселення.

{{< caution >}}
Якщо kubelet не вимірює локальне тимчасове сховище, то Pod, який перевищує своє обмеження локального сховища, не буде виселений за порушення обмежень ресурсів локального сховища.

Однак, якщо місця у файловій системі для шарів контейнерів, доступних для запису, логів на рівні вузла або томів `emptyDir` стає мало, вузол позначає себе {{< glossary_tooltip text="taint" term_id="taint" >}} про нестачу локального сховища, і цей taint запускає виселення всіх Podʼів, які спеціально не толерують цей taint.

Дивіться підтримувані [конфігурації](#configurations) для тимчасового локального сховища.
{{< /caution >}}

kubelet підтримує різні способи вимірювання використання сховища Podʼа:

{{< tabs name="resource-emphemeralstorage-measurement" >}}

{{% tab name="Періодичне сканування" %}}

kubelet виконує регулярні заплановані перевірки, які сканують кожен том `emptyDir`, теку логів контейнера та шар контейнера, доступний для запису.

Сканування вимірює, скільки місця використовується.

{{< note >}}
У цьому режимі kubelet не відстежує відкриті дескриптори видалених файлів.

Якщо ви (або контейнер) створюєте файл у томі `emptyDir`, щось потім відкриває цей файл, а ви видаляєте файл, поки він ще відкритий, то inode видаленого файлу залишається, доки ви не закриєте цей файл, але kubelet не вважає це місце використаним.

{{< /note >}}

{{% tab name="Квота проєкту файлової системи" %}}

Квоти проєктів — це можливість на рівні операційної системи для керування використанням сховища у файлових системах. У Kubernetes ви можете ввімкнути квоти проєктів для моніторингу використання сховища. Переконайтеся, що файлова система, на якій розміщено томи `emptyDir` на вузлі, підтримує квоти проєктів. Наприклад, XFS та ext4fs пропонують квоти проєктів.

{{< note >}}
Квоти проєктів дозволяють моніторити використання сховища; вони не застосовують обмеження.
{{< /note >}}

Kubernetes використовує ідентифікатори проєктів, починаючи з `1048576`. Використовувані ідентифікатори зареєстровані в `/etc/projects` та `/etc/projid`. Якщо ідентифікатори проєктів у цьому діапазоні використовуються в системі для інших цілей, їх необхідно зареєструвати в `/etc/projects` та `/etc/projid`, щоб Kubernetes не використовував їх.

Квоти є швидшими та точнішими, ніж сканування тек. Коли тека призначається проєкту, всі файли, створені в цій теці, створюються в цьому проєкті, і ядро має лише відстежувати, скільки блоків використовується файлами в цьому проєкті. Якщо файл створено та видалено, але він має відкритий дескриптор файлу, він продовжує споживати простір. Відстеження квот точно фіксує цей простір, тоді як сканування тек пропускає простір, який використовують видалені файли.

Щоб використовувати квоти для відстеження використання ресурсів Podʼом, Pod повинен бути в просторі імен користувача. У просторах імен користувачів ядро обмежує зміни projectID у файловій системі, забезпечуючи надійність метрик сховища, обчислених за допомогою квот.

Якщо ви хочете використовувати квоти проєктів, вам слід:

* Увімкнути функціональну можливість [`LocalStorageCapacityIsolationFSQuotaMonitoring=true`](/docs/reference/command-line-tools-reference/feature-gates/#LocalStorageCapacityIsolationFSQuotaMonitoring) за допомогою поля `featureGates` у [конфігурації kubelet](/docs/reference/config-api/kubelet-config.v1beta1/).

* Переконатися, що функціональну можливість [`UserNamespacesSupport`](/docs/reference/command-line-tools-reference/feature-gates/#UserNamespacesSupport) увімкнено, а ядро, реалізація CRI та середовище виконання OCI підтримують простори імен користувачів.

* Переконатися, що в кореневій файловій системі (або необовʼязковій файловій системі середовища виконання) увімкнено квоти проєктів. Усі файлові системи XFS підтримують квоти проєктів. Для файлових систем ext4 потрібно ввімкнути можливість відстеження квот проєктів, поки файлова система не змонтована.

  ```bash
  # For ext4, with /dev/block-device not mounted
  sudo tune2fs -O project -Q prjquota /dev/block-device
  ```

* Переконатися, що коренева файлова система (або необовʼязкова файлова система середовища виконання) змонтована з увімкненими квотами проєктів. Для XFS і ext4fs параметр монтування називається `prjquota`.

Якщо ви не хочете використовувати квоти проєктів, вам слід:

* Вимкнути функціональну можливість [`LocalStorageCapacityIsolationFSQuotaMonitoring`](/docs/reference/command-line-tools-reference/feature-gates/#LocalStorageCapacityIsolationFSQuotaMonitoring) за допомогою поля `featureGates` у [конфігурації kubelet](/docs/reference/config-api/kubelet-config.v1beta1/).
