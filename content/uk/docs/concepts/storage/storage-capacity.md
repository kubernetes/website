Місткість сховища обмежена і може відрізнятися залежно від вузла, на якому працює Pod: мережеве сховище може бути доступним не всім вузлам, а сховище може бути локальним для вузла від самого початку.

{{< feature-state for_k8s_version="v1.24" state="stable" >}}

На цій сторінці описано, як Kubernetes відстежує місткість сховища та як планувальник використовує цю інформацію, щоб [планувати Podʼи](/docs/concepts/scheduling-eviction/) на вузли, які мають доступ до достатньої місткості сховища для томів, яких ще бракує. Без відстеження місткості сховища планувальник може вибрати вузол, який не має достатньо місткості для надання тому, і знадобиться кілька повторних спроб планування.

## {{% heading "prerequisites" %}} {#before-you-begin}

Kubernetes v{{< skew currentVersion >}} містить підтримку API на рівні кластера для відстеження місткості сховища. Щоб скористатися нею, ви також повинні використовувати драйвер CSI, який підтримує відстеження місткості. Зверніться до документації драйверів CSI, які ви використовуєте, щоб дізнатися, чи доступна ця підтримка і, якщо так, як її використовувати. Якщо ви не використовуєте Kubernetes v{{< skew currentVersion >}}, перегляньте документацію для своєї версії Kubernetes.

## API

Для цієї можливості існує два розширення API:

- Обʼєкти [CSIStorageCapacity](/docs/reference/kubernetes-api/config-and-storage-resources/csi-storage-capacity-v1/): їх створює драйвер CSI у просторі імен, де його встановлено. Кожен обʼєкт містить інформацію про місткість для одного класу сховища і визначає, які вузли мають доступ до цього сховища.
- [Поле `CSIDriverSpec.StorageCapacity`](/docs/reference/kubernetes-api/config-and-storage-resources/csi-driver-v1/#CSIDriverSpec): якщо встановлено значення `true`, планувальник Kubernetes враховуватиме місткість сховища для томів, які використовують драйвер CSI.

## Планування {#scheduling}

Планувальник Kubernetes використовує інформацію про місткість сховища, якщо:

- Pod використовує том, який ще не створено,
- цей том використовує {{< glossary_tooltip text="StorageClass" term_id="storage-class" >}}, який посилається на драйвер CSI та використовує [режим привʼязки тому](/docs/concepts/storage/storage-classes/#volume-binding-mode) `WaitForFirstConsumer`, і
- обʼєкт `CSIDriver` для цього драйвера має `StorageCapacity` зі значенням true.

У цьому випадку планувальник розглядає для Podʼа лише ті вузли, яким доступно достатньо сховища. Ця перевірка дуже спрощена і лише порівнює розмір тому з місткістю, вказаною в обʼєктах `CSIStorageCapacity` з топологією, що включає цей вузол.

Для томів із режимом привʼязки `Immediate` драйвер сховища вирішує, де створити том, незалежно від Podʼів, які використовуватимуть цей том. Потім планувальник планує Podʼи на вузли, де том доступний після його створення.

Для [ефемерних томів CSI](/docs/concepts/storage/ephemeral-volumes/#csi-ephemeral-volumes) планування завжди відбувається без урахування місткості сховища. Це ґрунтується на припущенні, що цей тип тому використовують лише спеціальні драйвери CSI, які є локальними для вузла й не потребують там значних ресурсів.

## Перепланування {#rescheduling}

Коли вузол вибрано для Podʼа з томами `WaitForFirstConsumer`, це рішення все ще є попереднім. Наступним кроком драйверу сховища CSI надсилається запит створити том із підказкою, що том має бути доступний на вибраному вузлі.

Оскільки Kubernetes міг вибрати вузол на підставі застарілої інформації про місткість, може статися, що том не вдасться створити. Тоді вибір вузла скидається, і планувальник Kubernetes знову намагається знайти вузол для Podʼа.

## Обмеження {#limitations}

Відстеження місткості сховища збільшує ймовірність того, що планування спрацює з першої спроби, але не може цього гарантувати, оскільки планувальник має приймати рішення на підставі потенційно застарілої інформації. Зазвичай збої планування обробляє той самий механізм повторних спроб, що й для планування без інформації про місткість сховища.

Одна із ситуацій, коли планування може остаточно зазнати невдачі, — коли Pod використовує кілька томів: один том уже може бути створений у сегменті топології, де потім бракує місткості для іншого тому. Щоб це виправити, потрібне ручне втручання, наприклад, збільшення місткості або видалення вже створеного тому.
