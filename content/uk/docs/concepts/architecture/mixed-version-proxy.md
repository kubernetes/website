У Kubernetes {{< skew currentVersion >}} включено бета-функцію, яка дозволяє {{< glossary_tooltip text="API-серверу" term_id="kube-apiserver" >}} проксіювати запити ресурсів до інших _рівноправних_ API-серверів. Це також дозволяє клієнтам отримати цілісне уявлення про ресурси, що обслуговуються в усьому кластері, за допомогою виявлення. Це корисно, коли існують кілька API-серверів, що працюють на різних версіях Kubernetes в одному кластері (наприклад, під час тривалого впровадження нового релізу Kubernetes).

Це дозволяє адміністраторам кластерів налаштовувати високодоступні кластери, які можна оновлювати безпечніше:

1. гарантуючи, що контролери, які покладаються на виявлення для показу повного списку ресурсів для важливих завдань, завжди отримують повний огляд усіх ресурсів. Ми називаємо це повним виявленням у масштабі кластера — _Peer-aggregated discovery_.
1. направляючи запити на ресурси (зроблені під час оновлення) на відповідний kube-apiserver. Це проксіювання запобігає появі у користувачів несподіваних помилок 404 Not Found, спричинених процесом оновлення. Цей механізм називається _Mixed Version Proxy_.

## Активація Peer-aggregated Discovery та Mixed Version Proxy {#enabling-peer-aggregated-discovery-and-mixed-version-proxy}

Переконайтеся, що функціональну можливість [`UnknownVersionInteroperabilityProxy`](/docs/reference/command-line-tools-reference/feature-gates/#UnknownVersionInteroperabilityProxy) увімкнено, коли ви запускаєте {{< glossary_tooltip text="API-сервер" term_id="kube-apiserver" >}}:

```shell
kube-apiserver \
--feature-gates=UnknownVersionInteroperabilityProxy=true \
# обовʼязкові аргументи командного рядка для цієї функції
--peer-ca-file=<шлях до сертифіката CA kube-apiserver>
--proxy-client-cert-file=<шлях до сертифіката агрегатора проксі>,
--proxy-client-key-file=<шлях до ключа агрегатора проксі>,
--requestheader-client-ca-file=<шлях до сертифіката CA агрегатора>,
# requestheader-allowed-names може бути встановлено як порожнє значення, щоб дозволити будь-яке Common Name
--requestheader-allowed-names=<дійсні значення Common Name для перевірки сертифіката клієнта проксі>,

# необовʼязкові прапорці для цієї функції
--peer-advertise-ip=`IP цього kube-apiserver, який повинні використовувати рівноправні сервери для проксіювання запитів`
--peer-advertise-port=`порт цього kube-apiserver, який повинні використовувати рівноправні сервери для проксіювання запитів`

# …і інші прапорці як зазвичай
```

### Транспорт та автентифікація проксі між API-серверами {#transport-and-authn}

* Вихідний kube-apiserver повторно використовує
  [наявні прапорці автентифікації клієнта API-сервера](/docs/tasks/extend-kubernetes/configure-aggregation-layer/#kubernetes-apiserver-client-authentication) `--proxy-client-cert-file` та `--proxy-client-key-file` для представлення своєї ідентичності, яку перевіряє рівноправний сервер (цільовий kube-apiserver). Цільовий API-сервер перевіряє це підключення на основі конфігурації, яку ви вказуєте за допомогою аргументу командного рядка `--requestheader-client-ca-file`.

* Для автентифікації сертифікатів цільового сервера вам слід налаштувати пакет сертифікатів центру сертифікації, вказавши аргумент командного рядка `--peer-ca-file` **вихідному** API-серверу.

### Налаштування для зʼєднання з рівноправним API-сервером {#configuring-for-peer-api-server-connectivity}

Для встановлення мережевого розташування kube-apiserver, яке рівноправні сервери будуть використовувати для проксіювання запитів, використовуйте аргументи командного рядка `--peer-advertise-ip` та `--peer-advertise-port` для kube-apiserver або вказуйте ці поля в конфігураційному файлі API-сервера. Якщо ці прапорці не вказані, рівноправні сервери будуть використовувати значення з аргументів командного рядка `--advertise-address` або `--bind-address` для kube-apiserver. Якщо ці прапорці теж не встановлені, використовується типовий інтерфейс хоста.

## Peer-aggregated discovery

Коли ви вмикаєте цю функцію, запити на виявлення автоматично вмикаються для надання комплексного документа виявлення (з переліком усіх ресурсів, що обслуговуються будь-яким apiserver у кластері) стандартно.

Якщо ви хочете запросити документ non peer-aggregated discovery, ви можете вказати це, додавши до запиту на виявлення такий заголовок Accept:

```none
application/json;g=apidiscovery.k8s.io;v=v2;as=APIGroupDiscoveryList;profile=nopeer
```

{{< note >}}
Peer-aggregated discovery підтримується тільки для запитів [Aggregated Discovery](/docs/concepts/overview/kubernetes-api/#aggregated-discovery) до точки доступу `/apis`, а не для запитів [Unaggregated (Legacy) Discovery](/docs/concepts/overview/kubernetes-api/#unaggregated-discovery).
{{< /note >}}

## Проксіювання змішаних версій {#mixed-version-proxying}

Коли ви вмикаєте проксіювання змішаних версій, [шар агрегації](/docs/concepts/extend-kubernetes/api-extension/apiserver-aggregation/) завантажує спеціальний фільтр, який виконує такі дії:

* Коли запит ресурсу надходить до API-сервера, який не може обслуговувати цей API (чи то тому, що його версія старіша за появу цього API, чи тому, що API вимкнено на API-сервері), API-сервер намагається надіслати запит до рівноправного API-сервера, який може обслуговувати затребуваний API. Це відбувається шляхом ідентифікації груп API / версій / ресурсів, які локальний сервер не розпізнає, і спроби проксіювати ці запити до рівноправного API-сервера, який може обробити запит.
* Якщо рівноправний API-сервер не відповідає, то _вихідний_ API-сервер відповідає помилкою 503 ("Service Unavailable").

### Як це працює під капотом {#how-it-works-under-the-hood}

Коли API-сервер отримує запит ресурсу, він спочатку перевіряє, які API-сервери можуть обслуговувати затребуваний ресурс. Ця перевірка відбувається за допомогою документа non peer-aggregated discovery.

* Якщо ресурс є в документі non peer-aggregated discovery, отриманому від API-сервера, що отримав запит (наприклад, `GET /api/v1/pods/some-pod`), запит обробляється локально.

* Якщо ресурс у запиті (наприклад, `GET /apis/resource.k8s.io/v1beta1/resourceclaims`) не знайдено в документі non peer-aggregated discovery, отриманому з API-сервера, який намагається обробити запит (_API-сервер обробки_), ймовірно, через те, що API `resource.k8s.io/v1beta1` був введений в новій версії Kubernetes, а _API-сервер обробки_ працює на старій версії, яка його не підтримує, тоді _API-сервер обробки_ знаходить рівноправні API-сервери, які обслуговують відповідну групу API / версію / ресурс (у цьому випадку `resource.k8s.io/v1beta1/resourceclaims`) перевіряючи документи non peer-aggregated discovery усіх рівноправних API-серверів. Потім _API-сервер обробки_ проксіює запит до одного з відповідних рівноправних kube-apiserver, які знають про запитуваний ресурс.

* Якщо для цієї групи API / версії / ресурсу немає відомого рівноправного сервера, API-сервер обробки передає запит до власного ланцюжка обробників, який повинен зрештою повернути відповідь 404 ("Not Found").

* Якщо API-сервер обробки визначив і вибрав рівноправний API-сервер, але той не відповідає (через проблеми з підключенням до мережі або стан гонитви між отриманням запиту та реєстрацією контролером інформації про рівноправний сервер у панелі управління), API-сервер обробки відповідає помилкою 503 ("Service Unavailable").
