<!-- overview -->

Для підтримки робочих навантажень, критичних до затримки та з високою пропускною здатністю, Kubernetes пропонує набір менеджерів ресурсів. Ці менеджери призначені для координації та оптимізації вирівнювання ресурсів вузла для Podʼів, налаштованих із конкретними вимогами до ресурсів CPU, пристроїв і памʼяті (hugepages).

<!-- body -->

## Менеджер топології {#topology-manager}

{{< feature-state feature_gate_name="TopologyManager" >}}

*Менеджер топології* — це компонент kubelet, який координує набір компонентів, відповідальних за ці оптимізації. Щоб дізнатися більше, прочитайте [Керування політиками топології на вузлі](/docs/tasks/administer-cluster/topology-manager/).

## Менеджер CPU {#cpu-manager}

{{< feature-state feature_gate_name="CPUManager" >}}

*Менеджер CPU* — це компонент kubelet, який забезпечує ексклюзивне виділення ресурсів CPU. Для прийняття рішень щодо призначення ресурсів він консультується з менеджером топології. Щоб дізнатися більше, прочитайте [Налаштування політик керування CPU на вузлі](/docs/tasks/administer-cluster/cpu-management-policies/).

### Політики призначення CPU Podʼам {#policies-for-assigning-cpus-to-pods}

Після привʼязки Podʼа до вузла kubelet на цьому вузлі може потребувати або мультиплексування наявного апаратного забезпечення (наприклад, спільного використання CPU між кількома Podʼами), або виділення апаратного забезпечення шляхом резервування певних ресурсів (наприклад, виділення одного або кількох CPU для виключного використання одним Podʼом).

Стандартно kubelet використовує [квоту CFS](https://en.wikipedia.org/wiki/Completely_Fair_Scheduler) для застосування обмежень CPU Podʼів. Коли на вузлі працює багато Podʼів, залежних від CPU, робоче навантаження може переміщуватися між різними ядрами CPU залежно від того, чи зазнає Pod тротлінгу і які ядра CPU доступні на момент планування. Багато робочих навантажень не чутливі до цієї міграції і тому нормально працюють без будь-якого втручання.

Однак для робочих навантажень, де спорідненість кешу CPU та затримка планування суттєво впливають на продуктивність, kubelet дозволяє використовувати альтернативні політики керування CPU, щоб визначати деякі вподобання щодо розміщення на вузлі. Це реалізовано за допомогою _менеджера CPU_ та його політики. Доступні дві політики:

- `none`: політика `none` явно вмикає наявну стандартну схему спорідненості CPU, не забезпечуючи спорідненості понад те, що автоматично робить планувальник ОС. Обмеження використання CPU для [Podʼів Guaranteed](/docs/concepts/workloads/pods/pod-qos/) та [Podʼів Burstable](/docs/concepts/workloads/pods/pod-qos/) застосовуються за допомогою квоти CFS.
- `static`: політика `static` дозволяє контейнерам у Podʼах `Guaranteed` із цілочисельними `requests` CPU отримувати доступ до ексклюзивних CPU на вузлі. Ця ексклюзивність забезпечується за допомогою [контролера cgroup cpuset](https://www.kernel.org/doc/Documentation/cgroup-v2.txt).

{{< note >}}
Системні сервіси, такі як середовище виконання контейнерів і сам kubelet, можуть і надалі працювати на цих ексклюзивних CPU. Ексклюзивність поширюється лише на інші Podʼи.
{{< /note >}}

Менеджер CPU не підтримує вимкнення та ввімкнення CPU під час роботи.

#### Політика static {#static-policy}

Політика static забезпечує детальніше керування CPU та ексклюзивне призначення CPU. Ця політика керує спільним пулом CPU, який спочатку містить усі CPU вузла. Кількість CPU, доступних для ексклюзивного виділення, дорівнює загальній кількості CPU вузла за вирахуванням резервувань CPU, заданих конфігурацією kubelet. CPU, зарезервовані цими параметрами, беруться в цілій кількості з початкового спільного пулу за зростанням фізичного ідентифікатора ядра. Цей спільний пул є набором CPU, на яких працюють усі контейнери в Podʼах `BestEffort` та `Burstable`. Контейнери в Podʼах `Guaranteed` із дробовими `requests` CPU також працюють на CPU зі спільного пулу. Ексклюзивні CPU отримують лише контейнери, які є частиною Podʼа `Guaranteed` і мають цілочисельні `requests` CPU.

{{< note >}}
kubelet вимагає резервування CPU більше за нуль, коли ввімкнено політику static. Це тому, що нульове резервування CPU дозволило б спільному пулу стати порожнім.
{{< /note >}}

Коли Podʼи `Guaranteed`, контейнери яких відповідають вимогам статичного призначення, плануються на вузол, CPU вилучаються зі спільного пулу та розміщуються в cpuset контейнера. Квота CFS не використовується для обмеження використання CPU цими контейнерами, оскільки їхнє використання обмежене самим доменом планування. Іншими словами, кількість CPU в cpuset контейнера дорівнює цілочисельному `limit` CPU, вказаному в специфікації Podʼа. Це статичне призначення підвищує спорідненість CPU та зменшує кількість перемикань контексту через тротлінг для робочого навантаження, залежного від CPU.

Розгляньмо контейнери в наведених нижче специфікаціях Podʼів:

```yaml
spec:
  containers:
  - name: nginx
    image: nginx
```

Наведений вище Pod працює в класі QoS `BestEffort`, оскільки не вказано жодних `requests` чи `limits` ресурсів. Він працює в спільному пулі.

```yaml
spec:
  containers:
  - name: nginx
    image: nginx
    resources:
      limits:
        memory: "200Mi"
      requests:
        memory: "100Mi"
```

Наведений вище Pod працює в класі QoS `Burstable`, оскільки `requests` ресурсів не дорівнюють `limits`, а кількість `cpu` не вказана. Він працює в спільному пулі.

```yaml
spec:
  containers:
  - name: nginx
    image: nginx
    resources:
      limits:
        memory: "200Mi"
        cpu: "2"
      requests:
        memory: "100Mi"
        cpu: "1"
```

Наведений вище Pod працює в класі QoS `Burstable`, оскільки `requests` ресурсів не дорівнюють `limits`. Він працює в спільному пулі.

```yaml
spec:
  containers:
  - name: nginx
    image: nginx
    resources:
      limits:
        memory: "200Mi"
        cpu: "2"
      requests:
        memory: "200Mi"
        cpu: "2"
```

Наведений вище Pod працює в класі QoS `Guaranteed`, оскільки `requests` дорівнюють `limits`. І обмеження ресурсу CPU контейнера є цілим числом, більшим або рівним одиниці. Контейнер `nginx` отримує 2 ексклюзивні CPU.

```yaml
spec:
  containers:
  - name: nginx
    image: nginx
    resources:
      limits:
        memory: "200Mi"
        cpu: "1.5"
      requests:
        memory: "200Mi"
        cpu: "1.5"
```

Наведений вище Pod працює в класі QoS `Guaranteed`, оскільки `requests` дорівнюють `limits`. Але обмеження ресурсу CPU контейнера є дробовим. Він працює в спільному пулі.

```yaml
spec:
  containers:
  - name: nginx
    image: nginx
    resources:
      limits:
        memory: "200Mi"
        cpu: "2"
```

Наведений вище Pod працює в класі QoS `Guaranteed`, оскільки вказано лише `limits`, а `requests` прирівнюються до `limits`, коли їх не вказано явно. І обмеження ресурсу CPU контейнера є цілим числом, більшим або рівним одиниці. Контейнер `nginx` отримує 2 ексклюзивні CPU.

##### Параметри політики static {#cpu-policy-static--options}

Ось доступні параметри політики керування CPU static, перелічені в алфавітному порядку:

`align-by-socket` (alpha, стандартно приховано)
: Вирівнювання CPU за межею фізичного пакета / сокета, а не за логічними межами NUMA (доступно з Kubernetes v1.25)

`distribute-cpus-across-cores` (alpha, стандартно приховано)
: Розподіл віртуальних ядер, які іноді називають апаратними потоками, по різних фізичних ядрах (доступно з Kubernetes v1.31)

`distribute-cpus-across-numa` (beta, стандартно видимо)
: Розподіл CPU по різних доменах NUMA з метою рівномірного балансу між вибраними доменами (доступно з Kubernetes v1.23)

`full-pcpus-only` (GA, стандартно видимо)
: Завжди виділяти повні фізичні ядра (доступно з Kubernetes v1.22, GA з Kubernetes v1.33)

`strict-cpu-reservation` (GA, стандартно видимо)
: Запобігання запуску всіх Podʼів незалежно від їхнього класу якості обслуговування на зарезервованих CPU (доступно з Kubernetes v1.32, GA з Kubernetes v1.35)

`prefer-align-cpus-by-uncorecache` (GA, стандартно видимо)
: Вирівнювання CPU за межею кешу uncore (Last-Level) за принципом best-effort (доступно з Kubernetes v1.32)

Ви можете вмикати або вимикати групи параметрів залежно від їхнього рівня зрілості за допомогою таких функціональних можливостей:

- `CPUManagerPolicyBetaOptions` (стандартно увімкнено). Вимкніть, щоб приховати параметри рівня beta.
- `CPUManagerPolicyAlphaOptions` (стандартно вимкнено). Увімкніть, щоб показати параметри рівня alpha.

Вам все одно потрібно ввімкнути кожен параметр за допомогою поля `cpuManagerPolicyOptions` у файлі конфігурації kubelet.

Щоб дізнатися більше про окремі параметри, які можна налаштувати, читайте далі.

###### `full-pcpus-only`

Якщо вказано параметр політики `full-pcpus-only`, політика static завжди виділятиме повні фізичні ядра. Стандартно, без цього параметра, політика static виділяє CPU за принципом найкращого збігу з урахуванням топології. На системах з увімкненим SMT політика може виділяти окремі віртуальні ядра, які відповідають апаратним потокам. Це може призвести до того, що різні контейнери використовуватимуть ті самі фізичні ядра; така поведінка, у свою чергу, сприяє [проблемі шумних сусідів](https://en.wikipedia.org/wiki/Cloud_computing_issues#Performance_interference_and_noisy_neighbors). З увімкненим параметром kubelet допустить Pod лише тоді, коли запит CPU всіх його контейнерів можна задовольнити виділенням повних фізичних ядер. Якщо Pod не проходить допуск, він переходить у стан Failed із повідомленням `SMTAlignmentError`.

###### `distribute-cpus-across-numa`

Якщо вказано параметр політики `distribute-cpus-across-numa`, політика static рівномірно розподілятиме CPU між вузлами NUMA у випадках, коли для виконання виділення потрібно більше одного вузла NUMA. Стандартно `CPUManager` розміщує CPU на одному вузлі NUMA, доки він не заповниться, а залишкові CPU просто переходять на наступний вузол NUMA. Це може спричинити небажані вузькі місця в паралельному коді, що використовує барʼєри (та подібні примітиви синхронізації), оскільки такий код зазвичай працює лише так швидко, як його найповільніший робочий процес (який сповільнюється через те, що принаймні на одному вузлі NUMA доступно менше CPU). Рівномірно розподіляючи CPU між вузлами NUMA, розробники застосунків можуть легше забезпечити, щоб жоден робочий процес не страждав від ефектів NUMA більше за інші, покращуючи загальну продуктивність таких застосунків.

###### `align-by-socket`

Якщо вказано параметр політики `align-by-socket`, CPU вважатимуться вирівняними за межею сокета під час вирішення того, як виділити CPU контейнеру. Стандартно `CPUManager` вирівнює виділення CPU за межею NUMA, що може призвести до зниження продуктивності, якщо для виконання виділення CPU потрібно взяти більш ніж з одного вузла NUMA. Хоча він намагається забезпечити виділення всіх CPU з _мінімальної_ кількості вузлів NUMA, немає гарантії, що ці вузли NUMA будуть на одному сокеті. Вказавши `CPUManager` явно вирівнювати CPU за межею сокета, а не NUMA, ми можемо уникнути таких проблем. Зверніть увагу, що цей параметр політики несумісний із політикою `single-numa-node` `TopologyManager` і не застосовується до апаратного забезпечення, де кількість сокетів більша за кількість вузлів NUMA.

###### `distribute-cpus-across-cores`

Якщо вказано параметр політики `distribute-cpus-across-cores`, політика static намагатиметься виділяти віртуальні ядра (апаратні потоки) на різних фізичних ядрах. Стандартно `CPUManager` намагається розмістити CPU на якомога меншій кількості фізичних ядер, що може призвести до конкуренції між CPU на одному фізичному ядрі та спричинити вузькі місця продуктивності. Увімкнення політики `distribute-cpus-across-cores` забезпечує розподіл CPU на якомога більшій кількості фізичних ядер, зменшуючи конкуренцію на одному фізичному ядрі та покращуючи загальну продуктивність. Однак важливо зазначити, що ця стратегія може бути менш ефективною за високого навантаження системи. У таких умовах користь від зменшення конкуренції зменшується. Натомість стандартна поведінка може допомогти зменшити накладні витрати на міжядерну комунікацію, потенційно забезпечуючи кращу продуктивність за високого навантаження.

###### `strict-cpu-reservation`

Параметр `reservedSystemCPUs` у [KubeletConfiguration](/docs/reference/config-api/kubelet-config.v1beta1/) або застарілий параметр командного рядка kubelet `--reserved-cpus` визначає явний набір CPU для системних демонів ОС і демонів Kubernetes. Докладніше про цей параметр читайте на сторінці [Явно зарезервований список CPU](/docs/tasks/administer-cluster/reserve-compute-resources/#explicitly-reserved-cpu-list). Стандартно ця ізоляція реалізована лише для Podʼів guaranteed із цілочисельними запитами CPU, але не для Podʼів burstable та best-effort (і Podʼів guaranteed із дробовими запитами CPU). Допуск лише порівнює запити CPU з доступними для розподілу CPU. Оскільки обмеження CPU вище за запит, стандартна поведінка дозволяє Podʼам burstable та best-effort вичерпати місткість `reservedSystemCPUs` і спричинити голодування сервісів ОС хоста в реальних розгортаннях. Якщо ввімкнено параметр політики `strict-cpu-reservation`, політика static не дозволить жодному робочому навантаженню використовувати ядра CPU, вказані в `reservedSystemCPUs`.

###### `prefer-align-cpus-by-uncorecache`

Якщо вказано політику `prefer-align-cpus-by-uncorecache`, політика static виділятиме ресурси CPU для окремих контейнерів так, щоб усі CPU, призначені контейнеру, використовували той самий блок кешу uncore (також відомий як кеш останнього рівня, Last-Level Cache або LLC). Стандартно `CPUManager` щільно розподіляє CPU, що може призвести до того, що контейнери отримають CPU з кількох кешів uncore. Цей параметр дозволяє `CPUManager` виділяти CPU так, щоб максимізувати ефективне використання кешу uncore. Виділення виконується за принципом best-effort з метою розмістити якомога більше CPU в межах одного кешу uncore. Якщо вимога контейнера до CPU перевищує місткість CPU одного кешу uncore, `CPUManager` мінімізує кількість використаних кешів uncore, щоб підтримувати оптимальне вирівнювання. Окремі робочі навантаження можуть виграти в продуктивності завдяки зменшенню затримки між кешами та впливу шумних сусідів на рівні кешу. Якщо `CPUManager` не може оптимально вирівняти CPU, хоча вузол має достатньо ресурсів, контейнер однаково буде допущено зі стандартною щільною поведінкою.

## Менеджер памʼяті {#memory-manager}

{{< feature-state feature_gate_name="MemoryManager" >}}

*Менеджер памʼяті* — це компонент kubelet, який забезпечує ексклюзивне виділення ресурсів памʼяті. Для прийняття рішень щодо призначення ресурсів він консультується з менеджером топології. Щоб дізнатися більше, прочитайте [Керування політиками управління памʼяттю на вузлі](/docs/tasks/administer-cluster/memory-manager/).

### Політики призначення памʼяті Podʼам {#memory-management-policies}

*Менеджер памʼяті* Kubernetes виділяє ресурси оперативної памʼяті (памʼять і, за потреби, великі сторінки Linux) для Podʼів із {{< glossary_tooltip text="класом QoS" term_id="qos-class" >}} `Guaranteed`.

Менеджер памʼяті використовує протокол генерації підказок, щоб визначити найбільш придатну спорідненість NUMA для Podʼа. Менеджер памʼяті передає ці підказки спорідненості центральному менеджеру (*менеджеру топології*). На основі підказок і політики менеджера топології Pod відхиляється або допускається на вузол.

Крім того, менеджер памʼяті забезпечує виділення запитаної Podʼом памʼяті з мінімальної кількості вузлів NUMA.

Щоб дізнатися більше, прочитайте [Керування політиками управління памʼяттю на вузлі](/docs/tasks/administer-cluster/memory-manager/).

## Менеджер пристроїв {#device-manager}

{{< feature-state for_k8s_version="v1.26" state="stable" >}}

*Менеджер пристроїв* — це компонент kubelet, який виділяє апаратні пристрої Podʼам за допомогою API втулків пристроїв. Для прийняття рішень щодо призначення ресурсів він консультується з менеджером топології, використовуючи інформацію про топологію, надану втулками пристроїв. Щоб дізнатися більше, прочитайте [Інтеграція втулків пристроїв з менеджером топології](/docs/concepts/extend-kubernetes/compute-storage-net/device-plugins/#device-plugin-integration-with-the-topology-manager).

## Менеджери ресурсів на рівні Podʼів {#pod-level-resource-managers}

{{< feature-state feature_gate_name="PodLevelResourceManagers" >}}

Підтримка ресурсів на рівні Podʼів для менеджерів ресурсів `kubelet` (топології, CPU та памʼяті) дозволяє менеджерам ресурсів використовувати `.spec.resources` безпосередньо для рішень щодо вирівнювання за NUMA та ексклюзивного виділення.

Щоб дізнатися більше, перегляньте окрему сторінку концепції [Менеджери ресурсів на рівні Podʼів](/docs/concepts/resource-management/pod-level-resource-managers/) або прочитайте, як [призначати ресурси CPU та памʼяті на рівні Podʼів](/docs/tasks/configure-pod-container/assign-pod-level-resources/).
