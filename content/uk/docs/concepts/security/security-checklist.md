Цей список перевірки має на меті надати базовий перелік настанов із посиланнями на докладнішу документацію з кожної теми. Він не претендує на вичерпність і буде змінюватися з часом.

Як читати й використовувати цей документ:

- Порядок тем не відображає порядок пріоритетів.
- Деякі пункти списку описано докладніше в абзаці під списком кожного розділу.

{{< caution >}}
Самих лише списків перевірки **недостатньо** для досягнення належного рівня безпеки. Належний рівень безпеки потребує постійної уваги й удосконалення, але список перевірки може бути першим кроком на нескінченному шляху до готовності в питаннях безпеки. Деякі рекомендації в цьому списку можуть бути надто обмежувальними або надто мʼякими для ваших конкретних потреб у безпеці. Оскільки безпека Kubernetes не є універсальною для всіх, кожну категорію пунктів списку слід оцінювати окремо.
{{< /caution >}}

## Автентифікація та авторизація {#authentication-authorization}

- [ ] Група `system:masters` не використовується для автентифікації користувачів чи компонентів після початкового налаштування.
- [ ] Компонент kube-controller-manager працює з увімкненим параметром `--use-service-account-credentials`.
- [ ] Кореневий сертифікат захищений (або офлайн CA, або керований онлайн CA з ефективними засобами контролю доступу).
- [ ] Проміжні та кінцеві сертифікати мають строк дії не більше ніж 3 роки наперед.
- [ ] Існує процес періодичного перегляду доступу, і перегляди відбуваються з інтервалом не більше ніж 24 місяці.
- [ ] Для настанов щодо автентифікації та авторизації використовуються [рекомендації щодо контролю доступу на основі ролей](/docs/concepts/security/rbac-good-practices/).

Після початкового налаштування ні користувачі, ні компоненти не повинні автентифікуватися в API Kubernetes як `system:masters`. Так само слід уникати запуску всього kube-controller-manager від імені `system:masters`. Фактично `system:masters` слід використовувати лише як механізм аварійного доступу, а не як адміністративного користувача.

## Безпека мережі {#network-security}

- [ ] CNI-втулки, що використовуються, підтримують мережеві політики.
- [ ] Мережеві політики для вхідного та вихідного трафіку застосовано до всіх робочих навантажень у кластері.
- [ ] У кожному просторі імен діють стандартні мережеві політики, які вибирають усі Podʼи та забороняють усе.
- [ ] За потреби використовується service mesh для шифрування всіх зʼєднань усередині кластера.
- [ ] Доступ до API Kubernetes, API kubelet та etcd не відкрито публічно в Інтернеті.
- [ ] Доступ робочих навантажень до API хмарних метаданих фільтрується.
- [ ] Використання LoadBalancer та ExternalIPs обмежено.

Низка [втулків Container Network Interface (CNI)](/docs/concepts/extend-kubernetes/compute-storage-net/network-plugins/) дозволяє обмежувати мережеві ресурси, з якими можуть взаємодіяти Podʼи. Найчастіше це робиться за допомогою [мережевих політик](/docs/concepts/services-networking/network-policies/), які є ресурсом у межах простору імен для визначення правил. Стандартні мережеві політики, які блокують увесь вихідний і вхідний трафік у кожному просторі імен, вибираючи всі Podʼи, допомагають застосувати підхід зі списком дозволеного й переконатися, що жодне робоче навантаження не пропущено.

Не всі CNI-втулки забезпечують шифрування під час передавання. Якщо обраний втулок не має цієї можливості, альтернативним рішенням може бути використання service mesh.

Сховище даних etcd панелі управління повинно мати засоби обмеження доступу й не повинно бути публічно доступним в Інтернеті. Крім того, для безпечного звʼязку з ним слід використовувати взаємний TLS (mTLS). Центр сертифікації для цього має бути окремим, лише для etcd.

Зовнішній доступ з Інтернету до API-сервера Kubernetes слід обмежити, щоб не відкривати API публічно. Будьте обережні: багато керованих дистрибутивів Kubernetes стандартно відкривають публічний доступ до API-сервера. У такому разі для доступу до сервера можна використовувати хост-бастіон.

Доступ до API [kubelet](/docs/reference/command-line-tools-reference/kubelet/) слід обмежити й не відкривати публічно: стандартні налаштування автентифікації та авторизації, якщо файл конфігурації не вказано прапорцем `--config`, є надто дозвільними.

Якщо Kubernetes розміщено в хмарного провайдера, доступ Podʼів до API хмарних метаданих `169.254.169.254` також слід обмежити або заблокувати, якщо він не потрібен, оскільки це може призвести до витоку інформації.

Докладніше про обмеження використання LoadBalancer та ExternalIPs дивіться [CVE-2020-8554: Man in the middle using LoadBalancer or ExternalIPs](https://github.com/kubernetes/kubernetes/issues/97076) та [контролер допуску DenyServiceExternalIPs](/docs/reference/access-authn-authz/admission-controllers/#denyserviceexternalips).

## Безпека Podʼів {#pod-security}

- [ ] Права RBAC `create`, `update`, `patch`, `delete` для робочих навантажень надаються лише за потреби.
- [ ] Для всіх просторів імен визначено й примусово застосовано відповідну політику стандартів безпеки Podʼів.
- [ ] Для робочих навантажень встановлено обмеження памʼяті, що дорівнює запиту або менше за нього.
- [ ] Для чутливих робочих навантажень можна встановити обмеження CPU.
- [ ] На вузлах, що його підтримують, увімкнено Seccomp з відповідним профілем syscalls для програм.
- [ ] На вузлах, що їх підтримують, увімкнено AppArmor або SELinux з відповідним профілем для програм.

Авторизація RBAC є важливою, але [не може бути достатньо деталізованою, щоб авторизувати дії з ресурсами Podʼів](/docs/concepts/security/rbac-good-practices/#workload-creation) (або з будь-яким ресурсом, який керує Podʼами). Єдиним рівнем деталізації є дієслова API для самого ресурсу, наприклад `create` для Podʼів. Без додаткового контролю допуску дозвіл на створення цих ресурсів надає прямий необмежений доступ до придатних для планування вузлів кластера.

[Стандарти безпеки Podʼів](/docs/concepts/security/pod-security-standards/) визначають три різні політики: privileged, baseline і restricted, які обмежують, як можна встановлювати поля `PodSpec`, що стосуються безпеки. Ці стандарти можна примусово застосовувати на рівні простору імен за допомогою нового допуску [Pod Security](/docs/concepts/security/pod-security-admission/), стандартно ввімкненого, або стороннього вебхука допуску. Зверніть увагу, що, на відміну від вилученого допуску PodSecurityPolicy, який він замінює, допуск [Pod Security](/docs/concepts/security/pod-security-admission/) можна легко поєднувати з вебхуками допуску та зовнішніми сервісами.

Політика `restricted` допуску Pod Security, найсуворіша політика з набору [стандартів безпеки Podʼів](/docs/concepts/security/pod-security-standards/), [може працювати в кількох режимах](/docs/concepts/security/pod-security-admission/#pod-security-admission-labels-for-namespaces), `warn`, `audit` або `enforce`, щоб поступово застосовувати найвідповідніший [контекст безпеки](/docs/tasks/configure-pod-container/security-context/) згідно з рекомендаціями з безпеки. Проте [контекст безпеки](/docs/tasks/configure-pod-container/security-context/) Podʼів слід досліджувати окремо, щоб обмежити привілеї та доступ, які Podʼи можуть мати понад наперед визначені стандарти безпеки, для конкретних сценаріїв використання.

Практичний навчальний матеріал про [Pod Security](/docs/concepts/security/pod-security-admission/) дивіться в дописі блогу [Kubernetes 1.23: Pod Security Graduates to Beta](/blog/2021/12/09/pod-security-admission-beta/).

[Обмеження памʼяті та CPU](/docs/concepts/configuration/manage-resources-containers/) слід встановлювати, щоб обмежити ресурси памʼяті та CPU, які Pod може споживати на вузлі, і таким чином запобігти можливим DoS-атакам зі зловмисних або скомпрометованих робочих навантажень. Таку політику може примусово застосовувати контролер допуску. Зверніть увагу, що обмеження CPU спричиняють тротлінг і тому можуть мати небажаний вплив на можливості автомасштабування або на ефективність, тобто на виконання процесу в режимі best effort з доступними ресурсами CPU.

{{< caution >}}
Обмеження памʼяті, що перевищує запит, може наразити весь вузол на проблеми з OOM.
{{< /caution >}}

### Увімкнення Seccomp {#enabling-seccomp}

Seccomp означає режим безпечних обчислень (secure computing mode) і є можливістю ядра Linux з версії 2.6.12. Його можна використовувати, щоб ізолювати привілеї процесу в пісочниці, обмежуючи виклики, які він може робити з простору користувача до ядра. Kubernetes дозволяє автоматично застосовувати до ваших Podʼів і контейнерів профілі seccomp, завантажені на вузол.

Seccomp може покращити безпеку ваших робочих навантажень, зменшуючи поверхню атаки через системні виклики ядра Linux, доступну всередині контейнерів. Режим фільтрації seccomp використовує BPF для створення списків дозволених або заборонених конкретних системних викликів, які називаються профілями.

Починаючи з Kubernetes 1.27, ви можете ввімкнути використання `RuntimeDefault` як стандартного профілю seccomp для всіх робочих навантажень. На цю тему є [навчальний матеріал з безпеки](/docs/tutorials/security/seccomp/). Крім того, [Kubernetes Security Profiles Operator](https://github.com/kubernetes-sigs/security-profiles-operator) — це проєкт, що полегшує керування seccomp і його використання в кластерах.

{{< note >}}
Seccomp доступний лише на вузлах Linux.
{{< /note >}}

### Увімкнення AppArmor або SELinux {#enabling-apparmor-or-selinux}

#### AppArmor

[AppArmor](/docs/tutorials/security/apparmor/) — це модуль безпеки ядра Linux, який може забезпечити простий спосіб реалізації обовʼязкового контролю доступу (MAC, Mandatory Access Control) та кращого аудиту через системні логи. На вузлах, які його підтримують, примусово застосовується стандартний профіль AppArmor, або можна налаштувати власний профіль. Як і seccomp, AppArmor налаштовується через профілі, де кожен профіль працює або в режимі примусового застосування (enforcing), який блокує доступ до заборонених ресурсів, або в режимі скарг (complain), який лише повідомляє про порушення. Профілі AppArmor застосовуються до кожного контейнера окремо за допомогою анотації, що дозволяє процесам отримувати саме ті привілеї, які їм потрібні.

{{< note >}}
AppArmor доступний лише на вузлах Linux і ввімкнений у [деяких дистрибутивах Linux](https://gitlab.com/apparmor/apparmor/-/wikis/home#distributions-and-ports).
{{< /note >}}

#### SELinux

[SELinux](https://github.com/SELinuxProject/selinux-notebook/blob/main/src/selinux_overview.md) також є модулем безпеки ядра Linux, який надає механізм підтримки політик безпеки контролю доступу, зокрема обовʼязкового контролю доступу (MAC). Мітки SELinux можна призначати контейнерам або Podʼам [через їхній розділ `securityContext`](/docs/tasks/configure-pod-container/security-context/#assign-selinux-labels-to-a-container).

{{< note >}}
SELinux доступний лише на вузлах Linux і ввімкнений у [деяких дистрибутивах Linux](https://en.wikipedia.org/wiki/Security-Enhanced_Linux#Implementations).
{{< /note >}}

## Розташування Podʼів {#pod-placement}

- [ ] Розташування Podʼів відповідає рівням чутливості застосунку.
- [ ] Чутливі застосунки працюють ізольовано на вузлах або з окремими середовищами виконання в пісочниці.

Podʼи різних рівнів чутливості, наприклад Pod застосунку та API-сервер Kubernetes, слід розгортати на окремих вузлах. Мета ізоляції вузлів — не дати зловмиснику після виходу за межі контейнера застосунку отримати прямий доступ до застосунків із вищим рівнем чутливості й легко переміщуватися кластером. Це розділення слід забезпечувати примусово, щоб Podʼи випадково не розгорталися на тому самому вузлі. Для цього можна використовувати такі можливості:

[Селектори вузлів](/docs/concepts/scheduling-eviction/assign-pod-node/)
: Пари ключ-значення в специфікації Podʼа, які вказують, на яких вузлах його розгортати. Їх можна примусово застосовувати на рівні простору імен і кластера за допомогою контролера допуску [PodNodeSelector](/docs/reference/access-authn-authz/admission-controllers/#podnodeselector).

[PodTolerationRestriction](/docs/reference/access-authn-authz/admission-controllers/#podtolerationrestriction)
: Контролер допуску, який дозволяє адміністраторам обмежувати дозволені [tolerations](/docs/concepts/scheduling-eviction/taint-and-toleration/) у межах простору імен. Podʼи в просторі імен можуть використовувати лише tolerations, вказані в ключах анотації обʼєкта простору імен, які задають набір стандартних і дозволених tolerations.

[RuntimeClass](/docs/concepts/containers/runtime-class/)
: RuntimeClass — це можливість вибору конфігурації середовища виконання контейнерів. Ця конфігурація використовується для запуску контейнерів Podʼа й може забезпечувати більшу або меншу ізоляцію від хоста ціною додаткових витрат продуктивності.

## Secrets {#secrets}

- [ ] ConfigMaps не використовуються для зберігання конфіденційних даних.
- [ ] Для Secret API налаштовано шифрування у стані спокою.
- [ ] За потреби розгорнуто й доступний механізм для додавання Secrets, що зберігаються в сторонньому сховищі.
- [ ] Токени ServiceAccount не монтуються в Podʼи, яким вони не потрібні.
- [ ] Використовується [том привʼязаних токенів ServiceAccount](/docs/reference/access-authn-authz/service-accounts-admin/#bound-service-account-token-volume) замість токенів без строку дії.

Конфіденційні дані, потрібні Podʼам, слід зберігати в обʼєктах Secret Kubernetes, а не в альтернативах на кшталт ConfigMap. Ресурси Secret, що зберігаються в etcd, слід [шифрувати у стані спокою](/docs/tasks/administer-cluster/encrypt-data/).

Podʼи, яким потрібні Secrets, повинні отримувати їх автоматично змонтованими через томи, бажано збереженими в памʼяті, як-от за допомогою [параметра `emptyDir.medium`](/docs/concepts/storage/volumes/#emptydir). Цей механізм також можна використовувати для додавання Secrets зі сторонніх сховищ у вигляді томів, як-от у [Secrets Store CSI Driver](https://secrets-store-csi-driver.sigs.k8s.io/). Цьому способу слід надавати перевагу перед наданням ServiceAccount Podʼа доступу RBAC до Secrets. Це дозволить додавати Secrets у Pod як змінні середовища або файли. Зверніть увагу, що спосіб зі змінними середовища може бути більш схильним до витоків через аварійні дампи в логах і неконфіденційну природу змінних середовища в Linux, на відміну від механізму дозволів на файли.

Токени ServiceAccount не слід монтувати в Podʼи, яким вони не потрібні. Це можна налаштувати, встановивши [`automountServiceAccountToken`](/docs/tasks/configure-pod-container/configure-service-account/#use-the-default-service-account-to-access-the-api-server) у `false` або в ServiceAccount, щоб застосувати це до всього простору імен, або окремо для Podʼа. Для Kubernetes v1.22 і новіших використовуйте [привʼязані ServiceAccounts](/docs/reference/access-authn-authz/service-accounts-admin/#bound-service-account-token-volume) для обмежених у часі облікових даних ServiceAccount.

## Образи {#images}

- [ ] Мінімізуйте непотрібний вміст в образах контейнерів.
- [ ] Образи контейнерів налаштовано на запуск від імені непривілейованого користувача.
- [ ] На образи контейнерів посилаються за дайджестами sha256 (а не за теґами), або походження образу підтверджується перевіркою його цифрового підпису під час розгортання [через контроль допуску](/docs/tasks/administer-cluster/verify-signed-artifacts/#verifying-image-signatures-with-admission-controller).
- [ ] Образи контейнерів регулярно скануються під час створення та розгортання, а для відомого вразливого програмного забезпечення застосовуються виправлення.

Образ контейнера повинен містити лише мінімум, потрібний для запуску програми, яку він пакує. Бажано лише програму та її залежності, а сам образ слід збирати з мінімально можливої бази. Зокрема, образи, що використовуються в промисловому середовищі, не повинні містити оболонок або засобів налагодження, оскільки для усунення несправностей можна використовувати [ефемерний контейнер налагодження](/docs/tasks/debug/debug-application/debug-running-pod/#ephemeral-container).

Збирайте образи так, щоб вони одразу запускалися від імені непривілейованого користувача, за допомогою [інструкції `USER` у Dockerfile](https://docs.docker.com/develop/develop-images/dockerfile_best-practices/#user). [Контекст безпеки](/docs/tasks/configure-pod-container/security-context/#set-the-security-context-for-a-pod) дозволяє запускати образ контейнера від імені певного користувача та групи за допомогою `runAsUser` і `runAsGroup`, навіть якщо їх не вказано в маніфесті образу. Однак дозволи на файли в шарах образу можуть унеможливити простий запуск процесу від імені нового непривілейованого користувача без зміни образу.

Уникайте посилань на образ за теґом, особливо за теґом `latest`, оскільки образ за теґом можна легко змінити в реєстрі. Надавайте перевагу повному дайджесту `sha256`, який є унікальним для маніфесту образу. Цю політику можна примусово застосовувати за допомогою [ImagePolicyWebhook](/docs/reference/access-authn-authz/admission-controllers/#imagepolicywebhook). Підписи образів також можна автоматично [перевіряти контролером допуску](/docs/tasks/administer-cluster/verify-signed-artifacts/#verifying-image-signatures-with-admission-controller) під час розгортання, щоб підтверджувати їхню автентичність і цілісність.

Сканування образу контейнера може запобігти потраплянню критичних вразливостей до кластера разом з образом. Сканування образу слід завершувати до розгортання образу контейнера в кластері, і зазвичай воно виконується як частина процесу розгортання в конвеєрі CI/CD. Мета сканування образу — отримати інформацію про можливі вразливості та їх запобігання в образі контейнера, наприклад оцінку [Common Vulnerability Scoring System (CVSS)](https://www.first.org/cvss/). Якщо результати сканування поєднати з правилами відповідності конвеєра, до промислового середовища потраплять лише образи контейнерів із належними виправленнями.

## Контролери допуску {#admission-controllers}

- [ ] Увімкнено відповідний набір контролерів допуску.
- [ ] Політика безпеки Podʼів примусово застосовується за допомогою Pod Security Admission та/або контролера допуску на основі вебхука.
- [ ] Втулки ланцюжка допуску та вебхуки налаштовано безпечно.

Контролери допуску можуть допомогти покращити безпеку кластера. Однак вони самі можуть становити ризики, оскільки розширюють API-сервер і [мають бути належно захищені](/blog/2022/01/19/secure-your-admission-controllers-and-webhooks/).

У наведених нижче списках подано низку контролерів допуску, які варто розглянути для покращення безпеки вашого кластера та застосунку. Сюди входять контролери, на які можуть бути посилання в інших частинах цього документа.

Ця перша група контролерів допуску містить втулки, [стандартно ввімкнені](/docs/reference/access-authn-authz/admission-controllers/#which-plugins-are-enabled-by-default). Залишайте їх увімкненими, якщо тільки не розумієте, що робите:

[`CertificateApproval`](/docs/reference/access-authn-authz/admission-controllers/#certificateapproval)
: Виконує додаткові перевірки авторизації, щоб переконатися, що користувач, який затверджує запит на сертифікат, має на це дозвіл.

[`CertificateSigning`](/docs/reference/access-authn-authz/admission-controllers/#certificatesigning)
: Виконує додаткові перевірки авторизації, щоб переконатися, що користувач, який підписує запити на сертифікати, має на це дозвіл.

[`CertificateSubjectRestriction`](/docs/reference/access-authn-authz/admission-controllers/#certificatesubjectrestriction)
: Відхиляє будь-який запит на сертифікат, у якому вказано «групу» (або «атрибут організації») `system:masters`.

[`LimitRanger`](/docs/reference/access-authn-authz/admission-controllers/#limitranger)
: Застосовує обмеження API LimitRange.

[`MutatingAdmissionWebhook`](/docs/reference/access-authn-authz/admission-controllers/#mutatingadmissionwebhook)
: Дозволяє використовувати власні контролери через вебхуки; ці контролери можуть змінювати запити, які вони перевіряють.

[`PodSecurity`](/docs/reference/access-authn-authz/admission-controllers/#podsecurity)
: Заміна Pod Security Policy; обмежує контексти безпеки розгорнутих Podʼів.

[`ResourceQuota`](/docs/reference/access-authn-authz/admission-controllers/#resourcequota)
: Застосовує квоти ресурсів, щоб запобігти надмірному використанню ресурсів.

[`ValidatingAdmissionWebhook`](/docs/reference/access-authn-authz/admission-controllers/#validatingadmissionwebhook)
: Дозволяє використовувати власні контролери через вебхуки; ці контролери не змінюють запити, які вони перевіряють.

Друга група містить втулки, які стандартно не ввімкнені, але перебувають у стані загальної доступності й рекомендовані для покращення безпеки:

[`DenyServiceExternalIPs`](/docs/reference/access-authn-authz/admission-controllers/#denyserviceexternalips)
: Відхиляє будь-яке нове використання поля `Service.spec.externalIPs`. Це захід помʼякшення для [CVE-2020-8554: Man in the middle using LoadBalancer or ExternalIPs](https://github.com/kubernetes/kubernetes/issues/97076).

[`NodeRestriction`](/docs/reference/access-authn-authz/admission-controllers/#noderestriction)
: Обмежує дозволи kubelet лише зміною ресурсів API Podʼів, які йому належать, або ресурсу API вузла, що його представляє. Він також не дозволяє kubelet використовувати анотацію `node-restriction.kubernetes.io/`, яку зловмисник із доступом до облікових даних kubelet міг би використати, щоб впливати на розміщення Podʼів на контрольованому вузлі.

Третя група містить втулки, які стандартно не ввімкнені, але їх можна розглянути для певних сценаріїв використання:

[`AlwaysPullImages`](/docs/reference/access-authn-authz/admission-controllers/#alwayspullimages)
: Примусово забезпечує використання останньої версії образу з теґом і перевіряє, що той, хто виконує розгортання, має дозволи на використання образу.

[`ImagePolicyWebhook`](/docs/reference/access-authn-authz/admission-controllers/#imagepolicywebhook)
: Дозволяє застосовувати додаткові засоби контролю для образів через вебхуки.
