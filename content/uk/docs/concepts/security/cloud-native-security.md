# Індекс розділу це явно зазначає
hide_summary: true

description: >
  Концепції захисту ваших робочих навантажень cloud native.

Kubernetes базується на архітектурі cloud native і спирається на поради {{< glossary_tooltip text="CNCF" term_id="cncf" >}} щодо рекомендованих практик інформаційної безпеки cloud native.

Нижче наведено огляд того, як Kubernetes допомагає розгорнути безпечну платформу cloud native.

## Інформаційна безпека cloud native {#cloud-native-information-security}

У [white paper](https://github.com/cncf/tag-security/blob/main/community/resources/security-whitepaper/v2/CNCF_cloud-native-security-whitepaper-May2022-v2.pdf) CNCF про безпеку cloud native визначено засоби контролю та практики безпеки для різних _фаз життєвого циклу_.

## Фаза життєвого циклу _Розробка_ {#lifecycle-phase-develop}

- Забезпечте цілісність середовищ розробки.
- Проєктуйте застосунки відповідно до рекомендованих практик інформаційної безпеки, що підходять для вашого контексту.
- Враховуйте безпеку кінцевого користувача як частину проєктного рішення.

Для цього:

1. Використовуйте архітектуру, таку як [нульова довіра](https://glossary.cncf.io/zero-trust-architecture/), що мінімізує поверхню атаки навіть для внутрішніх загроз.
1. Визначте процес перевірки коду, який враховує питання безпеки.
1. Створіть _модель загроз_ вашої системи або застосунку, яка визначає межі довіри. Використовуйте цю модель, щоб виявляти ризики й визначати, як із ними працювати.
1. Там, де це виправдано, впроваджуйте передову автоматизацію безпеки, таку як _fuzzing_ та [security chaos engineering](https://glossary.cncf.io/security-chaos-engineering/).

## Фаза життєвого циклу _Розповсюдження_ {#lifecycle-phase-distribute}

- Забезпечте безпеку ланцюга постачання образів контейнерів, які ви запускаєте.
- Забезпечте безпеку ланцюга постачання кластера та інших компонентів, які запускають ваш застосунок. Наприклад, це може бути зовнішня база даних, яку ваш застосунок cloud native використовує для зберігання даних.

Для цього:

1. Скануйте образи контейнерів та інші артефакти на наявність відомих вразливостей.
1. Переконайтеся, що розповсюдження програмного забезпечення використовує шифрування під час передавання з ланцюгом довіри до джерела програмного забезпечення.
1. Запровадьте процеси оновлення залежностей, коли стають доступні оновлення, особливо у відповідь на оголошення про безпеку, і дотримуйтеся їх.
1. Використовуйте механізми перевірки, такі як цифрові сертифікати, для гарантії безпеки ланцюга постачання.
1. Підписуйтесь на стрічки (feeds) та інші механізми, щоб отримувати сповіщення про безпекові ризики.
1. Обмежуйте доступ до артефактів. Розміщуйте образи контейнерів у [приватному реєстрі](/docs/concepts/containers/images/#using-a-private-registry), який дозволяє завантажувати образи лише авторизованим клієнтам.

## Фаза життєвого циклу _Розгортання_ {#lifecycle-phase-deploy}

Забезпечте відповідні обмеження на те, що можна розгортати, хто може це робити й куди це можна розгорнути. Ви можете застосовувати заходи з фази _розповсюдження_, такі як перевірка криптографічної ідентичності артефактів образів контейнерів.

Ви можете розгортати різні застосунки та компоненти кластера в різних {{< glossary_tooltip text="просторах імен" term_id="namespace" >}}. Контейнери та простори імен забезпечують механізми ізоляції, що є важливими для інформаційної безпеки.

Під час розгортання Kubernetes ви також закладаєте основу для середовища виконання ваших застосунків: кластер Kubernetes (або кілька кластерів). Ця інфраструктура має забезпечувати гарантії безпеки, яких очікують вищі рівні.

## Фаза життєвого циклу _Виконання_ {#lifecycle-phase-runtime}

Фаза виконання охоплює три критичні області: [доступ](#protection-runtime-access), [обчислення](#protection-runtime-compute) та [зберігання](#protection-runtime-storage).

### Захист під час виконання: доступ {#protection-runtime-access}

API Kubernetes — це те, завдяки чому працює ваш кластер. Захист цього API є ключовим для ефективної безпеки кластера.

Інші сторінки документації Kubernetes докладніше описують, як налаштувати окремі аспекти контролю доступу. [Список перевірки безпеки](/docs/concepts/security/security-checklist/) містить рекомендовані базові перевірки для вашого кластера.

Крім того, захист кластера означає впровадження ефективної [автентифікації](/docs/concepts/security/controlling-access/#authentication) та [авторизації](/docs/concepts/security/controlling-access/#authorization) для доступу до API. Використовуйте [ServiceAccounts](/docs/concepts/security/service-accounts/), щоб надавати ідентичності безпеки робочим навантаженням і компонентам кластера та керувати ними.

Kubernetes використовує TLS для захисту трафіку API; переконайтеся, що кластер розгорнуто з TLS (зокрема для трафіку між вузлами та панеллю управління), і захистіть ключі шифрування. Якщо ви використовуєте власний API Kubernetes для [CertificateSigningRequests](/docs/reference/access-authn-authz/certificate-signing-requests/#certificate-signing-requests), приділіть особливу увагу обмеженню зловживань ним.

### Захист під час виконання: обчислення {#protection-runtime-compute}

{{< glossary_tooltip text="Контейнери" term_id="container" >}} забезпечують дві речі: ізоляцію між застосунками та механізм обʼєднання цих ізольованих застосунків для роботи на одному хост-компʼютері. Ці два аспекти — ізоляція та агрегація — означають, що безпека під час виконання передбачає пошук компромісів і відповідного балансу.

Kubernetes покладається на {{< glossary_tooltip text="середовище виконання контейнерів" term_id="container-runtime" >}} для налаштування та запуску контейнерів. Проєкт Kubernetes не рекомендує конкретне середовище виконання контейнерів, і вам слід переконатися, що вибране середовище відповідає вашим потребам в інформаційній безпеці.

Для захисту обчислень під час виконання ви можете:

1. Застосовувати до застосунків [стандарти безпеки Podʼів](/docs/concepts/security/pod-security-standards/), щоб вони працювали лише з потрібними привілеями.
1. Запускати на вузлах спеціалізовану операційну систему, призначену саме для контейнеризованих робочих навантажень. Зазвичай вона базується на операційній системі лише для читання (_незмінний образ_), яка надає тільки сервіси, необхідні для запуску контейнерів.

   Операційні системи для контейнерів допомагають ізолювати системні компоненти та зменшують поверхню атаки в разі виходу за межі контейнера.

1. Визначати [ResourceQuotas](/docs/concepts/policy/resource-quotas/) для справедливого розподілу спільних ресурсів і використовувати механізми, такі як [LimitRanges](/docs/concepts/policy/limit-range/), щоб Podʼи вказували свої вимоги до ресурсів.
1. Розподіляти робочі навантаження між різними вузлами для кращої ізоляції. Використовувати механізми [ізоляції вузлів](/docs/concepts/scheduling-eviction/assign-pod-node/#node-isolation-restriction) із самого Kubernetes або з екосистеми, щоб Podʼи з різними контекстами довіри працювали на окремих наборах вузлів.
1. Використовувати {{< glossary_tooltip text="середовище виконання контейнерів" term_id="container-runtime" >}}, яке забезпечує обмеження безпеки.
1. На вузлах Linux використовувати модуль безпеки Linux, такий як [AppArmor](/docs/tutorials/security/apparmor/) або [seccomp](/docs/tutorials/security/seccomp/).

### Захист під час виконання: зберігання {#protection-runtime-storage}

Щоб захистити сховище вашого кластера та застосунків, що в ньому працюють:

1. Інтегруйте свій кластер із зовнішнім втулком сховища, який забезпечує шифрування томів у стані спокою.
1. Увімкніть [шифрування в стані спокою](/docs/tasks/administer-cluster/encrypt-data/) для обʼєктів API.
1. Захистіть стійкість даних за допомогою резервних копій і перевіряйте, що можете відновити їх, коли це потрібно.
1. Автентифікуйте зʼєднання між вузлами кластера та будь-яким мережевим сховищем, на яке вони спираються.
1. Впровадьте шифрування даних у межах вашого власного застосунку.

Генерація ключів шифрування на спеціалізованому обладнанні забезпечує найкращий захист від ризиків розголошення. _Апаратний модуль безпеки_ дозволяє виконувати криптографічні операції без можливості копіювання ключа безпеки в інше місце.

### Мережа та безпека {#networking-and-security}

Також варто врахувати заходи мережевої безпеки, такі як [NetworkPolicy](/docs/concepts/services-networking/network-policies/) або [service mesh](https://glossary.cncf.io/service-mesh/). Деякі мережеві втулки для Kubernetes шифрують мережу кластера за допомогою таких технологій, як оверлей віртуальної приватної мережі (VPN). За задумом Kubernetes дозволяє використовувати власний мережевий втулок для кластера. Якщо ви використовуєте керований Kubernetes, провайдер міг уже вибрати мережевий втулок за вас.

Мережевий втулок, який ви виберете, і спосіб його інтеграції можуть суттєво вплинути на безпеку інформації під час передавання.

### Спостережуваність та безпека виконання {#observability-and-runtime-security}

Kubernetes дозволяє розширювати кластер додатковими інструментами. Ви можете налаштувати сторонні рішення для моніторингу або усунення несправностей ваших застосунків і кластерів, у яких вони працюють. Ви також отримуєте деякі базові можливості спостережуваності, вбудовані в сам Kubernetes. Ваш код у контейнерах може генерувати логи, публікувати метрики або надавати інші дані спостережуваності; під час розгортання потрібно переконатися, що ваш кластер забезпечує для них відповідний рівень захисту.

Якщо ви налаштовуєте dashboard метрик або щось подібне, перегляньте ланцюжок компонентів, які передають дані до цього dashboard, а також сам dashboard. Переконайтеся, що весь ланцюжок має достатню стійкість і захист цілісності, щоб на нього можна було покластися навіть під час інциденту, коли робота вашого кластера може погіршитися.

За потреби розгортайте заходи безпеки нижче рівня Kubernetes, такі як криптографічно вимірюване завантаження або автентифікований розподіл часу (що допомагає забезпечити точність логів і записів аудиту).

Для середовищ із високим рівнем гарантій розгортайте криптографічний захист, щоб логи були захищені від підробки й конфіденційні.
