## Проксі {#proxies}

Під час роботи з Kubernetes вам можуть трапитися кілька різних проксі:

1. [Проксі kubectl](/docs/tasks/access-application-cluster/access-cluster/#directly-accessing-the-rest-api):

    - працює на компʼютері користувача або в Podʼі
    - проксіює запити з локальної адреси до apiserver Kubernetes
    - між клієнтом і проксі використовується HTTP
    - між проксі й apiserver використовується HTTPS
    - визначає розташування apiserver
    - додає заголовки автентифікації

1. [Проксі apiserver](/docs/tasks/access-application-cluster/access-cluster-services/#discovering-builtin-services):

    - є бастіоном, вбудованим в apiserver
    - зʼєднує користувача поза кластером з кластерними IP, які інакше можуть бути недоступними
    - працює в процесах apiserver
    - між клієнтом і проксі використовується HTTPS (або http, якщо так налаштовано apiserver)
    - між проксі й ціллю може використовуватися HTTP або HTTPS, на вибір проксі за наявною інформацією
    - може використовуватися для доступу до Node, Pod або Service
    - виконує балансування навантаження, коли використовується для доступу до Service

1. [kube proxy](/docs/concepts/services-networking/service/#ips-and-vips):

    - працює на кожному вузлі
    - проксіює UDP, TCP та SCTP
    - не розуміє HTTP
    - забезпечує балансування навантаження
    - використовується лише для доступу до Services

1. Проксі/балансувальник навантаження перед одним або кількома apiserver:

    - наявність та реалізація різняться від кластера до кластера (наприклад, nginx)
    - розташований між усіма клієнтами та одним або кількома apiserver
    - діє як балансувальник навантаження, якщо є кілька apiserver.

1. Хмарні балансувальники навантаження для зовнішніх Services:

    - надаються деякими хмарними провайдерами (наприклад, AWS ELB, Google Cloud Load Balancer)
    - створюються автоматично, коли Service у Kubernetes має тип `LoadBalancer`
    - зазвичай підтримують лише UDP/TCP
    - підтримка SCTP залежить від реалізації балансувальника навантаження хмарного провайдера
    - реалізація залежить від хмарного провайдера.

Зазвичай користувачам Kubernetes не потрібно турбуватися ні про що, крім перших двох типів. За правильне налаштування решти типів зазвичай відповідає адміністратор кластера.

## Запит на перенаправлення {#requesting-redirects}

Проксі замінили можливості перенаправлення. Перенаправлення визнано застарілими.
