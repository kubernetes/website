Kubernetes надає можливість _відокремлення конфігурації від коду_. Це поширена практика, яка узгоджується з принципами DevOps та з хмарною архітектурою.

Якщо у вас є {{< glossary_tooltip text="образ контейнера" term_id="image" >}}, який дозволяє окрему конфігурацію, ви можете розгортати **той самий** код застосунку в різних контекстах. Наприклад, ви можете запускати тести для зібраного образу, а потім запускати той самий образ у виробничому контексті. Це дає вам більше впевненості у вашому тестуванні порівняно з розгортанням застосунку одним способом для тестів та іншим у промисловій експлуатації.

Щоб дізнатися про налаштування інструмента командного рядка `kubectl`, прочитайте [налаштування доступу до кількох кластерів](/docs/tasks/access-application-cluster/configure-access-multiple-clusters/).

## API Kubernetes, повʼязані з конфігурацією {#api-kinds}

Kubernetes надає два основні види API, які ви можете використовувати для зберігання конфігурації, готової для завантаження та використання Podʼом (або іншим компонентом): [ConfigMap](/docs/concepts/configuration/configmap/) та [Secret](/docs/concepts/configuration/secret/).

Види API спеціального призначення [CertificateSigningRequest](/docs/reference/access-authn-authz/certificate-signing-requests/#certificate-signing-requests)
та [ClusterTrustBundle](/docs/reference/access-authn-authz/certificate-signing-requests/#cluster-trust-bundles) також містять дані конфігурації, що стосуються деяких конкретних випадків, таких як конфігурація TLS.

Усі ці механізми конфігурації, навіть для сертифікатів, розроблені так, щоб конфігурацію можна було повторно використовувати та спільно використовувати між кількома Podʼами. Зазвичай вам не потрібно записувати конфігурацію окремо для кожного Podʼа, і ви маєте проєктувати застосунки, де це можливо, так, щоб вони могли працювати зі спільною конфігурацією.

Щоб дізнатися про використання конфігурації у ваших застосунках, прочитайте про [інʼєкцію даних у застосунки](/docs/tasks/inject-data-application/).

### Secrets

Secret — це обʼєкт, який містить певний обсяг конфіденційних даних, таких як пароль, токен або ключ.

Secrets схожі на {{< glossary_tooltip text="ConfigMaps" term_id="configmap" >}}, але спеціально призначені для зберігання конфіденційних даних. Прочитайте сторінку про [Secrets](/docs/concepts/configuration/secret/), щоб дізнатися про переваги (та обмеження) щодо інформаційної безпеки та Secrets.

## Конфігурація через sidecar-контейнери або init-контейнери {#config-helper-overview}

Ви також можете використовувати {{< glossary_tooltip text="init-контейнер" term_id="init-container" >}} або {{< glossary_tooltip text="sidecar-контейнер" term_id="sidecar-container" >}}, щоб надати конфігурацію вашому робочому навантаженню.

Це корисно, якщо у вас уже є певний спосіб, поза межами Kubernetes, для зберігання конфігурації, ключів безпеки або іншої інформації, яку ваші контейнери мають використовувати і яка не повинна зберігатися в образах контейнерів.

### Sidecar-контейнер як помічник {#config-helper-sidecar}

_Помічник_ конфігурації _sidecar_ працює в тому самому Podʼі, що й контейнер застосунку, тому кожен Pod має власний sidecar. Типовий sidecar конфігурації отримує дані конфігурації через мережу Podʼа, а потім записує їх у {{< glossary_tooltip text="том" term_id="volume" >}}, який змонтовано в обидва контейнери.

Існує багато варіацій цього базового шаблону, у яких все ще є контейнер-помічник, що записує конфігурацію для споживання контейнером застосунку.

### Init-контейнер як помічник {#config-helper-init-container}

Podʼи можуть мати _init_-контейнери, які запускаються перед головним застосунком. На відміну від sidecar-контейнерів, init-контейнери завершуються до того, як запустяться головні контейнери Podʼа (з основним застосунком), тому конфігурація встановлюється тільки один раз.

У вас є два основні варіанти конфігурації за допомогою init-контейнерів:

#### Конфігурація через файлову систему {#init-container-shared-volume}

За цього варіанту init-контейнер отримує конфігурацію та записує її у файл або кілька файлів, зазвичай у локальний для Podʼа {{< glossary_tooltip text="том" term_id="volume" >}}.
