<!-- overview -->

_Аудит_ Kubernetes надає важливий для безпеки хронологічний набір записів, що документують послідовність дій у кластері. Кластер проводить аудит дій, ініційованих користувачами, застосунками, які використовують API Kubernetes, і самою панеллю управління.

Аудит дає змогу адміністраторам кластера відповісти на такі запитання:

- що сталося?
- коли це сталося?
- хто це ініціював?
- з чим це сталося?
- де це було помічено?
- звідки це було ініційовано?
- куди це прямувало?

<!-- body -->

Записи аудиту починають свій життєвий цикл у компоненті [kube-apiserver](/docs/reference/command-line-tools-reference/kube-apiserver/). Кожен запит на кожному етапі виконання генерує подію аудиту, яку потім попередньо обробляють відповідно до певної політики й записують у бекенд. Політика визначає, що записується, а бекенди зберігають записи. Поточні реалізації бекендів — файли логів і вебхуки.

Кожен запит можна записати з відповідним _етапом_ (stage). Визначено такі етапи:

- `RequestReceived` — етап для подій, що генеруються, щойно обробник аудиту отримує запит, і до того, як запит передано далі ланцюжком обробників.
- `ResponseStarted` — після надсилання заголовків відповіді, але до надсилання тіла відповіді. Цей етап генерується лише для тривалих запитів (наприклад, watch).
- `ResponseComplete` — тіло відповіді завершено, і більше жодних байтів не буде надіслано.
- `Panic` — події, що генеруються, коли сталася паніка.

{{< note >}}
Конфігурація [події аудиту](/docs/reference/config-api/apiserver-audit.v1/#audit-k8s-io-v1-Event) відрізняється від обʼєкта API [Event](/docs/reference/generated/kubernetes-api/{{< param "version" >}}/#event-v1-core).
{{< /note >}}

Можливість логування аудиту збільшує споживання памʼяті API-сервером, оскільки для кожного запиту зберігається певний контекст, потрібний для аудиту. Споживання памʼяті залежить від конфігурації логування аудиту.

## Політика аудиту {#audit-policy}

Політика аудиту визначає правила щодо того, які події слід записувати і які дані вони мають містити. Структуру обʼєкта політики аудиту визначено в [групі API `audit.k8s.io`](/docs/reference/config-api/apiserver-audit.v1/#audit-k8s-io-v1-Policy). Під час обробки подію по черзі порівнюють зі списком правил. Перше правило, що збіглося, встановлює _рівень аудиту_ події. Визначено такі рівні аудиту:

- `None` — не записувати події, які відповідають цьому правилу.
- `Metadata` — записувати події з метаданими (користувач, що надіслав запит, часова мітка, ресурс, дієслово тощо), але без тіла запиту чи відповіді.
- `Request` — записувати події з метаданими й тілом запиту, але без тіла відповіді. Це не стосується запитів, не повʼязаних з ресурсами.
- `RequestResponse` — записувати події з метаданими запиту, тілом запиту й тілом відповіді. Це не стосується запитів, не повʼязаних з ресурсами.

Файл з політикою можна передати `kube-apiserver` за допомогою прапорця `--audit-policy-file`. Якщо прапорець пропущено, жодні події не записуються. Зверніть увагу, що поле `rules` __обовʼязково__ має бути у файлі політики аудиту. Політика без правил (0) вважається неприпустимою.

Можна використати мінімальний файл політики аудиту, щоб записувати всі запити на рівні `Metadata`:


Докладніше про визначені поля дивіться в [довіднику конфігурації `Policy`](/docs/reference/config-api/apiserver-audit.v1/#audit-k8s-io-v1-Policy).

## Бекенди аудиту {#audit-backends}

Бекенди аудиту зберігають події аудиту в зовнішньому сховищі. Без додаткових налаштувань kube-apiserver надає два бекенди:

- бекенд логів, який записує події у файлову систему
- бекенд webhook, який надсилає події до зовнішнього HTTP API

У всіх випадках події аудиту мають структуру, визначену API Kubernetes у [групі API `audit.k8s.io`](/docs/reference/config-api/apiserver-audit.v1/#audit-k8s-io-v1-Event).

{{< note >}}
У разі патчів тіло запиту — це масив JSON з операціями патча, а не обʼєкт JSON з відповідним обʼєктом API Kubernetes. Наприклад, наведене нижче тіло запиту є коректним запитом на патч до `/apis/batch/v1/namespaces/some-namespace/jobs/some-job-name`:

```json
[
  {
    "op": "replace",
    "path": "/spec/parallelism",
    "value": 0
  },
  {
    "op": "remove",
    "path": "/spec/template/spec/containers/0/terminationMessagePolicy"
  }
]
```

{{< /note >}}

### Бекенд логів {#log-backend}

Бекенд логів записує події аудиту у файл у форматі [JSONlines](https://jsonlines.org/). Бекенд аудиту логів можна налаштувати за допомогою таких прапорців `kube-apiserver`:

- `--audit-log-path` вказує шлях до файлу логу, який бекенд логів використовує для запису подій аудиту. Якщо цей прапорець не вказано, бекенд логів вимкнено. `-` означає стандартний вивід
- `--audit-log-maxage` визначає максимальну кількість днів для зберігання старих файлів логів аудиту
- `--audit-log-maxbackup` визначає максимальну кількість файлів логів аудиту для зберігання
- `--audit-log-maxsize` визначає максимальний розмір файлу логу аудиту в мегабайтах, після якого виконується його ротація

Якщо панель управління вашого кластера запускає kube-apiserver як Pod, не забудьте змонтувати `hostPath` у розташування файлу політики й файлу логів, щоб записи аудиту зберігалися. Наприклад:

```yaml
  - --audit-policy-file=/etc/kubernetes/audit-policy.yaml
  - --audit-log-path=/var/log/kubernetes/audit/audit.log
```

потім змонтуйте томи:

```yaml
...
volumeMounts:
  - mountPath: /etc/kubernetes/audit-policy.yaml
    name: audit
    readOnly: true
  - mountPath: /var/log/kubernetes/audit/
    name: audit-log
    readOnly: false
```

і нарешті налаштуйте `hostPath`:

```yaml
...
volumes:
- name: audit
  hostPath:
    path: /etc/kubernetes/audit-policy.yaml
    type: File

- name: audit-log
  hostPath:
    path: /var/log/kubernetes/audit/
    type: DirectoryOrCreate
```

### Бекенд Webhook {#webhook-backend}

Бекенд аудиту webhook надсилає події аудиту до віддаленого веб-API, яке вважається різновидом API Kubernetes, зокрема щодо засобів автентифікації. Бекенд аудиту webhook можна налаштувати за допомогою таких прапорців kube-apiserver:

- `--audit-webhook-config-file` вказує шлях до файлу з конфігурацією webhook. Конфігурація webhook фактично є спеціалізованим [kubeconfig](/docs/tasks/access-application-cluster/configure-access-multiple-clusters).
- `--audit-webhook-initial-backoff` вказує час очікування після першого невдалого запиту перед повторною спробою. Подальші запити повторюються з експоненційною затримкою.

Файл конфігурації webhook використовує формат kubeconfig, щоб вказати віддалену адресу сервісу й облікові дані для підʼєднання до нього.

## Пакетна обробка подій {#batching}

Обидва бекенди, `log` і `webhook`, підтримують пакетну обробку. Нижче наведено перелік доступних прапорців для кожного бекенду. Стандартно пакетну обробку й тротлінг **увімкнено** для бекенду `webhook` і **вимкнено** для бекенду `log`.

- `--audit-webhook-mode` визначає стратегію буферизації. Можливі значення:
  - `batch` — буферизувати події й асинхронно обробляти їх пакетами. Це стандартний режим для бекенду `webhook`.
  - `blocking` — блокувати відповіді API-сервера під час обробки кожної окремої події.
  - `blocking-strict` — те саме, що й `blocking`, але якщо під час логування аудиту на етапі RequestReceived стається збій, увесь запит до kube-apiserver завершується невдачею.

Такі прапорці використовуються лише в режимі `batch`:

- `--audit-webhook-batch-buffer-size` визначає кількість подій для буферизації перед пакетною обробкою. Якщо швидкість надходження подій переповнює буфер, події відкидаються. Стандартне значення — 10000.
- `--audit-webhook-batch-max-size` визначає максимальну кількість подій в одному пакеті. Стандартне значення — 400.
- `--audit-webhook-batch-max-wait` визначає максимальний час очікування перед безумовною пакетною обробкою подій у черзі. Стандартне значення — 30 секунд.
- `--audit-webhook-batch-throttle-enable` визначає, чи увімкнено тротлінг пакетів. Стандартно тротлінг увімкнено.
- `--audit-webhook-batch-throttle-qps` визначає максимальну середню кількість пакетів, що генеруються за секунду. Стандартне значення — 10.
- `--audit-webhook-batch-throttle-burst` визначає максимальну кількість пакетів, згенерованих у той самий момент, якщо дозволений QPS раніше використовувався не повністю. Стандартне значення — 15.

- `--audit-log-mode` визначає стратегію буферизації. Можливі значення:
  - `batch` — буферизувати події й асинхронно обробляти їх пакетами. Пакетна обробка не рекомендується для бекенду `log`.
  - `blocking` — блокувати відповіді API-сервера під час обробки кожної окремої події. Це стандартний режим для бекенду `log`.

- `--audit-log-batch-buffer-size` визначає кількість подій для буферизації перед пакетною обробкою. Якщо швидкість надходження подій переповнює буфер, події відкидаються.

- `--audit-log-batch-max-wait` визначає максимальний час очікування перед безумовною пакетною обробкою подій у черзі.
- `--audit-log-batch-throttle-enable` визначає, чи увімкнено тротлінг пакетної обробки.

## Налаштування параметрів {#parameter-tuning}

Параметри слід задавати з урахуванням навантаження на API-сервер.

Наприклад, якщо kube-apiserver отримує 100 запитів щосекунди і кожен запит проходить аудит лише на етапах `ResponseStarted` і `ResponseComplete`, слід розраховувати на ≅200 подій аудиту щосекунди. Якщо в пакеті до 100 подій, рівень тротлінгу слід встановити щонайменше 2 запити на секунду. Якщо бекенду може знадобитися до 5 секунд для запису подій, розмір буфера слід встановити так, щоб він вміщував події за 5 секунд, тобто 10 пакетів або 1000 подій.

Однак у більшості випадків стандартних параметрів має бути достатньо, і вам не потрібно задавати їх вручну. Щоб відстежувати стан підсистеми аудиту, можна переглядати такі метрики Prometheus, які надає kube-apiserver, а також логи.

- Метрика `apiserver_audit_event_total` містить загальну кількість експортованих подій аудиту.
- Метрика `apiserver_audit_error_total` містить загальну кількість подій, відкинутих через помилку під час експорту.

### Обрізання записів логу {#truncate}

Обидва бекенди, логів і webhook, підтримують обмеження розміру подій, що записуються. Наприклад, ось перелік прапорців, доступних для бекенду логів:

- `audit-log-truncate-enabled` — чи ввімкнено обрізання подій і пакетів.
- `audit-log-truncate-max-batch-size` — максимальний розмір у байтах пакета, що надсилається до базового бекенду.
- `audit-log-truncate-max-event-size` — максимальний розмір у байтах події аудиту, що надсилається до базового бекенду.

Стандартно обрізання вимкнено і для `webhook`, і для `log`; щоб увімкнути цю можливість, адміністратор кластера має встановити `audit-log-truncate-enabled` або `audit-webhook-truncate-enabled`.
