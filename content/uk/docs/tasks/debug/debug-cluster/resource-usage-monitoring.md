<!-- overview -->

Щоб масштабувати застосунок і забезпечувати надійний сервіс, потрібно розуміти, як застосунок поводиться після розгортання. Ви можете аналізувати продуктивність застосунку в кластері Kubernetes, досліджуючи контейнери, [Podʼи](/docs/concepts/workloads/pods/), [сервіси](/docs/concepts/services-networking/service/) і загальні характеристики кластера. Kubernetes надає докладну інформацію про використання ресурсів застосунком на кожному з цих рівнів. Ця інформація дає змогу оцінити продуктивність застосунку й визначити, де можна усунути вузькі місця, щоб покращити загальну продуктивність.

<!-- body -->

У Kubernetes моніторинг застосунків не залежить від одного рішення для моніторингу. У нових кластерах для збирання статистики моніторингу можна використовувати конвеєри [метрик ресурсів](#resource-metrics-pipeline) або [повних метрик](#full-metrics-pipeline).

## Конвеєр метрик ресурсів {#resource-metrics-pipeline}

Конвеєр метрик ресурсів надає обмежений набір метрик, повʼязаних із компонентами кластера, такими як контролер [Горизонтального автомасштабування Podʼів](/docs/tasks/run-application/horizontal-pod-autoscale/), а також утиліта `kubectl top`. Ці метрики збирає легкий [metrics-server](https://github.com/kubernetes-sigs/metrics-server), що зберігає короткострокові дані в памʼяті, а доступні вони через API `metrics.k8s.io`.

metrics-server виявляє всі вузли в кластері й запитує в [kubelet](/docs/reference/command-line-tools-reference/kubelet/) кожного вузла дані про використання CPU і памʼяті. kubelet діє як міст між панеллю управління Kubernetes і вузлами, керуючи Podʼами й контейнерами, що працюють на машині. kubelet розкладає кожен Pod на його контейнери й отримує статистику використання окремих контейнерів від середовища виконання контейнерів через інтерфейс середовища виконання контейнерів. Якщо ви використовуєте середовище виконання контейнерів, яке реалізує контейнери за допомогою cgroups і просторів імен Linux, і воно не публікує статистику використання, kubelet може отримувати цю статистику безпосередньо (використовуючи код з [cAdvisor](https://github.com/google/cadvisor)). Незалежно від того, як надходить ця статистика, kubelet потім надає агреговану статистику використання ресурсів Podʼів через Resource Metrics API metrics-server. Цей API доступний за шляхом `/metrics/resource` на автентифікованому порту kubelet і порту лише для читання.

## Конвеєр повних метрик {#full-metrics-pipeline}

Конвеєр повних метрик дає доступ до ширшого набору метрик. Kubernetes може реагувати на ці метрики, автоматично масштабуючи або адаптуючи кластер відповідно до його поточного стану за допомогою таких механізмів, як Horizontal Pod Autoscaler. Конвеєр моніторингу отримує метрики від kubelet, а потім надає їх Kubernetes через адаптер, що реалізує API `custom.metrics.k8s.io` або `external.metrics.k8s.io`.

Kubernetes розроблено для роботи з [OpenMetrics](https://openmetrics.io/), одним із [проєктів CNCF Observability and Analysis - Monitoring](https://landscape.cncf.io/?group=projects-and-products&view-mode=card#observability-and-analysis--monitoring), який ґрунтується на [форматі експонування Prometheus](https://prometheus.io/docs/instrumenting/exposition_formats/) і обережно розширює його майже на 100% зворотно сумісним способом.

Якщо ви поглянете на [CNCF Landscape](https://landscape.cncf.io/?group=projects-and-products&view-mode=card#observability-and-analysis--monitoring), то побачите низку проєктів моніторингу, які можуть працювати з Kubernetes, _збираючи_ (scraping) дані метрик і використовуючи їх, щоб допомогти вам спостерігати за кластером. Вибір інструмента чи інструментів, що відповідають вашим потребам, залежить від вас. CNCF Landscape для спостережуваності й аналітики містить поєднання програмного забезпечення з відкритим кодом, платного програмного забезпечення як сервісу та інших комерційних продуктів.

Коли ви проєктуєте й реалізуєте конвеєр повних метрик, ви можете зробити ці дані моніторингу знову доступними для Kubernetes. Наприклад, HorizontalPodAutoscaler може використовувати оброблені метрики, щоб визначити, скільки Podʼів запускати для компонента вашого робочого навантаження.

Інтеграція конвеєра повних метрик у вашу реалізацію Kubernetes виходить за межі документації Kubernetes через дуже широкий спектр можливих рішень.

Вибір платформи моніторингу значною мірою залежить від ваших потреб, бюджету й технічних ресурсів. Kubernetes не рекомендує жодного конкретного конвеєра метрик; [доступно багато варіантів](https://landscape.cncf.io/?group=projects-and-products&view-mode=card#observability-and-analysis--monitoring). Ваша система моніторингу має підтримувати стандарт передавання метрик [OpenMetrics](https://openmetrics.io/), і її слід вибирати так, щоб вона найкраще вписувалася в загальний дизайн і розгортання вашої інфраструктурної платформи.
