Ця сторінка надає огляд кроків, які вам слід виконати для оновлення кластера Kubernetes.

Проєкт Kubernetes рекомендує оперативно оновлюватись до останніх випусків патчів, а також переконатися, що ви використовуєте підтримуваний мінорний випуск Kubernetes. Дотримання цих рекомендацій допоможе вам залишатися в безпеці.

Спосіб оновлення кластера залежить від того, як ви спочатку розгорнули його та від будь-яких наступних змін.

На високому рівні кроки, які ви виконуєте, такі:

- Оновити {{< glossary_tooltip text="панель управління" term_id="control-plane" >}}
- Оновити вузли в вашому кластері
- Оновити клієнти, такі як {{< glossary_tooltip text="kubectl" term_id="kubectl" >}}
- Відредагувати маніфести та інші ресурси на основі змін API, які супроводжують нову версію Kubernetes

## {{% heading "prerequisites" %}} {#before-you-begin}

Вам потрібен наявний кластер. Ця сторінка присвячена оновленню з Kubernetes {{< skew currentVersionAddMinor -1 >}} до Kubernetes {{< skew currentVersion >}}. Якщо ваш кластер зараз працює не на Kubernetes {{< skew currentVersionAddMinor -1 >}}, перегляньте документацію для версії Kubernetes, до якої ви плануєте оновитися.

{{< note >}}
На вузлах Linux kubelet стандартно підтримує лише cgroups v2. Для Kubernetes {{< skew currentVersion >}} параметр конфігурації kubelet `FailCgroupV1` стандартно має значення `true`.

Докладніше дивіться [документацію про застарівання cgroup v1 у Kubernetes](/docs/concepts/architecture/cgroups/#deprecation-of-cgroup-v1).
{{</ note >}}

## Підходи до оновлення {#upgrade-approaches}

### kubeadm {#upgrade-kubeadm}

Якщо ваш кластер був розгорнутий за допомогою інструменту `kubeadm`, дивіться [Оновлення кластерів kubeadm](/docs/tasks/administer-cluster/kubeadm/kubeadm-upgrade/) для докладної інформації щодо оновлення кластера.

Після того, як ви оновили кластер, не забудьте [встановити останню версію `kubectl`](/docs/tasks/tools/).

### Ручне розгортання {#manual-deployments}

{{< caution >}}
Ці кроки не враховують сторонніх розширень, таких як мережеві втулки та втулки сховищ.
{{< /caution >}}

Панель управління слід оновлювати вручну в такій послідовності:

- etcd (всі екземпляри)
- kube-apiserver (всі хости панелі управління)
- kube-controller-manager
- kube-scheduler
- cloud controller manager, якщо ви його використовуєте

На цьому етапі вам слід [встановити останню версію `kubectl`](/docs/tasks/tools/).

Для кожного вузла кластера виконайте [drain](/docs/tasks/administer-cluster/safely-drain-node/) цього вузла, а потім або замініть його новим вузлом, що використовує kubelet {{< skew currentVersion >}}, або оновіть kubelet на цьому вузлі й поверніть вузол до роботи.

{{< caution >}}
Виконання drain для вузлів перед оновленням kubelet гарантує, що Podʼи буде повторно допущено, а контейнери — перестворено, що може бути потрібно для усунення деяких проблем безпеки або інших важливих помилок.
{{</ caution >}}

### Інші розгортання {#upgrade-other}

Рекомендовані кроки з обслуговування дивіться в документації до вашого інструменту розгортання кластера.

## Завдання після оновлення {#post-upgrade-tasks}

### Перемикання версії API зберігання кластера {#switch-your-cluster-s-storage-api-version}

Обʼєкти, які серіалізуються в etcd для внутрішнього представлення кластером активних у ньому ресурсів Kubernetes, записуються з використанням певної версії API.

Коли підтримуване API змінюється, ці обʼєкти, можливо, доведеться перезаписати з використанням новішого API. Якщо цього не зробити, зрештою ресурси вже не зможе декодувати чи використовувати API-сервер Kubernetes.

Кожен уражений обʼєкт отримайте з використанням найновішої підтримуваної версії API, а потім запишіть його назад також з використанням найновішої підтримуваної версії API.

### Оновлення маніфестів {#update-manifests}

Оновлення до нової версії Kubernetes може надати нові API.

Ви можете використовувати команду `kubectl convert` для конвертації маніфестів між різними версіями API. Наприклад:

```shell
kubectl convert -f pod.yaml --output-version v1
```

Інструмент `kubectl` замінює вміст `pod.yaml` на маніфест, який встановлює `kind` на Pod (незмінно), але з оновленим `apiVersion`.

### Втулки пристроїв {#device-plugins}

Якщо ваш кластер використовує втулки пристроїв і вузол потребує оновлення до випуску Kubernetes з новішою версією API втулка пристроїв, втулки пристроїв повинні бути оновлені для підтримки обох версій перед оновленням вузла, щоб гарантувати, що виділення пристроїв продовжує успішно завершуватися під час оновлення.

Докладніше дивіться [Сумісність API](/docs/concepts/extend-kubernetes/compute-storage-net/device-plugins/#api-compatibility) і [Версії API менеджера пристроїв kubelet](/docs/reference/node/device-plugin-api-versions/).
