Оскільки хмарні провайдери розвиваються та випускають нові функції в іншому темпі порівняно з проєктом Kubernetes, абстрагування провайдер-залежного коду у бінарний файл `{{< glossary_tooltip text="cloud-controller-manager" term_id="cloud-controller-manager" >}}` дозволяє хмарним постачальникам розвиватися незалежно від основного коду Kubernetes.

`cloud-controller-manager` може бути повʼязаний з будь-яким хмарним провайдером, який відповідає вимогам [cloudprovider.Interface](https://github.com/kubernetes/cloud-provider/blob/master/cloud.go). Для забезпечення зворотної сумісності, [cloud-controller-manager](https://github.com/kubernetes/kubernetes/tree/master/cmd/cloud-controller-manager), що постачається у складі основного проєкту Kubernetes, використовує ті ж хмарні бібліотеки, що і `kube-controller-manager`. Очікується, що хмарні провайдери, які вже підтримуються в ядрі Kubernetes, використовуватимуть вбудований cloud-controller-manager, щоб перейти з ядра Kubernetes на зовнішню реалізацію.

## Адміністрування {#administration}

### Вимоги {#requirements}

Кожна хмара має свій власний набір вимог для запуску інтеграції зі своїм хмарним провайдером; вони не повинні суттєво відрізнятися від вимог до запуску `kube-controller-manager`. Як загальне правило, вам знадобиться:

* автентифікація/авторизація в хмарі: вашій хмарі може знадобитися токен або правила IAM, щоб дозволити доступ до її API
* автентифікація/авторизація в Kubernetes: cloud-controller-manager може потребувати налаштування правил RBAC для звʼязку з API-сервером Kubernetes
* висока доступність: як і для kube-controller-manager, вам може знадобитися налаштування високої доступності для cloud controller manager з використанням вибору лідера (стандартно увімкнено).

### Запуск cloud-controller-manager {#running-cloud-controller-manager}

Для успішного запуску cloud-controller-manager потрібні деякі зміни в конфігурації кластера.

* `kubelet` та `kube-controller-manager` повинні бути налаштовані відповідно до використання користувачем зовнішнього CCM. Якщо користувач має зовнішній CCM (а не внутрішні цикли контролерів хмари в Kubernetes Controller Manager), потрібно вказати `--cloud-provider=external`. Інакше цей прапорець вказувати не слід.

Майте на увазі, що налаштування кластера на використання cloud controller manager кількома способами змінить поведінку вашого кластера:

* Компоненти, що вказують `--cloud-provider=external`, додають taint `node.cloudprovider.kubernetes.io/uninitialized` з ефектом `NoSchedule` під час ініціалізації. Це позначає вузол як такий, що потребує другої ініціалізації зовнішнім контролером, перш ніж на нього можна буде планувати роботу. Зверніть увагу, що в разі недоступності cloud controller manager нові вузли у кластері залишаться непридатними для планування. Taint важливий, оскільки планувальнику може знадобитися специфічна для хмари інформація про вузли, наприклад їхній регіон чи тип (high cpu, gpu, high memory, spot instance тощо).
* інформація з хмари про вузли в кластері більше не отримуватиметься з локальних метаданих, натомість усі виклики API для отримання інформації про вузли проходитимуть через cloud controller manager. Це може означати, що ви можете обмежити доступ до API вашої хмари з kubelet для кращої безпеки. Для великих кластерів варто зважити, чи не досягатиме cloud controller manager обмежень частоти запитів (rate limits), оскільки тепер він відповідає майже за всі виклики API до вашої хмари зсередини кластера.

Cloud controller manager може реалізовувати:

* контролер вузлів — відповідає за оновлення вузлів Kubernetes за допомогою API хмари та видалення вузлів Kubernetes, які було видалено у вашій хмарі.
* контролер Service — відповідає за балансувальники навантаження у вашій хмарі для Service типу LoadBalancer.
* контролер маршрутів — відповідає за налаштування мережевих маршрутів у вашій хмарі
* будь-які інші функції, які ви хочете реалізувати, якщо використовуєте зовнішнього (out-of-tree) провайдера.

## Обмеження {#limitations}

Запуск cloud controller manager супроводжується кількома можливими обмеженнями. Хоча ці обмеження усуваються в наступних релізах, важливо знати про них для промислових робочих навантажень.

### Підтримка томів {#support-for-volumes}

Cloud controller manager не реалізує жодного з контролерів томів, що є в `kube-controller-manager`, оскільки інтеграція томів також потребує координації з kubelet. З розвитком CSI (container storage interface) і посиленням підтримки втулків flex volume до cloud controller manager буде додано необхідну підтримку, щоб хмари могли повністю інтегруватися з томами. Дізнайтеся більше про зовнішні втулки томів CSI [тут](https://github.com/kubernetes/features/issues/178).

### Масштабованість {#scalability}

Cloud-controller-manager запитує API вашого хмарного провайдера для отримання інформації про всі вузли. Для дуже великих кластерів зважте на можливі вузькі місця, як-от вимоги до ресурсів та обмеження частоти запитів до API.

### Курка чи яйце {#chicken-and-egg}

Метою проєкту cloud controller manager є відокремлення розробки хмарних функцій від основного проєкту Kubernetes. На жаль, багато аспектів проєкту Kubernetes спираються на припущення, що функції хмарного провайдера тісно інтегровані у проєкт. Внаслідок цього перехід на нову архітектуру може створити кілька ситуацій, коли робиться запит інформації від хмарного провайдера, але cloud controller manager може не мати змоги повернути цю інформацію без завершення початкового запиту.

Хорошим прикладом цього є функція TLS bootstrapping у kubelet. TLS bootstrapping передбачає, що kubelet може запитати у хмарного провайдера (або локальної служби метаданих) всі типи своїх адрес (приватні, публічні тощо), але cloud controller manager не може встановити типи адрес вузла, не будучи спершу ініціалізованим, а для цього kubelet потрібні TLS-сертифікати для звʼязку з API-сервером.

Під час розвитку цієї ініціативи будуть внесені зміни для розвʼязання цих питань у майбутніх релізах.
