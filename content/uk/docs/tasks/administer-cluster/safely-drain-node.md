<!-- overview -->

Ця сторінка показує, як безпечно очистити {{< glossary_tooltip text="вузол" term_id="node" >}}, за бажанням дотримуючись PodDisruptionBudget, який ви визначили.

## {{% heading "prerequisites" %}} {#before-you-begin}

Це завдання передбачає, що ви виконали такі попередні умови:

1. Вам не потрібно, щоб ваші застосунки були високодоступними під час очищення вузла, або
1. Ви прочитали про концепцію [PodDisruptionBudget](/docs/concepts/workloads/pods/disruptions/) та [налаштували PodDisruptionBudget](/docs/tasks/run-application/configure-pdb/) для застосунків, які їх потребують.

<!-- steps -->

## (Необовʼязково) Налаштування бюджету порушень {#configure-poddisruptionbudget}

Щоб забезпечити доступність ваших робочих навантажень під час технічного обслуговування, ви можете налаштувати [PodDisruptionBudget](/docs/concepts/workloads/pods/disruptions/).

Якщо доступність важлива для будь-яких застосунків, які запускаються або можуть запускатися на вузлах, які ви очищуєте, [спочатку налаштуйте PodDisruptionBudget](/docs/tasks/run-application/configure-pdb/), а потім продовжуйте виконувати цей посібник.

Рекомендується встановити для ваших PodDisruptionBudget [політику виселення несправних Podʼів](/docs/tasks/run-application/configure-pdb/#unhealthy-pod-eviction-policy) `AlwaysAllow`, щоб підтримати виселення застосунків з некоректною поведінкою під час очищення вузла. Стандартно очищення продовжується лише після того, як Podʼи застосунку стануть [справними](/docs/tasks/run-application/configure-pdb/#healthiness-of-a-pod).

## Використання `kubectl drain` для виведення вузла з обслуговування {#use-kubectl-drain-to-remove-a-node-from-service}

Ви можете використовувати `kubectl drain` для безпечного виселення всіх ваших Podʼів з вузла перед тим, як виконувати обслуговування вузла (наприклад, оновлення ядра, обслуговування обладнання тощо). Безпечні виселення дозволяють контейнерам Podʼа [коректно завершити роботу](/docs/concepts/workloads/pods/pod-lifecycle/#pod-termination) і враховують PodDisruptionBudget, які ви вказали.

{{< note >}}
Стандартно `kubectl drain` ігнорує певні системні Podʼи на вузлі, роботу яких не можна завершити примусово; докладніше див. документацію [kubectl drain](/docs/reference/generated/kubectl/kubectl-commands/#drain).
{{< /note >}}

Коли `kubectl drain` успішно завершується, це означає, що всі Podʼи (крім тих, які виключені, як описано в попередньому абзаці) безпечно виселені (з дотриманням бажаного пільгового періоду завершення роботи та визначеного вами PodDisruptionBudget). Після цього можна безпечно вимкнути вузол, вимкнувши його фізичну машину або, якщо він працює на хмарній платформі, видаливши його віртуальну машину.

{{< note >}}
Якщо будь-які нові Podʼи толерують taint `node.kubernetes.io/unschedulable`, то ці Podʼи можуть бути заплановані на вузол, який ви очистили. Уникайте толерування цього taint, крім як для DaemonSet.

Якщо ви або інший користувач API безпосередньо встановили поле [`nodeName`](/docs/concepts/scheduling-eviction/assign-pod-node/#nodename) для Podʼа (в обхід планувальника), то Pod буде привʼязаний до вказаного вузла і буде працювати там, навіть якщо ви його очистили та позначили як не придатний для планування.
{{< /note >}}

Спочатку визначте імʼя вузла, який ви хочете очистити. Ви можете перелічити всі вузли у своєму кластері за допомогою

```shell
kubectl get nodes
```

Далі скажіть Kubernetes очистити вузол:

```shell
kubectl drain --ignore-daemonsets <node name>
```

Якщо є Podʼи, керовані DaemonSet, вам потрібно вказати `--ignore-daemonsets` в `kubectl`, щоб успішно очистити вузол. Підкоманда `kubectl drain` сама по собі насправді не очищає вузол від його Podʼів DaemonSet: контролер DaemonSet (частина панелі управління) негайно замінює відсутні Podʼи новими еквівалентними Podʼами. Контролер DaemonSet також створює Podʼи, які ігнорують taint, що перешкоджають плануванню, що дозволяє новим Podʼам запускатися на вузлі, який ви очищуєте.

Podʼи DaemonSet, як правило, є локальними для вузла сервісами, такими як мережа, зберігання даних або збір журналів, які мають залишатися на вузлі стільки, скільки сам вузол працює. Оскільки контролер DaemonSet закріплює кожен Pod за конкретним вузлом і ігнорує taint, що перешкоджає плануванню, виселення цих Podʼів лише призведе до того, що їх буде повторно створено на тому самому вузлі. `--ignore-daemonsets` пропускає їх, щоб очищення могло завершитися; Podʼи продовжують працювати, поки ви виконуєте обслуговування, і видаляються разом із вузлом, коли його вилучають із кластера.

Після того, як команда завершиться (без помилки), ви можете вимкнути вузол (або, що рівнозначно, якщо ви працюєте на хмарній платформі, видалити віртуальну машину, на якій працює вузол). Якщо ви залишите вузол у кластері під час операції обслуговування, після цього вам потрібно виконати

```shell
kubectl uncordon <node name>
```

щоб повідомити Kubernetes, що він може відновити планування нових Podʼів на цей вузол.

## Очищення кількох вузлів паралельно {#draining-multiple-nodes-in-parallel}

Команду `kubectl drain` слід використовувати тільки для одного вузла за раз. Однак ви можете запускати кілька команд `kubectl drain` для різних вузлів паралельно, в різних терміналах або у фоні. Кілька команд очищення, які працюють одночасно, все одно дотримуються PodDisruptionBudget, який ви вказуєте.

Наприклад, якщо у вас є StatefulSet із трьома репліками та ви встановили для нього PodDisruptionBudget із `minAvailable: 2`, `kubectl drain` виселяє Pod зі StatefulSet лише тоді, коли всі три Podʼи-репліки [справні](/docs/tasks/run-application/configure-pdb/#healthiness-of-a-pod); якщо після цього ви запустите кілька команд очищення паралельно, Kubernetes дотримується PodDisruptionBudget та гарантує, що в будь-який момент часу недоступний лише один Pod (обчислюється як `replicas - minAvailable`). Будь-які очищення, через які кількість [справних](/docs/tasks/run-application/configure-pdb/#healthiness-of-a-pod) реплік опустилася б нижче вказаного бюджету, блокуються.

## API Eviction {#eviction-api}

Якщо ви не бажаєте використовувати [kubectl drain](/docs/reference/generated/kubectl/kubectl-commands/#drain) (наприклад, щоб уникнути виклику зовнішньої команди або отримати точніший контроль над процесом виселення Podʼів), ви також можете програмно ініціювати виселення за допомогою API Eviction.

Для отримання додаткової інформації див. [Виселення, ініційоване API](/docs/concepts/scheduling-eviction/api-eviction/).
