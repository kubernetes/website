## Контроль доступу до API Kubernetes {#controlling-access-to-the-kubernetes-api}

Оскільки Kubernetes повністю заснований на API, контроль та обмеження того, хто може отримати доступ до кластера та які дії дозволено виконувати, є першою лінією захисту.

### Використання Transport Layer Security (TLS) для всього трафіку API {#use-transport-layer-security-tls-for-all-api-traffic}

Kubernetes очікує, що всі комунікації API в кластері стандартно шифруються за допомогою TLS, і більшість методів встановлення дозволяють створювати необхідні сертифікати та розподіляти їх між компонентами кластера. Зверніть увагу, що деякі компоненти та методи встановлення можуть вмикати локальні порти через HTTP, і адміністраторам варто ознайомитися з налаштуваннями кожного компонента, щоб виявити потенційно незахищений трафік.

### Автентифікація API {#api-authentication}

Під час встановлення кластера виберіть механізм автентифікації для API-серверів, який відповідає типовим сценаріям доступу. Наприклад, невеликі однокористувацькі кластери можуть використовувати простий підхід із сертифікатами або статичними токенами Bearer. Більші кластери можуть інтегрувати наявний сервер OIDC або LDAP, який дозволяє розподіляти користувачів на групи.

Всі клієнти API повинні бути автентифіковані, навіть ті, що є частиною інфраструктури, такі як вузли, проксі, планувальник та втулки томів. Зазвичай ці клієнти є [службовими обліковими записами](/docs/reference/access-authn-authz/service-accounts-admin/) або використовують клієнтські сертифікати x509, і вони створюються автоматично під час запуску кластера або налаштовуються як частина встановлення кластера.

Для отримання додаткової інформації звертайтеся до [документації з автентифікації](/docs/reference/access-authn-authz/authentication/).

### Авторизація API {#api-authorization}

Після автентифікації кожен виклик API також повинен пройти перевірку авторизації. Kubernetes має вбудований компонент [керування доступом на основі ролей (RBAC)](/docs/reference/access-authn-authz/rbac/), який зіставляє користувача або групу з набором дозволів, обʼєднаних у ролі. Ці дозволи поєднують дієслова (get, create, delete) з ресурсами (pods, services, nodes) і можуть мати область дії простору імен або кластера. Надається набір готових ролей, які забезпечують розумне стандартне розділення відповідальності залежно від того, які дії може виконувати клієнт. Рекомендується використовувати авторизатори [Node](/docs/reference/access-authn-authz/node/) та [RBAC](/docs/reference/access-authn-authz/rbac/) разом із втулком допуску [NodeRestriction](/docs/reference/access-authn-authz/admission-controllers/#noderestriction).

Так само як і з автентифікацією, для менших кластерів можуть бути відповідні прості та загальні ролі, але зі збільшенням кількості користувачів, які взаємодіють з кластером, може знадобитися розділити команди на окремі {{< glossary_tooltip text="простори імен" term_id="namespace" >}} з більш обмеженими ролями.

Щодо авторизації важливо розуміти, як оновлення одного обʼєкта може спричинити дії в інших місцях. Наприклад, користувач може не мати змоги створювати Podʼи безпосередньо, але якщо дозволити йому створювати Deployment, який створює Podʼи від його імені, він зможе створювати ці Podʼи опосередковано. Так само видалення вузла з API призведе до завершення роботи Podʼів, запланованих на цей вузол, і їх повторного створення на інших вузлах. Готові ролі є компромісом між гнучкістю та поширеними випадками використання, але більш обмежені ролі слід уважно переглядати, щоб запобігти випадковому підвищенню привілеїв. Якщо готові ролі не відповідають вашим потребам, ви можете створити ролі, специфічні для вашого випадку використання.

Для отримання додаткової інформації звертайтеся до [розділу довідки з авторизації](/docs/reference/access-authn-authz/authorization/).

Якщо ваш кластер використовує [Динамічний розподіл ресурсів (DRA)](/docs/concepts/resource-management/dynamic-resource-allocation/), перегляньте авторизацію синтетичних субресурсів DRA (`resourceclaims/binding` та `resourceclaims/driver`) і надайте кожному компоненту лише мінімально необхідні дієслова. Докладніше див. [Посібник зі зміцнення безпеки — динамічний розподіл ресурсів](/docs/concepts/security/hardening-guide/dynamic-resource-allocation/) та [Посилення безпеки динамічного розподілу ресурсів у вашому кластері](/docs/tasks/administer-cluster/hardening-dra/).

## Контроль доступу до Kubelet {#controlling-access-to-the-kubelet}

Kubelet надає HTTPS-точки доступу, які дають потужний контроль над вузлом та контейнерами. Стандартно Kubelet дозволяє неавтентифікований доступ до цього API.

Промислові кластери повинні вмикати автентифікацію та авторизацію Kubelet.

Для отримання додаткової інформації звертайтеся до [розділу довідки з автентифікації/авторизації Kubelet](/docs/reference/access-authn-authz/kubelet-authn-authz/).

## Керування можливостями робочого навантаження або користувача під час виконання {#controlling-the-capabilities-of-a-workload-or-user-at-runtime}

Авторизація в Kubernetes навмисно має високий рівень і зосереджена на грубих діях з ресурсами. Потужніші засоби керування існують у вигляді **політик**, що обмежують, залежно від випадку використання, як ці обʼєкти діють на кластер, на себе та на інші ресурси.

### Обмеження використання ресурсів у кластері {#limiting-resource-usage-on-a-cluster}

[Квоти ресурсів](/docs/concepts/policy/resource-quotas/) обмежують кількість або місткість ресурсів, наданих простору імен. Найчастіше це використовується для обмеження обсягу CPU, памʼяті або постійного дискового простору, який може виділити простір імен, але також може контролювати кількість Podʼів, Service або томів, що існують у кожному просторі імен.

[Діапазони обмежень](/docs/tasks/administer-cluster/manage-resources/memory-default-namespace/) обмежують максимальний або мінімальний розмір деяких з вищезазначених ресурсів, щоб користувачі не могли запитувати надмірно високі або низькі значення для часто резервованих ресурсів, таких як памʼять, або щоб надавати стандартні обмеження, коли їх не вказано.

### Керування привілеями, з якими працюють контейнери {#controlling-what-privileges-containers-run-with}

В описі Podʼа міститься [контекст безпеки](/docs/tasks/configure-pod-container/security-context/), який дозволяє запитувати доступ до виконання від імені конкретного користувача Linux на вузлі (наприклад, root), доступ до виконання з підвищеними привілеями або доступ до мережі хосту та інші елементи керування, які інакше дозволили б йому працювати без обмежень на вузлі хосту.

Ви можете налаштувати [Pod Security Admission](/docs/concepts/security/pod-security-admission/), щоб забезпечити використання певного [стандарту безпеки Pod](/docs/concepts/security/pod-security-standards/) у {{< glossary_tooltip text="просторі імен" term_id="namespace" >}} або виявляти порушення.

Загалом, більшість робочих навантажень застосунків потребують обмеженого доступу до ресурсів хосту, щоб вони могли успішно працювати як процес root (uid 0) без доступу до інформації про хост. Однак, враховуючи привілеї, повʼязані з користувачем root, слід робити контейнери застосунків такими, що не вимагають прав root для виконання. Так само адміністратори, які бажають запобігти втечі клієнтських застосунків з їхніх контейнерів, повинні застосувати стандарт безпеки Pod **Baseline** або **Restricted**.

### Запобігання завантаженню небажаних модулів ядра контейнерами {#preventing-containers-from-loading-unwanted-kernel-modules}

Ядро Linux автоматично завантажує модулі ядра з диска за потреби в певних обставинах, наприклад, коли підʼєднано пристрій або змонтовано файлову систему. Особливо актуально для Kubernetes те, що навіть непривілейовані процеси можуть спричинити завантаження певних модулів ядра, повʼязаних з мережевими протоколами, просто створивши сокет відповідного типу. Це може дозволити зловмиснику використати вразливість у модулі ядра, який, як вважав адміністратор, не використовується.

Щоб запобігти автоматичному завантаженню конкретних модулів, ви можете деінсталювати їх з вузла або додати правила для їх блокування. У більшості дистрибутивів Linux ви можете це зробити, створивши файл, наприклад, `/etc/modprobe.d/kubernetes-blacklist.conf`, з таким вмістом:

```
# DCCP майже не потрібен, має кілька серйозних вразливостей
# і не знаходиться у доброму стані обслуговування.
blacklist dccp

# SCTP не використовується в більшості кластерів Kubernetes, і також мав
# вразливості в минулому.
blacklist sctp
```

Для більш загального блокування завантаження модулів можна використовувати Linux Security Module (наприклад, SELinux), щоб повністю відмовити контейнерам у дозволі `module_request`, не даючи ядру завантажувати модулі для контейнерів за будь-яких обставин. (Podʼи все ще зможуть використовувати модулі, які були завантажені вручну, або модулі, які ядро завантажило від імені якогось більш привілейованого процесу.)

### Обмеження доступу до мережі {#restricting-network-access}

[Мережеві політики](/docs/tasks/administer-cluster/declare-network-policy/) для простору імен дозволяють авторам застосунків обмежувати, які Podʼи в інших просторах імен можуть отримувати доступ до Podʼів і портів у їхніх просторах імен. Багато з підтримуваних [постачальників мережі Kubernetes](/docs/concepts/cluster-administration/networking/) зараз враховують мережеві політики.

Також можна використовувати квоти та діапазони обмежень, щоб контролювати, чи можуть користувачі запитувати порти вузлів або Service з балансуванням навантаження, що в багатьох кластерах визначає, чи будуть застосунки цих користувачів видимі поза кластером.

Можуть бути доступні додаткові засоби захисту, які керують мережевими правилами на рівні втулка або середовища, як-от брандмауери на рівні вузлів, фізичне розділення вузлів кластера для запобігання перехресному звʼязку або розширені мережеві політики.

### Обмеження доступу до API метаданих хмари {#restricting-cloud-metadata-api-access}

Хмарні платформи (AWS, Azure, GCE тощо) часто надають екземплярам локальний доступ до служб метаданих. Стандартно ці API доступні Podʼам, що працюють на екземплярі, і можуть містити хмарні облікові дані для цього вузла або дані надання, такі як облікові дані kubelet. Ці облікові дані можуть бути використані для підвищення привілеїв усередині кластера або в інших хмарних службах того самого облікового запису.

Під час запуску Kubernetes на хмарній платформі обмежуйте дозволи, надані обліковим даним екземплярів, використовуйте [мережеві політики](/docs/tasks/administer-cluster/declare-network-policy/) для обмеження доступу Podʼів до API метаданих та уникайте використання даних надання для передачі секретів.

### Керування тим, до яких вузлів мають доступ Podʼи {#controlling-which-nodes-pods-may-access}

Стандартно немає обмежень щодо того, на яких вузлах може запускатися Pod. Kubernetes пропонує [широкий набір політик для керування розміщенням Podʼів на вузлах](/docs/concepts/scheduling-eviction/assign-pod-node/) та [розміщення й виселення Podʼів на основі taint](/docs/concepts/scheduling-eviction/taint-and-toleration/), доступні для кінцевих користувачів. Для багатьох кластерів використання цих політик для розділення робочих навантажень може бути домовленістю, якої автори дотримуються або яку впроваджують за допомогою інструментів.

Адміністратор може використовувати бета-втулок допуску `PodNodeSelector`, щоб примусово встановлювати для Podʼів у просторі імен стандартний селектор вузлів або вимагати певний селектор вузлів, і якщо кінцеві користувачі не можуть змінювати простори імен, це може суттєво обмежити розміщення всіх Podʼів у певному робочому навантаженні.

## Захист компонентів кластера від компрометації {#protecting-cluster-components-from-compromise}

У цьому розділі описані деякі загальні шаблони для захисту кластерів від компрометації.

### Обмеження доступу до etcd {#restrict-access-to-etcd}

Доступ на запис до бекенду etcd для API еквівалентний отриманню root-доступу до всього кластера, а доступ на читання може бути використаний для досить швидкого підвищення привілеїв. Адміністратори повинні завжди використовувати надійні облікові дані від API-серверів до сервера etcd, наприклад взаємну автентифікацію за допомогою клієнтських сертифікатів TLS, і часто рекомендується ізолювати сервери etcd за брандмауером, доступ до якого мають лише API-сервери.

{{< caution >}}
Надання іншим компонентам у кластері доступу до головного екземпляра etcd з правами читання або запису до всього простору ключів еквівалентне наданню доступу cluster-admin. Наполегливо рекомендується використовувати окремі екземпляри etcd для компонентів, які не є головними, або використовувати ACL etcd для обмеження доступу на читання та запис до підмножини простору ключів.
{{< /caution >}}

### Увімкнення логування аудиту {#enable-audit-logging}

[Audit logger](/docs/tasks/debug/debug-cluster/audit/) є бета-функцією, яка записує дії, виконані API, для подальшого аналізу в разі компрометації. Рекомендується увімкнути логування аудиту та архівувати файл аудиту на захищеному сервері.

### Обмеження доступу до альфа- або бета-функцій {#restrict-access-to-alpha-or-beta-features}

Альфа- і бета-функції Kubernetes перебувають в активній розробці і можуть мати обмеження або помилки, які призводять до вразливостей безпеки. Завжди оцінюйте цінність, яку можуть надати альфа- або бета-функції, у порівнянні з можливим ризиком для вашої безпеки. У разі сумнівів вимикайте функції, які ви не використовуєте.

### Часто змінюйте облікові дані інфраструктури {#rotate-infrastructure-credentials-frequently}

Чим коротший термін дії Secret або облікових даних, тим складніше зловмиснику використати ці облікові дані. Встановлюйте короткі терміни дії сертифікатів та автоматизуйте їх ротацію. Використовуйте постачальника автентифікації, який може контролювати, як довго видані токени залишаються дійсними, і використовуйте короткі терміни дії, де це можливо. Якщо ви використовуєте токени службових облікових записів у зовнішніх інтеграціях, плануйте часту ротацію цих токенів. Наприклад, щойно завершиться фаза початкового завантаження, токен початкового завантаження (bootstrap token), використаний для налаштування вузлів, слід відкликати або скасувати його авторизацію.

### Перегляд інтеграцій сторонніх розробників перед їх увімкненням {#review-third-party-integrations-before-enabling-them}

Багато сторонніх інтеграцій з Kubernetes можуть змінювати профіль безпеки вашого кластера. Під час увімкнення інтеграції завжди переглядайте дозволи, які запитує розширення, перш ніж надати йому доступ. Наприклад, багато інтеграцій безпеки можуть запитувати доступ до перегляду всіх секретів у вашому кластері, що фактично робить цей компонент адміністратором кластера. У разі сумнівів обмежте роботу інтеграції одним простором імен, якщо це можливо.

Компоненти, які створюють Podʼи, також можуть бути несподівано потужними, якщо вони можуть робити це всередині просторів імен, таких як простір імен `kube-system`, оскільки ці Podʼи можуть отримати доступ до секретів службових облікових записів або працювати з підвищеними дозволами, якщо цим службовим обліковим записам надано доступ до надто дозвільних [PodSecurityPolicies](/docs/concepts/security/pod-security-policy/).

Якщо ви використовуєте [Pod Security admission](/docs/concepts/security/pod-security-admission/) та дозволяєте будь-якому компоненту створювати Podʼи в просторі імен, що дозволяє привілейовані Podʼи, ці Podʼи можуть втекти зі своїх контейнерів і використати цей розширений доступ для підвищення своїх привілеїв.

Ви не повинні дозволяти ненадійним компонентам створювати Podʼи в будь-якому системному просторі імен (тих, назви яких починаються з `kube-`) або в будь-якому просторі імен, де такий доступ відкриває можливість підвищення привілеїв.

### Шифрування секретів у стані спокою {#encrypt-secrets-at-rest}

Загалом база даних etcd міститиме будь-яку інформацію, доступну через API Kubernetes, і може надати зловмиснику значне уявлення про стан вашого кластера. Завжди шифруйте свої резервні копії за допомогою добре перевіреного рішення для резервного копіювання та шифрування, і розгляньте можливість використання повного шифрування диска, де це можливо.

Kubernetes підтримує необовʼязкове [шифрування у стані спокою](/docs/tasks/administer-cluster/encrypt-data/) для інформації в API Kubernetes. Це дозволяє гарантувати, що коли Kubernetes зберігає дані обʼєктів (наприклад, обʼєктів `Secret` або `ConfigMap`), API-сервер записує зашифроване представлення обʼєкта. Таке шифрування означає, що навіть той, хто має доступ до резервних копій даних etcd, не може переглянути вміст цих обʼєктів. У Kubernetes {{< skew currentVersion >}} ви також можете шифрувати власні ресурси; шифрування у стані спокою для API розширень, визначених через CustomResourceDefinitions, було додано в Kubernetes у випуску v1.26.
