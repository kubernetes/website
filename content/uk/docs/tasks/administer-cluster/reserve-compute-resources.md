<!-- overview -->

Вузли Kubernetes можуть бути заплановані на `Capacity`. Podʼи стандартно можуть використовувати всю доступну місткість на вузлі. Це проблема, оскільки на вузлах зазвичай працює досить багато системних служб, які забезпечують роботу операційної системи та самого Kubernetes. Якщо не виділити ресурси для цих системних служб, Podʼи та системні служби конкурують за ресурси, що призводить до проблем з вичерпанням ресурсів на вузлі.

`kubelet` надає можливість під назвою 'Node Allocatable', яка допомагає резервувати обчислювальні ресурси для системних служб. Kubernetes рекомендує адміністраторам кластера налаштовувати 'Node Allocatable' на основі щільності робочого навантаження на кожному вузлі.

## Node Allocatable

![місткість вузла](/images/docs/node-capacity.svg)

Allocatable на вузлі Kubernetes визначається як обсяг обчислювальних ресурсів, які доступні для Podʼів. Планувальник не допускає надмірного розподілу 'Allocatable'. Наразі підтримуються 'CPU', 'memory' та 'ephemeral-storage'.

Node Allocatable доступний як частина обʼєкта `v1.Node` в API та як частина `kubectl describe node` в CLI.

Ресурси можуть бути зарезервовані для двох категорій системних служб в `kubelet`.

### Увімкнення QoS та cgroups на рівні Podʼів {#enabling-qos-and-pod-level-cgroups}

Щоб належним чином застосовувати обмеження node allocatable на вузлі, потрібно ввімкнути нову ієрархію cgroup за допомогою параметра `cgroupsPerQOS`. Цей параметр стандартно ввімкнений. Коли його ввімкнено, `kubelet` розміщуватиме всі Podʼи кінцевих користувачів в ієрархії cgroup, якою керує `kubelet`.

### Налаштування драйвера cgroup {#configuring-a-cgroup-driver}

`kubelet` підтримує маніпулювання ієрархією cgroup на хості за допомогою драйвера cgroup. Драйвер налаштовується за допомогою параметра `cgroupDriver`.

Підтримуються такі значення:

* `cgroupfs` — це стандартний драйвер, який виконує пряме маніпулювання файловою системою cgroup на хості для керування пісочницями cgroup.
* `systemd` — це альтернативний драйвер, який управляє пісочницями cgroup за допомогою тимчасових сегментів для ресурсів, які підтримуються цією системою ініціалізації.

Залежно від конфігурації відповідного середовища виконання контейнерів, операторам може знадобитися вибрати певний драйвер cgroup, щоб забезпечити належну роботу системи. Наприклад, якщо оператори використовують драйвер cgroup `systemd`, наданий середовищем виконання `containerd`, `kubelet` повинен бути налаштований на використання драйвера cgroup `systemd`.

### Kube Reserved

* **KubeletConfiguration Setting**: `kubeReserved: {}`. Приклад: `{cpu: 100m, memory: 100Mi, ephemeral-storage: 1Gi, pid=1000}`
* **KubeletConfiguration Setting**: `kubeReservedCgroup: ""`

`kubeReserved` призначено для резервування ресурсів для системних демонів Kubernetes, таких як `kubelet`, `container runtime` тощо. Він не призначений для резервування ресурсів для системних служб, які запускаються як Podʼи. `kubeReserved` зазвичай залежить від `pod density` на вузлах.

Крім `cpu`, `memory` та `ephemeral-storage`, можна вказати `pid`, щоб зарезервувати вказану кількість ідентифікаторів процесів для системних демонів Kubernetes.

Для необовʼязкового застосування `kubeReserved` до системних демонів Kubernetes вкажіть батьківську контрольну групу для демонів kube як значення параметра `kubeReservedCgroup` та [додайте `kube-reserved` до `enforceNodeAllocatable`](#enforcing-node-allocatable).

Рекомендується розміщувати системні демони Kubernetes у контрольній групі верхнього рівня (наприклад, `runtime.slice` на машинах з systemd). В ідеалі кожен системний демон має працювати у власній дочірній контрольній групі. Докладнішу інформацію про рекомендовану ієрархію контрольних груп дивіться у [пропозиції дизайну](https://git.k8s.io/design-proposals-archive/node/node-allocatable.md#recommended-cgroups-setup).

Зверніть увагу, що Kubelet **не створює** `kubeReservedCgroup`, якщо вона не існує. Kubelet не запуститься, якщо вказано недійсну контрольну групу. З драйвером cgroup `systemd` вам слід дотримуватися певного шаблону для імені контрольної групи, яку ви визначаєте: імʼя повинно бути значенням, яке ви встановлюєте для `kubeReservedCgroup`, з додаванням `.slice`.

### System Reserved

* **KubeletConfiguration Setting**: `systemReserved: {}`. Приклад: `{cpu: 100m, memory: 100Mi, ephemeral-storage: 1Gi, pid=1000}`
* **KubeletConfiguration Setting**: `systemReservedCgroup: ""`

`systemReserved` призначено для резервування ресурсів для системних служб операційної системи, таких як `sshd`, `udev` тощо. `systemReserved` повинен резервувати `memory` також для `kernel`, оскільки памʼять `kernel` наразі не враховується для Podʼів у Kubernetes. Рекомендується також резервувати ресурси для сеансів входу користувачів (`user.slice` у світі systemd).

Крім `cpu`, `memory` та `ephemeral-storage`, можна вказати `pid`, щоб зарезервувати вказану кількість ідентифікаторів процесів для системних служб операційної системи.

Для необовʼязкового застосування `systemReserved` до системних служб вкажіть батьківську контрольну групу для системних служб операційної системи як значення параметра `systemReservedCgroup` та [додайте `system-reserved` до `enforceNodeAllocatable`](#enforcing-node-allocatable).

Рекомендується розміщувати системні служби операційної системи у контрольній групі верхнього рівня (наприклад, `system.slice` на машинах з systemd).

Зверніть увагу, що `kubelet` **не створює** `systemReservedCgroup`, якщо вона не існує. `kubelet` не запуститься, якщо вказано недійсну контрольну групу. З драйвером cgroup `systemd` вам слід дотримуватися певного шаблону для імені контрольної групи, яку ви визначаєте: імʼя повинно бути значенням, яке ви встановлюєте для `systemReservedCgroup`, з додаванням `.slice`.

### Явно зарезервований список CPU {#explicitly-reserved-cpu-list}

{{< feature-state for_k8s_version="v1.17" state="stable" >}}

**KubeletConfiguration Setting**: `reservedSystemCPUs:`. Приклад: `0-3`

`reservedSystemCPUs` призначено для визначення явного набору CPU для системних служб операційної системи та системних служб Kubernetes. `reservedSystemCPUs` призначений для систем, які не мають наміру визначати окремі контрольні групи верхнього рівня для системних служб операційної системи та системних служб Kubernetes щодо ресурсу cpuset. Ви не можете використовувати `reservedSystemCPUs` разом з `kubeReservedCgroup` або `systemReservedCgroup`. Коли ви встановлюєте `reservedSystemCPUs`, кількість його CPU замінює кількість CPU, вказану в `kubeReserved` та `systemReserved`, для резервування ресурсів kubelet.

Цей параметр спеціально розроблений для випадків використання в телекомунікаціях/NFV, де неконтрольовані переривання/таймери можуть впливати на продуктивність робочого навантаження. Ви можете використовувати цей параметр для визначення явного набору cpuset для системних служб і служб Kubernetes, а також для переривань/таймерів, щоб решта CPU у системі могли використовуватися виключно для робочих навантажень, з меншим впливом неконтрольованих переривань/таймерів. Щоб перенести системні служби, служби Kubernetes та переривання/таймери до явного набору cpuset, визначеного цим параметром, слід використовувати інші механізми поза Kubernetes. Наприклад: у CentOS це можна зробити за допомогою набору інструментів tuned.

### Пороги виселення {#eviction-thresholds}

**KubeletConfiguration Setting**: `evictionHard: {memory.available: "100Mi", nodefs.available: "10%", nodefs.inodesFree: "5%", imagefs.available: "15%"}`. Наприклад: `{memory.available: "<500Mi"}`

Нестача памʼяті на рівні вузла призводить до System OOMs, що впливає на весь вузол та всі Podʼи, що працюють на ньому. Вузли можуть тимчасово вийти з ладу, поки памʼять не буде звільнено. Щоб уникнути (або зменшити ймовірність) System OOMs, kubelet надає [керування нестачею ресурсів](/docs/concepts/scheduling-eviction/node-pressure-eviction/). Виселення підтримується тільки для `memory` та `ephemeral-storage`. Резервуючи певний обсяг памʼяті за допомогою параметра `evictionHard`, `kubelet` намагається виселити Podʼи, коли доступна памʼять на вузлі падає нижче зарезервованого значення. Гіпотетично, якби на вузлі не було системних служб, Podʼи не могли б використовувати більше, ніж `capacity - eviction-hard`. З цієї причини ресурси, зарезервовані для виселень, недоступні для Podʼів.

### Примусове застосування Node Allocatable {#enforcing-node-allocatable}

**KubeletConfiguration Setting**: `enforceNodeAllocatable: [pods]`. Наприклад: `[pods,system-reserved,kube-reserved]`

Планувальник розглядає 'Allocatable' як доступну `capacity` для Podʼів.

`kubelet` стандартно забезпечує дотримання 'Allocatable' для всіх Podʼів. Це забезпечується виселенням Podʼів, коли загальне використання ресурсів усіма Podʼами перевищує 'Allocatable'. Додаткові відомості про політику виселення можна знайти на сторінці [Виселення внаслідок тиску на вузол](/docs/concepts/scheduling-eviction/node-pressure-eviction/). Цим керують, вказуючи значення `pods` для параметра KubeletConfiguration `enforceNodeAllocatable`.

За бажанням `kubelet` можна налаштувати на примусове застосування `kubeReserved` та `systemReserved`, вказавши значення `kube-reserved` та `system-reserved` в тому самому параметрі. Крім того, можна примусово застосовувати лише ресурси, що піддаються стисненню, вказавши `kube-reserved-compressible` та `system-reserved-compressible`. Зверніть увагу, що для примусового застосування `kubeReserved` або `systemReserved` необхідно вказати відповідно `kubeReservedCgroup` або `systemReservedCgroup`.

## Загальні настанови {#general-guidelines}

Очікується, що системні служби будуть оброблятися аналогічно [гарантованим Podʼам](/docs/tasks/configure-pod-container/quality-service-pod/#create-a-pod-that-gets-assigned-a-qos-class-of-guaranteed). Системні служби можуть розширюватися в межах своїх обмежувальних контрольних груп, і цією поведінкою потрібно керувати як частиною розгортань Kubernetes. Наприклад, `kubelet` повинен мати свою власну контрольну групу і ділити ресурси `kubeReserved` з середовищем виконання контейнерів. Однак Kubelet не може розширитися і використати всі доступні ресурси вузла, якщо `kubeReserved` застосовується примусово.

Будьте особливо обережні під час примусового застосування резервування `systemReserved`, оскільки це може призвести до нестачі CPU для критичних системних служб, їх завершення через нестачу памʼяті (OOM) або неможливості створення процесів (fork) на вузлі. Рекомендується примусово застосовувати `systemReserved` лише у випадку, якщо користувач ретельно профілював свої вузли, щоб отримати точні оцінки, і впевнений у своїй здатності відновитися, якщо будь-який процес у цій групі буде завершено через нестачу памʼяті.

Примусове застосування лише ресурсів, що піддаються стисненню, для `kubeReserved` і `systemReserved` з меншою ймовірністю спричинить порушення, водночас забезпечуючи належний розподіл ресурсу в разі конкуренції за нього.

* Для початку примусово застосовуйте 'Allocatable' до `pods`.
* Після встановлення належного моніторингу та оповіщення для відстеження kube та системних демонів, спробуйте застосувати ресурси, що піддаються стисненню, на `kubeReserved` та `systemReserved`.
* Спробуйте застосувати ресурси `kubeReserved`, що не піддаються стисненню, на основі евристики використання.
* Якщо це абсолютно необхідно, застосуйте ресурси `systemReserved`, що не піддаються стисненню, з часом.

Вимоги до ресурсів системних служб kube можуть зростати з часом з додаванням все більшої кількості функцій. З часом проєкт Kubernetes намагатиметься знизити використання ресурсів системними службами вузла, але зараз це не пріоритет. Тож очікуйте зниження місткості `Allocatable` у майбутніх випусках.

## Приклад сценарію {#example-scenario}

Ось приклад для ілюстрації обчислення Node Allocatable:

* Вузол має `32Gi` памʼяті (`memory`), `16 CPUs` і `100Gi` сховища (`Storage`)
* `kubeReserved` встановлено у `{cpu: 1000m, memory: 2Gi, ephemeral-storage: 1Gi}`
* `systemReserved` встановлено у `{cpu: 500m, memory: 1Gi, ephemeral-storage: 1Gi}`
* `evictionHard` встановлено у `{memory.available: "<500Mi", nodefs.available: "<10%"}`

У цьому сценарії 'Allocatable' становитиме 14.5 CPU, 28.5Gi памʼяті та `88Gi` локального сховища. Планувальник гарантує, що загальний обсяг памʼяті в `requests` усіх Podʼів на цьому вузлі не перевищує 28.5Gi, а сховища — 88Gi. Kubelet виселяє Podʼи, коли загальне використання памʼяті Podʼами перевищує 28.5Gi або загальне використання диска перевищує 88Gi. Якщо всі процеси на вузлі споживають стільки CPU, скільки можуть, Podʼи разом не можуть спожити більше ніж 14.5 CPU.

Якщо `kubeReserved` та/або `systemReserved` не застосовуються примусово, і системні служби перевищують своє резервування, `kubelet` виселяє Podʼи, коли загальне використання памʼяті вузла перевищує 31.5Gi або `storage` перевищує 90Gi.
