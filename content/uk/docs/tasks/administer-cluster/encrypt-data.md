<!-- overview -->

Усі API в Kubernetes, які дозволяють записувати постійні дані ресурсів API, підтримують шифрування у стані спокою. Наприклад, ви можете увімкнути шифрування у стані спокою для {{< glossary_tooltip text="Secret" term_id="secret" >}}. Це шифрування у стані спокою є додатковим до будь-якого шифрування на рівні системи для кластера etcd або для файлових систем на вузлах, де ви запускаєте kube-apiserver.

На цій сторінці показано, як увімкнути та налаштувати шифрування даних API у стані спокою.

{{< note >}}
Це завдання охоплює шифрування даних ресурсів, збережених за допомогою {{< glossary_tooltip text="Kubernetes API" term_id="kubernetes-api" >}}. Наприклад, ви можете шифрувати обʼєкти Secret, включаючи дані у формі ключ-значення.

Якщо ви хочете шифрувати дані у файлових системах, змонтованих у контейнери, вам натомість потрібно або:

- використовувати інтеграцію зі сховищем, яка надає зашифровані {{< glossary_tooltip text="томи" term_id="volume" >}}
- шифрувати дані всередині вашого власного застосунку
{{< /note >}}

## {{% heading "prerequisites" %}} {#before-you-begin}

- {{< include "task-tutorial-prereqs.md" >}}

- Це завдання передбачає, що ви запускаєте API-сервер Kubernetes як {{< glossary_tooltip text="статичний Pod" term_id="static-pod" >}} на кожному вузлі панелі управління.

- Панель управління кластера **обовʼязково** має використовувати etcd версії 3.x (основна версія 3, будь-яка мінорна версія).

- Для шифрування власного ресурсу ваш кластер повинен працювати на Kubernetes v1.26 або новіше.

- Щоб використовувати символ підстановки для зіставлення ресурсів, ваш кластер повинен працювати на Kubernetes v1.27 або новіше.

## Визначте, чи вже увімкнено шифрування у стані спокою {#determining-whether-encryption-at-rest-is-already-enabled}

Стандартно API-сервер зберігає ресурси в etcd у вигляді відкритого тексту, без шифрування у стані спокою.

Процес `kube-apiserver` приймає аргумент `--encryption-provider-config`, який вказує шлях до файлу конфігурації. Вміст цього файлу, якщо ви його вказали, визначає спосіб шифрування даних API Kubernetes у etcd. Якщо ви запускаєте kube-apiserver без аргументу командного рядка `--encryption-provider-config`, то у вас немає увімкненого шифрування у стані спокою. Якщо ви запускаєте kube-apiserver з аргументом командного рядка `--encryption-provider-config`, і файл, на який він посилається, вказує на постачальника шифрування `identity` як першого постачальника шифрування у списку, то у вас немає увімкненого шифрування у стані спокою (**стандартний постачальник `identity` не надає захисту конфіденційності.**)

Якщо ви запускаєте kube-apiserver з аргументом командного рядка `--encryption-provider-config`, і файл, на який він посилається, вказує на іншого постачальника, а не `identity`, як першого постачальника шифрування у списку, то ви вже маєте увімкнене шифрування у стані спокою. Однак ця перевірка не показує, чи вдалася попередня міграція до зашифрованого сховища. Якщо ви не впевнені, [переконайтеся, що всі відповідні дані зашифровані](#ensure-all-secrets-are-encrypted).

## Розуміння конфігурації шифрування у стані спокою {#understanding-the-encryption-at-rest-configuration}

<!-- note to localizers: the highlight is to make the initial comment obvious -->
<!-- you can use as many lines as makes sense for your target localization    -->

{{< highlight yaml "linenos=false,hl_lines=2-5" >}}
---
#
# УВАГА: це приклад конфігурації.
# Не використовуйте його для вашого кластера!
#
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources:
      - secrets
      - configmaps
      - pandas.awesome.bears.example # a custom resource API
    providers:
      # Ця конфігурація не забезпечує конфіденційність даних. Перший
      # налаштований постачальник вказує механізм "identity", який
      # зберігає ресурси як простий текст.
      #
      - identity: {} # простий текст, іншими словами, шифрування НЕМАЄ
      - aesgcm:
          keys:
            - name: key1
              secret: c2VjcmV0IGlzIHNlY3VyZQ==
            - name: key2
              secret: dGhpcyBpcyBwYXNzd29yZA==
      - aescbc:
          keys:
            - name: key1
              secret: c2VjcmV0IGlzIHNlY3VyZQ==
            - name: key2
              secret: dGhpcyBpcyBwYXNzd29yZA==
      - secretbox:
          keys:
            - name: key1
              secret: YWJjZGVmZ2hpamtsbW5vcHFyc3R1dnd4eXoxMjM0NTY=
  - resources:
      - events
    providers:
      - identity: {} # не шифрувати Events навіть якщо *.* вказаний нижче
  - resources:
      - '*.apps' # використання символу підстановки потребує Kubernetes 1.27 або пізніше
    providers:
      - aescbc:
          keys:
          - name: key2
            secret: c2VjcmV0IGlzIHNlY3VyZSwgb3IgaXMgaXQ/Cg==
  - resources:
      - '*.*' # використання символу підстановки потребує Kubernetes 1.27 або пізніше
    providers:
      - aescbc:
          keys:
          - name: key3
            secret: c2VjcmV0IGlzIHNlY3VyZSwgSSB0aGluaw==
{{< /highlight >}}

Кожен елемент масиву `resources` — це окрема конфігурація, що містить повну конфігурацію. Поле `resources.resources` — це масив назв ресурсів Kubernetes (`resource` або `resource.group`), які слід шифрувати, як-от Secret, ConfigMap або інші ресурси.

Якщо власні ресурси додано до `EncryptionConfiguration` і версія кластера — 1.26 або новіша, будь-які новостворені власні ресурси, зазначені в `EncryptionConfiguration`, будуть зашифровані. Будь-які власні ресурси, які існували в etcd до цієї версії та конфігурації, залишатимуться незашифрованими, доки їх наступного разу не буде записано у сховище. Так само поводяться й вбудовані ресурси. Див. розділ [Забезпечте шифрування всіх відповідних даних](#ensure-all-secrets-are-encrypted).

Масив `providers` — це упорядкований список можливих постачальників шифрування, які можна використовувати для перелічених вами API. Кожен постачальник підтримує кілька ключів — ключі перевіряються по черзі для розшифрування, і якщо постачальник є першим, перший ключ використовується для шифрування.

Для кожного запису можна вказати лише один тип постачальника (можна вказати `identity` або `aescbc`, але не обидва в одному елементі). Перший постачальник у списку використовується для шифрування ресурсів, які записуються у сховище. Під час читання ресурсів зі сховища кожен постачальник, що відповідає збереженим даним, по черзі намагається розшифрувати дані. Якщо жоден постачальник не може прочитати збережені дані через невідповідність формату або секретного ключа, повертається помилка, яка не дає клієнтам отримати доступ до цього ресурсу.

`EncryptionConfiguration` підтримує використання символів підстановки для вказання ресурсів, які слід шифрувати. Використовуйте '`*.<group>`', щоб зашифрувати всі ресурси в групі (наприклад, '`*.apps`' у наведеному вище прикладі), або '`*.*`', щоб зашифрувати всі ресурси. '`*.`' можна використати для шифрування всіх ресурсів в основній групі (core). '`*.*`' зашифрує всі ресурси, навіть власні ресурси, які додано після запуску API-сервера.

{{< note >}} Використання символів підстановки, які перекриваються в тому самому списку ресурсів або між кількома записами, не дозволяється, оскільки частина конфігурації не діятиме. Порядок обробки та пріоритет списку `resources` визначаються порядком, у якому його вказано в конфігурації. {{< /note >}}

Якщо у вас є символ підстановки, який охоплює ресурси, і ви хочете відмовитися від шифрування у стані спокою для певного виду ресурсу, ви можете зробити це, додавши окремий елемент масиву `resources` з назвою ресурсу, який ви хочете виключити, а за ним — елемент масиву `providers`, де ви вказуєте постачальника `identity`. Ви додаєте цей елемент до списку так, щоб він ішов раніше, ніж конфігурація, де ви вказуєте шифрування (постачальника, відмінного від `identity`).

Наприклад, якщо ввімкнено '`*.*`' і ви хочете відмовитися від шифрування для Events та ConfigMap, додайте до `resources` новий елемент, розташований **раніше**, а за ним — елемент масиву providers з `identity` як постачальником. Конкретніший запис має йти перед записом із символом підстановки.

Новий елемент буде схожий на:

```yaml
  ...
  - resources:
      - configmaps. # саме з основної групи API,
                    # через крапку в кінці
      - events
    providers:
      - identity: {}
  # а потім інші записи в resources
```

Переконайтеся, що виключення вказано _перед_ елементом із символом підстановки '`*.*`' у масиві resources, щоб надати йому пріоритет.

Докладніше про структуру `EncryptionConfiguration` див. [API конфігурації шифрування](/docs/reference/config-api/apiserver-config.v1/).

{{< caution >}}
Якщо будь-який ресурс неможливо прочитати через конфігурацію шифрування (оскільки ключі було змінено) і ви не можете відновити робочу конфігурацію, єдиний вихід — видалити цей запис безпосередньо з базового etcd.

Будь-які виклики до API Kubernetes, які намагаються прочитати цей ресурс, завершаться невдачею, поки він не буде видалений або надано дійсний ключ для розшифрування.
{{< /caution >}}

### Зберігання ключів {#key-storage}

#### Локальне зберігання ключів {#local-key-storage}

Шифрування секретних даних локально керованим ключем захищає від компрометації etcd, але не захищає від компрометації хоста. Оскільки ключі шифрування зберігаються на хості у YAML-файлі EncryptionConfiguration, досвідчений зловмисник може отримати доступ до цього файлу та видобути ключі шифрування.

#### Зберігання ключів у керованій службі (KMS) {#kms-key-storage}

Постачальник KMS використовує _конвертне шифрування_: Kubernetes шифрує ресурси за допомогою ключа даних, а потім шифрує цей ключ даних за допомогою керованої служби шифрування. Kubernetes генерує унікальний ключ даних для кожного ресурсу. API-сервер зберігає зашифровану версію ключа даних в etcd поряд із шифротекстом; під час читання ресурсу API-сервер викликає керовану службу шифрування і передає як шифротекст, так і (зашифрований) ключ даних. У межах керованої служби шифрування постачальник використовує _ключ шифрування ключів_, щоб розшифрувати ключ даних, розшифровує ключ даних і, нарешті, відновлює відкритий текст. Взаємодія між панеллю управління та KMS потребує захисту під час передачі, такого як TLS.

Використання конвертного шифрування створює залежність від ключа шифрування ключів, який не зберігається в Kubernetes. У випадку KMS зловмиснику, який хоче отримати несанкціонований доступ до значень у відкритому вигляді, довелося б скомпрометувати etcd **та** стороннього постачальника KMS.

### Захист ключів шифрування {#protection-for-encryption-keys}

Вам слід вжити належних заходів для захисту конфіденційної інформації, що дає змогу розшифрування, чи то локальний ключ шифрування, чи то токен автентифікації, який дозволяє API-серверу викликати KMS.

Навіть коли ви покладаєтесь на постачальника для керування використанням та життєвим циклом основного ключа шифрування (або ключів), ви все одно відповідаєте за те, щоб контроль доступу та інші заходи безпеки для служби керування шифруванням були відповідними для ваших потреб у безпеці.

## Зашифруйте ваші дані {#encrypting-your-data}

### Згенеруйте ключ шифрування {#generate-key-no-kms}

Наведені нижче кроки передбачають, що ви не використовуєте KMS, а отже, вам потрібно згенерувати ключ шифрування. Якщо у вас уже є ключ шифрування, перейдіть до розділу [Створіть файл конфігурації шифрування](#write-an-encryption-configuration-file).

{{< caution >}}
Зберігання необробленого ключа шифрування в EncryptionConfig лише помірно покращує вашу безпеку порівняно з відсутністю шифрування.

Для додаткової секретності розгляньте використання постачальника `kms`, оскільки він покладається на ключі, що зберігаються поза вашим кластером Kubernetes. Реалізації `kms` можуть працювати з апаратними модулями безпеки (HSM) або зі службами шифрування, якими керує ваш хмарний провайдер.

Щоб дізнатися, як налаштувати шифрування в стані спокою з використанням KMS, див. [Використання постачальника KMS для шифрування даних](/docs/tasks/administer-cluster/kms-provider/). Втулок постачальника KMS, який ви використовуєте, також може постачатися з додатковою конкретною документацією.
{{< /caution >}}

Розпочніть з генерації нового ключа шифрування, а потім закодуйте його за допомогою base64:

{{< tabs name="generate_encryption_key" >}}
{{% tab name="Linux" %}}
Згенеруйте випадковий ключ з 32 байтів і закодуйте його у форматі base64. Ви можете використовувати цю команду:

```shell
head -c 32 /dev/urandom | base64
```

Ви можете використовувати `/dev/hwrng` замість `/dev/urandom`, якщо ви хочете використовувати вбудований апаратний генератор ентропії вашого ПК. Не всі пристрої з Linux надають апаратний генератор випадкових чисел.
{{% /tab %}}
{{% tab name="macOS" %}}
<!-- localization note: this is similar to the Linux tab and the wording
should match wherever the English text does -->
Згенеруйте випадковий ключ з 32 байтів і закодуйте його у форматі base64. Ви можете використовувати цю команду:

```shell
head -c 32 /dev/urandom | base64
```

{{% /tab %}}
{{% tab name="Windows" %}}
Згенеруйте випадковий ключ з 32 байтів і закодуйте його у форматі base64. Ви можете використовувати цю команду:

```powershell
# Не запускайте це в сесії, де ви встановили насіння генератора випадкових чисел.
[Convert]::ToBase64String((1..32|%{[byte](Get-Random -Max 256)}))
```

{{% /tab %}}
{{< /tabs >}}

{{< note >}}
Зберігайте ключ шифрування в таємниці, зокрема під час його генерації та, в ідеалі, навіть після того, як ви більше активно його не використовуєте.
{{< /note >}}

### Реплікація ключа шифрування {#replicate-the-encryption-key}

Використовуючи безпечний механізм передачі файлів, зробіть копію цього ключа шифрування доступною кожному іншому вузлу панелі управління.

Як мінімум використовуйте шифрування під час передачі даних — наприклад, захищену оболонку (SSH). Для більшої безпеки використовуйте асиметричне шифрування між вузлами або змініть підхід, який ви використовуєте, щоб ви покладалися на шифрування KMS.

### Створіть файл конфігурації шифрування {#write-an-encryption-configuration-file}

{{< caution >}}
Файл конфігурації шифрування може містити ключі, які можуть розшифрувати вміст в etcd. Якщо файл конфігурації містить будь-який вміст ключа, вам слід належним чином обмежити дозволи на всіх ваших вузлах панелі управління так, щоб лише користувач, який запускає kube-apiserver, міг читати цю конфігурацію.
{{< /caution >}}

Створіть новий файл конфігурації шифрування. Вміст має бути подібним до:

```yaml
---
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources:
      - secrets
      - configmaps
      - pandas.awesome.bears.example
    providers:
      - aescbc:
          keys:
            - name: key1
              # Див. наступний текст для отримання додаткової інформації про секретне значення
              secret: <BASE 64 ENCODED SECRET>
      - identity: {} # цей резервний варіант дозволяє читати незашифровані секрети;
                     # наприклад, під час початкової міграції
```

Щоб створити новий ключ шифрування (який не використовує KMS), див. [Згенеруйте ключ шифрування](#generate-key-no-kms).

### Використовуйте новий файл конфігурації шифрування {#use-the-new-encryption-configuration-file}

Вам потрібно буде змонтувати новий файл конфігурації шифрування в статичний Pod `kube-apiserver`. Ось приклад того, як це зробити:

1. Збережіть новий файл конфігурації шифрування у `/etc/kubernetes/enc/enc.yaml` на вузлі панелі управління.
1. Відредагуйте маніфест для статичного Podʼа `kube-apiserver`: `/etc/kubernetes/manifests/kube-apiserver.yaml`, щоб він був подібний до:

   ```yaml
   ---
   #
   # Це фрагмент маніфеста для статичного Podʼа.
   # Перевірте, чи це правильно для вашого кластера та для вашого API-сервера.
   #
   apiVersion: v1
   kind: Pod
   metadata:
     annotations:
       kubeadm.kubernetes.io/kube-apiserver.advertise-address.endpoint: 10.20.30.40:443
     creationTimestamp: null
     labels:
       app.kubernetes.io/component: kube-apiserver
       tier: control-plane
     name: kube-apiserver
     namespace: kube-system
   spec:
     containers:
     - command:
       - kube-apiserver
       ...
       - --encryption-provider-config=/etc/kubernetes/enc/enc.yaml  # додайте цей рядок
       volumeMounts:
       ...
       - name: enc                           # додайте цей рядок
         mountPath: /etc/kubernetes/enc      # додайте цей рядок
         readOnly: true                      # додайте цей рядок
       ...
     volumes:
     ...
     - name: enc                             # додайте цей рядок
       hostPath:                             # додайте цей рядок
         path: /etc/kubernetes/enc           # додайте цей рядок
         type: DirectoryOrCreate             # додайте цей рядок
     ...
   ```

1. Перезапустіть свій API-сервер.

{{< caution >}}
Ваш файл конфігурації містить ключі, які можуть розшифрувати вміст в etcd, тому вам слід належним чином обмежити дозволи на вузлах панелі управління так, щоб лише користувач, який запускає `kube-apiserver`, міг читати його.
{{< /caution >}}

Тепер у вас є шифрування для **одного** хоста панелі управління. У типовому кластері Kubernetes кілька хостів панелі управління, тож потрібно зробити ще дещо.

### Переконфігуруйте інші вузли панелі управління {#api-server-config-update-more}

Якщо у вашому кластері є кілька API-серверів, вам слід розгорнути зміни по черзі на кожному API-сервері.

{{< caution >}}
Для конфігурацій кластера з двома або більше вузлами панелі управління конфігурація шифрування повинна бути ідентичною на кожному вузлі панелі управління.

Якщо існує різниця в конфігурації постачальника шифрування між вузлами панелі управління, ця різниця може означати, що kube-apiserver не може розшифрувати дані.
{{< /caution >}}

Коли ви плануєте оновлення конфігурації шифрування вашого кластера, сплануйте це так, щоб API-сервери у вашій панелі управління завжди могли розшифрувати збережені дані (навіть під час часткового впровадження змін).

Переконайтеся, що ви використовуєте **однакову** конфігурацію шифрування на кожному вузлі панелі управління.

### Перевірте, що нові дані записані зашифровано {#verifying-that-data-is-encrypted}

Дані шифруються під час запису в etcd. Після перезапуску вашого `kube-apiserver` будь-який новостворений або оновлений Secret (або інші види ресурсів, налаштовані в `EncryptionConfiguration`) має бути зашифрований під час зберігання.

Щоб перевірити це, ви можете використати програму командного рядка `etcdctl`, щоб отримати вміст ваших секретних даних.

Цей приклад показує, як це перевірити для шифрування API Secret.

1. Створіть новий Secret під назвою `secret1` у просторі імен `default`:

   ```shell
   kubectl create secret generic secret1 -n default --from-literal=mykey=mydata
   ```

1. Використовуючи інструмент командного рядка `etcdctl`, прочитайте цей Secret з etcd:

   ```
   ETCDCTL_API=3 etcdctl get /registry/secrets/default/secret1 [...] | hexdump -C
   ```

   де `[...]` — це додаткові аргументи для підключення до сервера etcd.

   Наприклад:

   ```shell
   ETCDCTL_API=3 etcdctl \
      --cacert=/etc/kubernetes/pki/etcd/ca.crt   \
      --cert=/etc/kubernetes/pki/etcd/server.crt \
      --key=/etc/kubernetes/pki/etcd/server.key  \
      get /registry/secrets/default/secret1 | hexdump -C
   ```

   Вивід подібний до цього (скорочено):

   ```hexdump
   00000000  2f 72 65 67 69 73 74 72  79 2f 73 65 63 72 65 74  |/registry/secret|
   00000010  73 2f 64 65 66 61 75 6c  74 2f 73 65 63 72 65 74  |s/default/secret|
   00000020  31 0a 6b 38 73 3a 65 6e  63 3a 61 65 73 63 62 63  |1.k8s:enc:aescbc|
   00000030  3a 76 31 3a 6b 65 79 31  3a c7 6c e7 d3 09 bc 06  |:v1:key1:.l.....|
   00000040  25 51 91 e4 e0 6c e5 b1  4d 7a 8b 3d b9 c2 7c 6e  |%Q...l..Mz.=..|n|
   00000050  b4 79 df 05 28 ae 0d 8e  5f 35 13 2c c0 18 99 3e  |.y..(..._5.,...>|
   [...]
   00000110  23 3a 0d fc 28 ca 48 2d  6b 2d 46 cc 72 0b 70 4c  |#:..(.H-k-F.r.pL|
   00000120  a5 fc 35 43 12 4e 60 ef  bf 6f fe cf df 0b ad 1f  |..5C.N`..o......|
   00000130  82 c4 88 53 02 da 3e 66  ff 0a                    |...S..>f..|
   0000013a
   ```

1. Перевірте, що збережений Secret має префікс `k8s:enc:aescbc:v1:`, що вказує на те, що постачальник `aescbc` зашифрував отримані дані. Переконайтеся, що імʼя ключа, показане в `etcd`, відповідає імені ключа, вказаному в `EncryptionConfiguration` вище. У цьому прикладі ви бачите, що ключ шифрування з назвою `key1` використовується в `etcd` і в `EncryptionConfiguration`.

1. Перевірте, що Secret правильно розшифровується під час отримання через API:

   ```shell
   kubectl get secret secret1 -n default -o yaml
   ```

   Вивід повинен містити `mykey: bXlkYXRh`, з вмістом `mydata`, закодованим за допомогою base64; прочитайте [декодування Secret](/docs/tasks/configmap-secret/managing-secret-using-kubectl/#decoding-secret), щоб дізнатися, як повністю декодувати Secret.

### Забезпечте шифрування всіх відповідних даних {#ensure-all-secrets-are-encrypted}

Часто недостатньо лише переконатися, що нові обʼєкти зашифровані: ви також хочете, щоб шифрування застосовувалося до обʼєктів, які вже збережені.

У цьому прикладі ви налаштували свій кластер так, що Secret шифруються під час запису. Виконання операції заміни для кожного Secret зашифрує цей вміст у стані спокою, а самі обʼєкти не змінюються.

Ви можете виконати цю зміну для всіх Secret у вашому кластері:

```shell
# Виконайте це в якості адміністратора, який може читати і записувати всі Secret
kubectl get secrets --all-namespaces -o json | kubectl replace -f -
```

Команда вище зчитує всі Secret, а потім оновлює їх з тими самими даними, щоб застосувати шифрування на стороні сервера.

{{< note >}}
Якщо виникає помилка через конфлікт запису, повторіть команду. Цю команду безпечно виконувати більше одного разу.

Для великих кластерів ви можете розділити Secret за просторами імен або написати скрипт оновлення.
{{< /note >}}

## Запобігання отриманню відкритого тексту {#cleanup-all-secrets-encrypted}

Якщо ви хочете переконатися, що доступ до певного виду API здійснюється тільки з використанням шифрування, ви можете позбавити API-сервер можливості читати базові дані цього API у вигляді відкритого тексту.

{{< warning >}}
Ця зміна заважає API-серверу отримувати ресурси, які позначені як зашифровані в стані спокою, але насправді зберігаються у відкритому вигляді.

Коли ви налаштували шифрування у стані спокою для API (наприклад: вид API `Secret`, який представляє ресурси `secrets` в основній групі API), **вам необхідно** переконатися, що всі ці ресурси у цьому кластері дійсно зашифровані у стані спокою. Перевірте це, перш ніж продовжувати з наступними кроками.
{{< /warning >}}

Після того, як усі Secret у вашому кластері зашифровано, ви можете видалити частину `identity` з конфігурації шифрування. Наприклад:

{{< highlight yaml "linenos=false,hl_lines=12" >}}
---
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources:
      - secrets
    providers:
      - aescbc:
          keys:
            - name: key1
              secret: <BASE 64 ENCODED SECRET>
      - identity: {} # ВИДАЛІТЬ ЦЕЙ РЯДОК
{{< /highlight >}}

… а потім перезапустіть кожен API-сервер по черзі. Ця зміна запобігає API-серверу отримувати доступ до Secret у відкритому текстовому форматі, навіть випадково.

## Ротація ключа розшифрування {#rotating-a-decryption-key}

Зміна ключа шифрування для Kubernetes без простою вимагає багатокрокової операції, особливо в умовах високодоступного розгортання, де працюють кілька процесів `kube-apiserver`.

1. Згенеруйте новий ключ і додайте його як другий запис ключа для поточного постачальника на всіх вузлах панелі управління.
1. Перезапустіть **усі** процеси `kube-apiserver`, щоб кожен сервер міг розшифрувати будь-які дані, зашифровані новим ключем.
1. Зробіть безпечну резервну копію нового ключа шифрування. Якщо ви втратите всі копії цього ключа, вам доведеться видалити всі ресурси, зашифровані втраченим ключем, і робочі навантаження можуть працювати не так, як очікується, поки шифрування у стані спокою не працює.
1. Зробіть новий ключ першим записом у масиві `keys`, щоб він використовувався для шифрування у стані спокою під час нових записів.
1. Перезапустіть усі процеси `kube-apiserver`, щоб кожен хост панелі управління тепер шифрував за допомогою нового ключа.
1. Як привілейований користувач, виконайте `kubectl get secrets --all-namespaces -o json | kubectl replace -f -`, щоб зашифрувати всі наявні Secret новим ключем.
1. Після того, як ви оновили всі наявні Secret для використання нового ключа і зробили безпечну резервну копію нового ключа, видаліть старий ключ розшифрування з конфігурації.

## Розшифрування всіх даних {#decrypting-all-data}

У цьому прикладі показано, як зупинити шифрування API Secret у стані спокою. Якщо ви шифруєте інші види API, адаптуйте кроки відповідно.

Щоб вимкнути шифрування у стані спокою, розмістіть постачальника `identity` першим записом у вашому файлі конфігурації шифрування:

```yaml
---
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources:
      - secrets
      # перерахуйте тут будь-які інші ресурси, які ви раніше
      # шифрували у спокої
    providers:
      - identity: {} # додайте цей рядок
      - aescbc:
          keys:
            - name: key1
              secret: <BASE 64 ENCODED SECRET> # залиште це на місці
                                               # переконайтеся, що воно йде після "identity"
```

Потім виконайте таку команду, щоб примусово розшифрувати всі Secret:

```shell
kubectl get secrets --all-namespaces -o json | kubectl replace -f -
```

Після того, як для всіх наявних зашифрованих ресурсів ви замінили базові дані на такі, що не використовують шифрування, ви можете видалити налаштування шифрування з `kube-apiserver`.

## Налаштування автоматичного перезавантаження {#configure-automatic-reloading}

Ви можете налаштувати автоматичне перезавантаження конфігурації постачальника шифрування. Цей параметр визначає, чи має {{< glossary_tooltip text="API-сервер" term_id="kube-apiserver" >}} завантажувати файл, вказаний у `--encryption-provider-config`, лише один раз під час запуску чи автоматично щоразу, коли ви змінюєте цей файл. Увімкнення цього параметра дозволяє змінювати ключі для шифрування у стані спокою без перезапуску API-сервера.

Щоб дозволити автоматичне перезавантаження, налаштуйте API-сервер на запуск з `--encryption-provider-config-automatic-reload=true`. Коли це ввімкнено, зміни файлу перевіряються щохвилини. Метрика `apiserver_encryption_config_controller_automatic_reload_last_timestamp_seconds` показує, коли нова конфігурація набирає чинності. Це дозволяє виконувати ротацію ключів шифрування без перезапуску API-сервера.
