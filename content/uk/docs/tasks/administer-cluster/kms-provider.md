Ця сторінка показує, як налаштувати постачальника Служби керування ключами (KMS) та втулок для шифрування конфіденційних даних. У Kubernetes {{< skew currentVersion >}} існують дві версії шифрування у стані спокою за допомогою KMS. Якщо це можливо, вам слід використовувати KMS v2, оскільки KMS v1 застарів (починаючи з Kubernetes v1.28) і стандартно вимкнений (починаючи з Kubernetes v1.29). KMS v2 пропонує значно кращі характеристики продуктивності, ніж KMS v1.

{{< caution >}}
Ця документація стосується загальнодоступної (GA) реалізації KMS v2 (і застарілої реалізації версії 1). Якщо ви використовуєте будь-які компоненти панелі управління, старші за Kubernetes v1.29, перегляньте відповідну сторінку в документації для версії Kubernetes, яку використовує ваш кластер. Попередні випуски Kubernetes мали іншу поведінку, яка може бути важливою для інформаційної безпеки.
{{< /caution >}}

## Шифрування KMS та ключі для кожного обʼєкта {#kms-encryption-and-per-object-encryption-keys}

Постачальник шифрування KMS використовує схему конвертного шифрування (envelope encryption) для шифрування даних в etcd. Дані шифруються за допомогою ключа шифрування даних (data encryption key — DEK). DEK шифруються за допомогою ключа шифрування ключів (key encryption key — KEK), який зберігається та керується у віддаленому KMS.

Якщо ви використовуєте (застарілу) реалізацію v1 KMS, для кожного шифрування генерується новий DEK.

З KMS v2 новий DEK генерується **для кожного шифрування**: API-сервер використовує _функцію деривації ключа_ (key derivation function), щоб генерувати одноразові ключі шифрування даних із секретного початкового значення (seed), поєднаного з випадковими даними. Seed змінюється щоразу, коли виконується ротація KEK (докладніше див. розділ _Розуміння key_id та ротації ключів_ нижче).

Постачальник KMS використовує gRPC для звʼязку з певним втулком KMS через сокет домену UNIX. Втулок KMS, який реалізовано як сервер gRPC і розгорнуто на тих самих хостах, що й панель управління Kubernetes, відповідає за всю взаємодію з віддаленим KMS.

## Налаштування постачальника KMS {#configuring-the-kms-provider}

Щоб налаштувати постачальника KMS на API-сервері, додайте постачальника типу `kms` до масиву `providers` у файлі конфігурації шифрування і встановіть такі властивості:

### KMS v1 {#configuring-the-kms-provider-kms-v1}

- `apiVersion`: Версія API для постачальника KMS. Залиште це значення порожнім або встановіть його на `v1`.
- `name`: Назва втулка KMS для відображення. Її не можна змінити після встановлення.
- `endpoint`: Адреса прослуховування сервера gRPC (втулка KMS). Точка доступу — це сокет домену UNIX.
- `cachesize`: Кількість ключів шифрування даних (DEK), які зберігатимуться в кеші у відкритому вигляді. Ключі DEK з кешу можна використовувати без додаткового звернення до KMS; натомість ключі DEK, яких немає в кеші, потребують звернення до KMS для розгортання (unwrap).
- `timeout`: Скільки часу `kube-apiserver` має чекати на відповідь від втулка kms, перш ніж сповістити про помилку (стандартно — 3 секунди).

### KMS v2 {#configuring-the-kms-provider-kms-v2}

- `apiVersion`: Версія API для постачальника KMS. Встановіть значення `v2`.
- `name`: Назва втулка KMS для відображення. Її не можна змінити після встановлення.
- `endpoint`: Адреса прослуховування сервера gRPC (втулка KMS). Точка доступу — це сокет домену UNIX.
- `timeout`: Скільки часу `kube-apiserver` має чекати на відповідь від втулка kms, перш ніж сповістити про помилку (стандартно — 3 секунди).

KMS v2 не підтримує властивість `cachesize`. Усі ключі шифрування даних (DEK) зберігатимуться в кеші у відкритому вигляді, щойно сервер розгорне (unwrap) їх через звернення до KMS. Після кешування ключі DEK можна використовувати для розшифрування безстроково без звернення до KMS.

Див. [Розуміння конфігурації шифрування у стані спокою](/docs/tasks/administer-cluster/encrypt-data).

## Реалізація втулка KMS {#implementing-a-kms-plugin}

Для реалізації втулка KMS ви можете розробити новий сервер gRPC втулка або увімкнути втулок KMS, який вже надається вашим постачальником хмарних послуг. Потім ви інтегруєте втулок з віддаленим KMS та розгортаєте його на панелі управління Kubernetes.

### Увімкнення KMS, що підтримується вашим постачальником хмарних послуг {#enabling-the-kms-supported-by-your-cloud-provider}

Зверніться до вашого постачальника хмарних послуг для отримання інструкцій щодо увімкнення втулка KMS, який він надає.

### Розробка сервера gRPC втулка KMS {#developing-a-kms-plugin-grpc-server}

Ви можете розробити сервер gRPC втулка KMS, використовуючи файл-заглушку (stub), доступний для Go. Для інших мов ви використовуєте файл proto, щоб створити файл-заглушку, за допомогою якого можна написати код сервера gRPC.

#### KMS v1 {#developing-a-kms-plugin-gRPC-server-kms-v1}

- Використовуючи Go: Використовуйте функції та структури даних у файлі-заглушці [api.pb.go](https://github.com/kubernetes/kms/blob/release-{{< skew currentVersion >}}/apis/v1beta1/api.pb.go) для написання коду сервера gRPC.

- Використовуючи мови, відмінні від Go: Використовуйте компілятор protoc з файлом proto [api.proto](https://github.com/kubernetes/kms/blob/release-{{< skew currentVersion >}}/apis/v1beta1/api.proto), щоб згенерувати файл-заглушку для конкретної мови.

#### KMS v2 {#developing-a-kms-plugin-gRPC-server-kms-v2}

- Використовуючи Go: Для спрощення процесу надається високорівнева [бібліотека](https://github.com/kubernetes/kms/blob/release-{{< skew currentVersion >}}/pkg/service/interface.go). Низькорівневі реалізації можуть використовувати функції та структури даних у файлі-заглушці [api.pb.go](https://github.com/kubernetes/kms/blob/release-{{< skew currentVersion >}}/apis/v2/api.pb.go) для написання коду сервера gRPC.

- Використовуючи мови, відмінні від Go: Використовуйте компілятор protoc з файлом proto [api.proto](https://github.com/kubernetes/kms/blob/release-{{< skew currentVersion >}}/apis/v2/api.proto), щоб згенерувати файл-заглушку для конкретної мови.

Потім використовуйте функції та структури даних у файлі-заглушці для написання коду сервера.

#### Примітки {#notes}

##### KMS v1 {#developing-a-kms-plugin-gRPC-server-notes-kms-v1}

- Версія втулка kms: `v1beta1`

  У відповідь на виклик процедури Version сумісний втулок KMS повинен повернути `v1beta1` як `VersionResponse.version`.

- Версія повідомлення: `v1beta1`

  Усі повідомлення від постачальника KMS мають поле версії встановлене на `v1beta1`.

- Протокол: сокет домену UNIX (`unix`)

  Втулок реалізовано як сервер gRPC, який слухає сокет домену UNIX. Під час розгортання втулка слід створити файл у файловій системі для запуску зʼєднання gRPC через сокет домену unix. API-сервер (клієнт gRPC) налаштовується з точкою доступу сокета домену unix постачальника KMS (сервера gRPC), щоб взаємодіяти з ним. Можна використовувати абстрактний сокет Linux, якщо точка доступу починається з `/@`, наприклад, `unix:///@foo`. Використовуючи цей тип сокетів, слід бути обережними, оскільки вони не мають поняття ACL (на відміну від традиційних файлових сокетів). Однак на них поширюється мережевий простір імен Linux, тож вони будуть доступні лише контейнерам у тому самому Podʼі, якщо не використовується мережа хоста.

##### KMS v2 {#developing-a-kms-plugin-gRPC-server-notes-kms-v2}

- Версія втулка KMS: `v2`

  У відповідь на віддалений виклик процедури `Status` сумісний втулок KMS повинен повернути свою версію сумісності KMS як `StatusResponse.version`. Ця відповідь також має містити "ok" як `StatusResponse.healthz` і `key_id` (ідентифікатор KEK віддаленого KMS) як `StatusResponse.key_id`. Проєкт Kubernetes рекомендує зробити ваш втулок сумісним зі стабільним API KMS `v2`. Kubernetes {{< skew currentVersion >}} також підтримує API `v2beta1` для KMS; майбутні випуски Kubernetes, імовірно, продовжать підтримувати цю бета-версію.

  API-сервер опитує процедуру `Status` приблизно щохвилини, коли все справно, і кожні 10 секунд, коли втулок несправний. Втулки мають подбати про оптимізацію цього виклику, оскільки він перебуватиме під постійним навантаженням.

- Шифрування

  Виклик процедури `EncryptRequest` надає відкритий текст і UID для логування. Відповідь має містити шифротекст, `key_id` для використаного KEK і, за потреби, будь-які метадані, потрібні втулку KMS для майбутніх викликів `DecryptRequest` (через поле `annotations`). Втулок повинен гарантувати, що будь-який відмінний відкритий текст дає відмінну відповідь `(ciphertext, key_id, annotations)`.

  Якщо втулок повертає непорожню мапу `annotations`, усі ключі мапи мають бути повними доменними іменами, такими як `example.com`. Приклад використання `annotation` — `{"kms.example.io/remote-kms-auditid":"<audit ID used by the remote KMS>"}`

  API-сервер не виконує виклики процедури `EncryptRequest` з високою частотою. Реалізаціям втулків однаково слід прагнути, щоб затримка кожного запиту не перевищувала 100 мілісекунд.

- Розшифрування

  Виклик процедури `DecryptRequest` надає `(ciphertext, key_id, annotations)` з `EncryptRequest` та UID для логування. Як і очікувалося, це обернений виклик до `EncryptRequest`. Втулки мають перевіряти, що `key_id` їм відомий — вони не повинні намагатися розшифрувати дані, якщо не впевнені, що зашифрували їх раніше.

  API-сервер може виконати тисячі викликів процедури `DecryptRequest` під час запуску, щоб заповнити свій кеш спостереження (watch cache). Тому реалізації втулків мають виконувати ці виклики якнайшвидше й прагнути, щоб затримка кожного запиту не перевищувала 10 мілісекунд.

- Розуміння `key_id` та ротації ключів

  `key_id` — це публічна, несекретна назва KEK віддаленого KMS, який використовується наразі. Її можуть записувати в логи під час звичайної роботи API-сервера, тому вона не повинна містити жодних приватних даних. Реалізаціям втулків рекомендується використовувати хеш, щоб уникнути витоку будь-яких даних. Метрики KMS v2 хешують це значення, перш ніж показати його через точку доступу `/metrics`.

  API-сервер вважає `key_id`, отриманий з виклику процедури `Status`, авторитетним. Отже, зміна цього значення сигналізує API-серверу, що віддалений KEK змінився, і дані, зашифровані старим KEK, слід позначати як застарілі під час виконання запису без змін (no-op) (як описано нижче). Якщо виклик процедури `EncryptRequest` повертає `key_id`, що відрізняється від `Status`, відповідь відкидається, і втулок вважається несправним. Тому реалізації мають гарантувати, що `key_id`, який повертає `Status`, збігатиметься з тим, що повертає `EncryptRequest`. Крім того, втулки мають забезпечити, щоб `key_id` був стабільним і не перемикався туди-сюди між значеннями (наприклад, під час ротації віддаленого KEK).

  Втулки не повинні повторно використовувати `key_id`, навіть у ситуаціях, коли раніше використаний віддалений KEK було відновлено. Наприклад, якщо втулок використовував `key_id=A`, перемкнувся на `key_id=B`, а потім повернувся до `key_id=A`, — замість `key_id=A` втулок має повідомити якесь похідне значення, таке як `key_id=A_001`, або використати нове значення, наприклад `key_id=C`.

  Оскільки API-сервер опитує `Status` приблизно щохвилини, ротація `key_id` не є миттєвою. Крім того, API-сервер продовжуватиме працювати з останнім дійсним станом приблизно три хвилини. Тому, якщо користувач хоче застосувати пасивний підхід до міграції сховища (тобто зачекати), він має запланувати міграцію на `3 + N + M` хвилин після ротації віддаленого KEK (`N` — це час, потрібний втулку, щоб помітити зміну `key_id`, а `M` — бажаний запас часу для обробки змін конфігурації; рекомендовано мінімальне значення `M` пʼять хвилин). Зверніть увагу, що для ротації KEK перезапуск API-сервера не потрібен.

  {{< caution >}}
  Оскільки ви не контролюєте кількість записів, виконаних з DEK, проєкт Kubernetes рекомендує робити ротацію KEK принаймні кожні 90 днів.
  {{< /caution >}}

- Протокол: сокет домену UNIX (`unix`)

  Втулок реалізовано як сервер gRPC, який слухає сокет домену UNIX. Під час розгортання втулка слід створити файл у файловій системі для запуску зʼєднання gRPC через сокет домену unix. API-сервер (клієнт gRPC) налаштовується з точкою доступу сокета домену unix постачальника KMS (сервера gRPC), щоб взаємодіяти з ним. Можна використовувати абстрактний сокет Linux, якщо точка доступу починається з `/@`, наприклад, `unix:///@foo`. Використовуючи цей тип сокетів, слід бути обережними, оскільки вони не мають поняття ACL (на відміну від традиційних файлових сокетів). Однак на них поширюється мережевий простір імен Linux, тож вони будуть доступні лише контейнерам у тому самому Podʼі, якщо не використовується мережа хоста.

### Інтеграція втулка KMS з віддаленим KMS {#integrating-a-kms-plugin-with-the-remote-kms}

Втулок KMS може взаємодіяти з віддаленим KMS за допомогою будь-якого протоколу, який підтримує KMS. Усі дані конфігурації, зокрема облікові дані автентифікації, які втулок KMS використовує для взаємодії з віддаленим KMS, зберігаються та керуються втулком KMS самостійно. Втулок KMS може кодувати шифротекст з додатковими метаданими, які можуть знадобитися, перш ніж надіслати його до KMS для розшифрування (KMS v2 спрощує цей процес, надаючи окреме поле `annotations`).

### Розгортання втулка KMS {#deploying-the-kms-plugin}

Переконайтеся, що втулок KMS працює на тих самих хостах, що й API-сервер(и) Kubernetes.

## Шифрування ваших даних за допомогою постачальника KMS {#encrypting-your-data-with-the-kms-provider}

Щоб зашифрувати дані:

1. Створіть новий файл `EncryptionConfiguration`, використовуючи відповідні властивості для постачальника `kms`, щоб шифрувати ресурси, такі як Secret і ConfigMap. Якщо ви хочете зашифрувати API розширення, визначений у CustomResourceDefinition, ваш кластер повинен працювати на Kubernetes v1.26 або новішому.

1. Встановіть прапорець `--encryption-provider-config` для kube-apiserver, щоб вказати розташування файлу конфігурації.

1. Булевий аргумент `--encryption-provider-config-automatic-reload` визначає, чи слід [автоматично перезавантажувати](/docs/tasks/administer-cluster/encrypt-data/#configure-automatic-reloading) файл, заданий через `--encryption-provider-config`, у разі зміни вмісту на диску.

1. Перезапустіть свій API-сервер.

### KMS v1 {#encrypting-your-data-with-the-kms-provider-kms-v1}

   ```yaml
   apiVersion: apiserver.config.k8s.io/v1
   kind: EncryptionConfiguration
   resources:
     - resources:
         - secrets
         - configmaps
         - pandas.awesome.bears.example
       providers:
         - kms:
             name: myKmsPluginFoo
             endpoint: unix:///tmp/socketfile-foo.sock
             cachesize: 100
             timeout: 3s
         - kms:
             name: myKmsPluginBar
             endpoint: unix:///tmp/socketfile-bar.sock
             cachesize: 100
             timeout: 3s
   ```

### KMS v2 {#encrypting-your-data-with-the-kms-provider-kms-v2}

   ```yaml
   apiVersion: apiserver.config.k8s.io/v1
   kind: EncryptionConfiguration
   resources:
     - resources:
         - secrets
         - configmaps
         - pandas.awesome.bears.example
       providers:
         - kms:
             apiVersion: v2
             name: myKmsPluginFoo
             endpoint: unix:///tmp/socketfile-foo.sock
             timeout: 3s
         - kms:
             apiVersion: v2
             name: myKmsPluginBar
             endpoint: unix:///tmp/socketfile-bar.sock
             timeout: 3s
   ```

Встановлення `--encryption-provider-config-automatic-reload` в `true` обʼєднує всі перевірки стану в одну точку доступу перевірки стану. Індивідуальні перевірки стану доступні тільки тоді, коли використовуються постачальники KMS v1 і конфігурація шифрування не перезавантажується автоматично.

Наведена нижче таблиця підсумовує точки доступу перевірки стану для кожної версії KMS:

| Конфігурації KMS     | Без автоматичного перезавантаження | З автоматичним перезавантаженням |
| -------------------- | ---------------------------------- | ------------------------------- |
| Тільки KMS v1        | Індивідуальні перевірки            | Одна перевірка                  |
| Тільки KMS v2        | Одна перевірка                     | Одна перевірка                  |
| KMS v1 та KMS v2     | Індивідуальні перевірки            | Одна перевірка                  |
| Без KMS              | Немає                              | Одна перевірка                  |

`Одна перевірка` означає, що єдиною точкою доступу перевірки стану є `/healthz/kms-providers`.

`Індивідуальні перевірки` означає, що для кожного втулка KMS є асоційована точка доступу перевірки стану на основі його місця в конфігурації шифрування: `/healthz/kms-provider-0`, `/healthz/kms-provider-1` тощо.

Ці шляхи точок доступу перевірки стану жорстко закодовані та генеруються/контролюються сервером. Індекси для індивідуальних перевірок відповідають порядку, у якому обробляється конфігурація шифрування KMS.

Доки не виконано кроки, описані в [Забезпечення шифрування всіх секретів](#ensuring-all-secrets-are-encrypted), список `providers` повинен закінчуватися постачальником `identity: {}`, щоб можна було читати незашифровані дані. Після шифрування всіх ресурсів постачальника `identity` слід видалити, щоб API-сервер не приймав незашифровані дані.

Докладніше про формат `EncryptionConfiguration` див. [довідник API конфігурації шифрування API-сервера](/docs/reference/config-api/apiserver-config.v1/).

## Перевірка того, що дані зашифровані {#verifying-that-the-data-is-encrypted}

Коли шифрування у стані спокою правильно налаштовано, ресурси шифруються під час запису. Після перезапуску вашого `kube-apiserver` будь-які новостворені або оновлені Secret чи інші типи ресурсів, налаштовані в `EncryptionConfiguration`, мають бути зашифровані під час зберігання. Щоб перевірити це, ви можете використати програму командного рядка `etcdctl` для отримання вмісту ваших секретних даних.

1. Створіть новий Secret з назвою `secret1` в просторі імен `default`:

   ```shell
   kubectl create secret generic secret1 -n default --from-literal=mykey=mydata
   ```

1. Використовуючи командний рядок `etcdctl`, прочитайте цей Secret з etcd:

   ```shell
   ETCDCTL_API=3 etcdctl get /kubernetes.io/secrets/default/secret1 [...] | hexdump -C
   ```

   де `[...]` містить додаткові аргументи для підключення до сервера etcd.

1. Переконайтеся, що збережений Secret починається з префікса `k8s:enc:kms:v1:` для KMS v1 або з префікса `k8s:enc:kms:v2:` для KMS v2, що вказує на те, що постачальник `kms` зашифрував отримані дані.

1. Перевірте, що Secret правильно розшифровується під час отримання через API:

   ```shell
   kubectl describe secret secret1 -n default
   ```

   Secret повинен містити `mykey: mydata`.

## Забезпечення шифрування всіх секретів {#ensuring-all-secrets-are-encrypted}

Коли шифрування у стані спокою правильно налаштовано, ресурси шифруються під час запису. Тому ми можемо виконати оновлення на місці без змін (no-op), щоб переконатися, що дані зашифровані.

Наведена нижче команда читає всі Secret, а потім оновлює їх, щоб застосувати шифрування на боці сервера. Якщо через конфліктний запис виникне помилка, повторіть команду. Для більших кластерів ви можете розділити Secret за просторами імен або написати скрипт оновлення.

```shell
kubectl get secrets --all-namespaces -o json | kubectl replace -f -
```

## Перехід від локального постачальника шифрування до постачальника KMS {#switching-from-a-local-encryption-provider-to-the-kms-provider}

Щоб перейти від локального постачальника шифрування до постачальника `kms` та перешифрувати всі секрети:

1. Додайте постачальника `kms` як перший запис у файлі конфігурації, як показано в прикладі нижче.

   ```yaml
   apiVersion: apiserver.config.k8s.io/v1
   kind: EncryptionConfiguration
   resources:
     - resources:
         - secrets
       providers:
         - kms:
             apiVersion: v2
             name: myKmsPlugin
             endpoint: unix:///tmp/socketfile.sock
         - aescbc:
             keys:
               - name: key1
                 secret: <BASE 64 ENCODED SECRET>
   ```

1. Перезапустіть усі процеси `kube-apiserver`.

1. Виконайте таку команду, щоб примусово перешифрувати всі секрети за допомогою постачальника `kms`.

   ```shell
   kubectl get secrets --all-namespaces -o json | kubectl replace -f -
   ```
