<!-- overview -->

На цій сторінці описано кроки, потрібні для безпечного завершення роботи та перезапуску кластерів Kubernetes.

Адміністраторам кластера може знадобитися призупинити роботу кластера й перезапустити його пізніше, наприклад для обслуговування або зменшення витрат на інфраструктуру.

<!-- body -->

## {{% heading "prerequisites" %}} {#before-you-begin}

- У вас має бути наявний кластер і доступ до нього з правами адміністратора кластера.
- Ця процедура не призначена для середовищ, де використовується автомасштабування вузлів.
- У цій процедурі для завершення роботи кластера вимикаються вузли. Деякі системи керування серверами автоматично видаляють віртуальні машини, які не відповідають на перевірки життєздатності. Якщо у вашому середовищі це налаштовано, не виконуйте цю процедуру.

### (Необовʼязково) Перевірте строк дії сертифікатів {#check-certificate-expiration}

Якщо кластер вимикатиметься надовго, визначте, коли завершиться строк дії сертифікатів.

```bash
openssl x509 -in /etc/kubernetes/pki/apiserver.crt -noout -enddate
```

Приклад виводу:

```bash
notAfter=Mar  3 09:18:19 2026 GMT
```

Щоб кластер міг безперешкодно перезапуститися, заплануйте перезапуск не пізніше від зазначеної дати. Зверніть увагу, що різні сертифікати можуть мати різні дати завершення строку дії.

## (Необовʼязково) Створіть резервну копію кластера etcd {#optional-backup-an-etcd-cluster}

Якщо кластер Kubernetes використовує etcd як сховище даних, створіть [резервну копію etcd](/docs/tasks/administer-cluster/configure-upgrade-etcd/#backing-up-an-etcd-cluster). Вона може знадобитися для відновлення кластера, якщо перезапуск не вдасться.

{{< note >}}

- Ця процедура завершує роботу навантажень звичайним способом, щоб запобігти пошкодженню даних. За потреби створіть їхні резервні копії відповідним для кожного навантаження способом.
- Завершення роботи кластера виконує його адміністратор, але резервне копіювання навантажень можуть виконувати відповідальні за них команди. Завчасно повідомте користувачів про заплановане завершення роботи кластера.
{{< /note >}}

## Вимкніть вузли кластера {#node-shutdown}

Щоб коректно завершити роботу кластера, вимкніть його вузли. На відміну від звичайного [завершення роботи вузла](/docs/concepts/cluster-administration/node-shutdown/#graceful-node-shutdown), під час вимкнення кластера Podʼи не потрібно переміщувати на інші вузли до його перезапуску. Тому ця процедура запобігає повторному плануванню Podʼів, поки кластер вимкнено. Спочатку вимикаються робочі вузли, а потім вузли панелі управління.

### Заблокуйте планування на робочих вузлах {#mark-worker-nodes-unschedulable}

Зробіть усі вузли кластера недоступними для планування за допомогою `kubectl cordon`:

```bash
kubectl cordon --selector='!node-role.kubernetes.io/control-plane'
kubectl cordon --selector='node-role.kubernetes.io/control-plane'
```

### Виселіть Podʼи з вузлів {#terminating-pods-in-the-nodes}

Використовуйте `kubectl drain`, щоб виселити Podʼи з вузлів. Спочатку виконайте цю команду на робочих вузлах, а потім — на вузлах панелі управління. `kubectl drain` зазвичай позначає вибрані вузли як недоступні для планування перед виселенням Podʼів. У великих кластерах перед виконанням `kubectl drain` переконайтеся, що всі вузли позначено як недоступні для планування; перевірити це можна командою `kubectl get nodes`.

```bash
kubectl drain --ignore-daemonsets --selector='!node-role.kubernetes.io/control-plane'
kubectl drain --ignore-daemonsets --selector='node-role.kubernetes.io/control-plane'
```

### Вимкніть вузли кластера {#shutting-down-nodes-in-the-cluster}

Вимкніть усі вузли способом, що підходить для вашого кластера: наприклад, через вебконсоль постачальника хмарних послуг, скрипт або плейбук.

Приклад команди, яку слід виконати на кожному вузлі:

```bash
# Виконайте на кожному вузлі (не на власному компʼютері)
systemctl poweroff
```

### Вимкніть залежності кластера {#shutting-down-cluster-dependencies}

Після вимкнення всіх вузлів вимкніть інші непотрібні залежності кластера, наприклад зовнішні сховища. Перевірте документацію постачальника, щоб зʼясувати, які ресурси можна вимикати, призупиняти або видаляти.

## Перезапустіть кластер {#restart-the-cluster}

У цьому розділі описано перезапуск кластера після коректного вимкнення. Якщо кластер не відновиться, поверніть його до попереднього стану за допомогою [резервної копії etcd](/docs/tasks/administer-cluster/configure-upgrade-etcd/#restoring-an-etcd-cluster).

### Увімкніть залежності кластера {#powering-on-cluster-dependencies}

Увімкніть потрібні кластеру залежності, наприклад зовнішні сховища.

### Увімкніть вузли кластера {#powering-on-cluster-machines}

Спочатку увімкніть усі вузли панелі управління способом, який підходить для вашого кластера, наприклад через вебконсоль постачальника хмарних послуг. Дайте вузлам панелі управління кілька хвилин, щоб перейти у стан `Ready`. Компонентам панелі управління (kube-apiserver, etcd) може знадобитися більше часу для запуску. Переконайтеся, що всі вузли панелі управління мають стан `Ready`.

Потім увімкніть усі робочі вузли й переконайтеся, що вони також мають стан `Ready`:

```bash
kubectl get nodes --selector='node-role.kubernetes.io/control-plane'
kubectl get nodes --selector='!node-role.kubernetes.io/control-plane'
```

### Дозвольте планування на вузлах панелі управління {#making-control-plane-nodes-schedulable}

Коли вузли панелі управління матимуть стан `Ready`, дозвольте планування на них за допомогою `kubectl uncordon`:

```bash
kubectl uncordon --selector='node-role.kubernetes.io/control-plane'
```

### Дозвольте планування на робочих вузлах {#making-worker-nodes-schedulable}

Коли робочі вузли матимуть стан `Ready`, дозвольте планування на них:

```bash
kubectl uncordon --selector='!node-role.kubernetes.io/control-plane'
```

Дочекайтеся, поки всі Podʼи відновлять роботу, і переконайтеся, що їхній стан — `Running`:

```bash
kubectl get pods --all-namespaces
```

Це найпростіший спосіб перевірки. У реальному виробничому середовищі залежно від конфігурації системи можуть знадобитися додаткові процедури й перевірки.

### Застереження {#caveats}

Розподіл Podʼів по вузлах до вимкнення може не зберегтися після перезапуску. Вузли знову стають доступними для планування послідовно, і kube-scheduler планує Podʼи лише на вузлах, які на цей момент мають стан `Ready` і доступні для планування. Якщо вузлів багато, розміщення Podʼів може бути незбалансованим на користь вузлів, які стали доступними першими.
