## Як працює цей підхід {#how-the-design-works}

У цій вправі ви створите Pod, який отримує змінні середовища з файлів, проєцюючи ці значення в запущений контейнер.

{{% code_sample file="pods/inject/envars-file-container.yaml" %}}

У цьому маніфесті `initContainer` монтує том `emptyDir` і записує змінні середовища у файл усередині нього, а звичайні контейнери посилаються і на файл, і на ключ змінної середовища через поле `fileKeyRef`, не монтуючи том. Коли поле `optional` має значення false, вказаний `key` у `fileKeyRef` має існувати у файлі змінних середовища.

Том монтується лише в контейнер, який записує у файл (`initContainer`), а контейнер-споживач, який використовує змінну середовища, не матиме змонтованого тому.

Формат файлу env відповідає [стандарту файлів env у Kubernetes](/docs/tasks/inject-data-application/define-environment-variable-via-file/#env-file-syntax).

Під час ініціалізації контейнера kubelet отримує змінні середовища зі вказаних файлів у томі `emptyDir` і надає їх контейнеру.

{{< note >}}
Усі типи контейнерів (init-контейнери, звичайні контейнери, sidecar-контейнери й ефемерні контейнери) підтримують завантаження змінних середовища з файлів.

Хоча ці змінні середовища можуть зберігати конфіденційну інформацію, томи `emptyDir` не забезпечують тих самих механізмів захисту, що й окремі обʼєкти Secret. Тому надання конфіденційних змінних середовища контейнерам через цю можливість не вважається рекомендованою практикою безпеки.
{{< /note >}}

Створіть Pod:

```shell
kubectl apply -f https://k8s.io/examples/pods/inject/envars-file-container.yaml
```

Перевірте, що контейнер у Podʼі працює:

```shell
# Якщо новий Pod ще не справний, повторіть цю команду кілька разів.
kubectl get pods
```

Перевірте логи контейнера на наявність змінних середовища:

```shell
kubectl logs envfile-test-pod -c use-envfile | grep DB_ADDRESS
```

Вивід показує значення вибраних змінних середовища:

```
DB_ADDRESS=address
```

## Синтаксис файлів env {#env-file-syntax}

Формат файлу env, який використовує Kubernetes, є чітко визначеною підмножиною семантики змінних середовища для POSIX-сумісного bash. Будь-який файл env, який підтримує Kubernetes, створює ті самі змінні середовища, що й під час інтерпретації в POSIX-сумісному bash. Однак POSIX-сумісний bash підтримує деякі додаткові формати, які Kubernetes не приймає.

Приклад:

```
MY_VAR='my-literal-value'
```

### Правила {#rules}

* Оголошення змінної: використовуйте форму `VAR='value'`. Пробіли навколо `=` ігноруються; пробіли на початку рядка ігноруються; порожні рядки ігноруються.
* Значення в лапках: значення мають бути взяті в одинарні лапки (`'`).
  * Вміст в одинарних лапках зберігається дослівно. Обробка екранованих послідовностей, згортання пробілів чи інтерпретація символів не застосовуються.
  * Символи нового рядка в одинарних лапках зберігаються (багаторядкові значення підтримуються).
* Коментарі: рядки, що починаються з `#`, розглядаються як коментарі та ігноруються. Символ `#` всередині значення в одинарних лапках не є коментарем.

Приклади:

```
# comment
DB_ADDRESS='address'

MULTI='line1
line2'
```

### Непідтримувані форми {#unsupported-forms}

* Значення без лапок **заборонені**:
  * `VAR=value` — не підтримується.
* Значення в подвійних лапках **заборонені**:
  * `VAR="value"` — не підтримується.
* Кілька сусідніх рядків у лапках **не** підтримуються:
  * `VAR='val1''val2'` — не підтримується.
* Будь-яка форма інтерполяції, розгортання або конкатенації **не** підтримується:
  * `VAR='a'$OTHER` або `VAR=${OTHER}` — не підтримується.

Сувора вимога щодо одинарних лапок гарантує, що kubelet сприймає значення дослівно під час завантаження змінних середовища з файлів.
