## Налаштування API-сервера розширення для роботи із шаром агрегації {#set-up-an-extension-api-server-to-work-with-the-aggregation-layer}

Наведені нижче кроки описують налаштування API-сервера розширення *на високому рівні*. Ці кроки застосовні незалежно від того, чи використовуєте ви конфігурації YAML, чи API. Ми намагаємося окремо вказати всі відмінності між цими двома підходами. Конкретний приклад їх реалізації за допомогою конфігурацій YAML дивіться в [sample-apiserver](https://github.com/kubernetes/sample-apiserver/blob/master/README.md) у репозиторії Kubernetes.

Також можна використати наявне стороннє рішення, як-от [apiserver-builder](https://github.com/kubernetes-sigs/apiserver-builder-alpha/blob/master/README.md), яке має згенерувати каркас і автоматизувати всі наведені нижче кроки за вас.

1. Переконайтеся, що API APIService увімкнено (перевірте `--runtime-config`). Стандартно він має бути увімкнений, якщо його свідомо не вимкнули у вашому кластері.
1. Можливо, вам потрібно створити правило RBAC, яке дозволяє додавати обʼєкти APIService, або попросити про це адміністратора кластера. (Оскільки розширення API впливають на весь кластер, не рекомендовано тестувати, розробляти чи налагоджувати розширення API в робочому кластері.)
1. Створіть простір імен Kubernetes, у якому ви хочете запустити свій api-service розширення.
1. Створіть або отримайте сертифікат CA, який використовуватиметься для підпису серверного сертифіката, що його API-сервер розширення використовує для HTTPS.
1. Створіть серверний сертифікат і ключ, які API-сервер використовуватиме для HTTPS. Цей сертифікат має бути підписаний наведеним вище CA. Він також повинен мати CN з іменем Kube DNS. Це імʼя походить від сервісу Kubernetes і має вигляд `<service name>.<service name namespace>.svc`
1. Створіть Secret Kubernetes із серверним сертифікатом і ключем у вашому просторі імен.
1. Створіть Deployment Kubernetes для API-сервера розширення й переконайтеся, що завантажуєте Secret як том. Він має містити посилання на робочий образ вашого API-сервера розширення. Deployment також має бути у вашому просторі імен.
1. Переконайтеся, що ваш API-сервер розширення завантажує ці сертифікати з цього тому і що вони використовуються під час рукостискання HTTPS.
1. Створіть службовий обліковий запис Kubernetes у вашому просторі імен.
1. Створіть кластерну роль Kubernetes для операцій, які ви хочете дозволити над вашими ресурсами.
1. Створіть привʼязку кластерної ролі Kubernetes від службового облікового запису у вашому просторі імен до створеної кластерної ролі.
1. Створіть привʼязку кластерної ролі Kubernetes від службового облікового запису у вашому просторі імен до кластерної ролі `system:auth-delegator`, щоб делегувати рішення щодо автентифікації основному API-серверу Kubernetes.
1. Створіть привʼязку ролі Kubernetes від службового облікового запису у вашому просторі імен до ролі `extension-apiserver-authentication-reader`. Це дає вашому API-серверу розширення доступ до ConfigMap `extension-apiserver-authentication`.
1. Створіть apiservice Kubernetes. Наведений вище сертифікат CA має бути закодований у base64, без нових рядків, і використаний як spec.caBundle в apiservice. Він не має належати до простору імен. Якщо ви використовуєте [kube-aggregator API](https://github.com/kubernetes/kube-aggregator/), передавайте лише набір CA у кодуванні PEM, оскільки кодування base64 виконується за вас.
1. Використайте kubectl, щоб отримати ваш ресурс. Під час виконання kubectl має повернути "No resources found.". Це повідомлення вказує, що все спрацювало, але наразі у вас немає створених обʼєктів цього типу ресурсу.
