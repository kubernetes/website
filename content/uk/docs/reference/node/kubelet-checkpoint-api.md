Створення контрольної точки контейнера — це функціонал для створення копії запущеного контейнера разом з його станом. Після того, як у вас є копія контейнера з його станом, ви можете перенести її на інший компʼютер для налагодження або подібних цілей.

Якщо перемістити дані контейнера з контрольної точки на компʼютер, здатний їх відновити, відновлений контейнер продовжить працювати точно з того самого місця, в якому було створено контрольну точку. Також можна переглянути збережені дані, за умови, що є відповідні інструменти для цього.

Створення контрольної точки контейнера може мати наслідки для безпеки. Зазвичай контрольна точка містить усі сторінки памʼяті всіх процесів у контейнері, для якого її створено. Це означає, що все, що колись було в памʼяті, тепер доступне на локальному диску. Це включає всі приватні дані та, можливо, ключі, які використовувались для шифрування. Відповідні реалізації CRI (середовище виконання контейнерів на цьому вузлі) повинні створювати архів контрольної точки таким чином, щоб до нього мав доступ лише користувач `root`. Все одно важливо памʼятати, що якщо архів контрольної точки передається в іншу систему, усі сторінки памʼяті будуть доступні для читання власнику архіву контрольної точки.

## Операції {#operations}

### `post` створення контрольної точки вказаного контейнера {#post-checkpoint}

Дайте команду kubelet створити контрольну точку конкретного контейнера з вказаного Podʼа.

Для отримання додаткової інформації щодо керування доступом до інтерфейсу контрольних точок kubelet дивіться [довідку з автентифікації/авторизації kubelet](/docs/reference/access-authn-authz/kubelet-authn-authz).

Kubelet запитає контрольну точку у відповідної реалізації {{<glossary_tooltip term_id="cri" text="CRI">}}. У запиті на створення контрольної точки kubelet вкаже імʼя архіву контрольної точки у вигляді `checkpoint-<podFullName>-<containerName>-<timestamp>.tar`, а також попросить зберегти архів контрольної точки в теці `checkpoints` у своїй кореневій теці (як визначено параметром `--root-dir`). Типово це `/var/lib/kubelet/checkpoints`.

Архів контрольної точки має формат _tar_, і його вміст можна переглянути за допомогою реалізації [`tar`](https://pubs.opengroup.org/onlinepubs/7908799/xcu/tar.html). Вміст архіву залежить від відповідної реалізації CRI (середовища виконання контейнерів на цьому вузлі).

#### HTTP-запит {#post-checkpoint-request}

POST /checkpoint/{namespace}/{pod}/{container}

#### Параметри {#post-checkpoint-params}

- **namespace** (*в шляху*): string, обовʼязково

  {{< glossary_tooltip term_id="namespace" >}}

- **pod** (*в шляху*): string, обовʼязково

  {{< glossary_tooltip term_id="pod" >}}

- **container** (*в шляху*): string, обовʼязково

  {{< glossary_tooltip term_id="container" >}}

- **timeout** (*в запиті*): integer

  Тайм-аут у секундах для очікування завершення створення контрольної точки. Якщо вказано нуль або тайм-аут не вказано, буде використане типове значення тайм-ауту {{<glossary_tooltip term_id="cri" text="CRI">}}. Час створення контрольної точки безпосередньо залежить від обсягу памʼяті, яку використовує контейнер. Чим більше памʼяті використовує контейнер, тим більше часу потрібно для створення відповідної контрольної точки.

#### Відповідь {#post-checkpoint-response}

200: OK

401: Unauthorized

404: Not Found (якщо функціональну можливість `ContainerCheckpoint` вимкнено)

404: Not Found (якщо не вдається знайти вказаний `namespace`, `pod` або `container`)

500: Internal Server Error (якщо реалізація CRI стикається з помилкою під час створення контрольної точки (подробиці див. у повідомленні про помилку))

500: Internal Server Error (якщо реалізація CRI не реалізує CRI API для контрольних точок (подробиці див. у повідомленні про помилку))
