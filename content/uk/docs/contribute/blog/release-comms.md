Команда _Release Comms_ Kubernetes (частина [SIG Release](https://github.com/kubernetes/community/tree/master/sig-release)) займається анонсами випусків, які публікуються у [головному блозі проєкту](/docs/contribute/blog/#main-blog).

Після кожного випуску команда Release Comms на певний час бере на себе головний блог і публікує серію додаткових статей, щоб пояснити або оголосити зміни, повʼязані з цим випуском. Ці додаткові статті називають _post-release comms_ (комунікаціями після випуску).

<!-- body -->

## Участь у комунікаціях після випуску {#opt-in}

Під час циклу випуску ви як учасник можете долучитися до комунікацій після випуску щодо майбутньої зміни в Kubernetes.

Щоб долучитися, відкрийте чернетку _placeholder_ [pull request](https://www.k8s.dev/docs/guide/pull-requests/) (PR) до [k/website](https://github.com/kubernetes/website). Спочатку це може бути порожній коміт. Згадайте тікет KEP або інший тікет щодо покращення Kubernetes в описі вашого placeholder PR.

Коли ви відкриваєте **чернетку** pull request, ви відкриваєте її з _main_ як базовою гілкою, а не з гілкою `dev-{{< skew nextMinorVersion >}}`. Це відрізняється від [процесу](/docs/contribute/new-content/new-features/#open-a-placeholder-pr) для змін майбутнього випуску та нових можливостей.

Також слід залишити коментар у відповідному тікеті [kubernetes/enhancements](https://github.com/kubernetes/enhancements) з посиланням на PR, щоб повідомити команду Release Comms, яка керує цим випуском. Ваш коментар допоможе команді побачити, що зміну потрібно анонсувати і що ваша SIG вирішила долучитися.

Крім того, в ідеалі слід звʼязатися з командою Release Comms через Slack (канал [`#release-comms`](https://kubernetes.slack.com/archives/CNT9Y603D)), щоб повідомити, що ви це зробили й хочете долучитися.

## Підготовка вмісту статті {#preparation}

Щоб перетворити ваш placeholder PR на щось готове до рецензування, дотримуйтеся звичайного процесу [подання статті](/docs/contribute/blog/article-submission/). Однак для комунікацій після випуску у вас може не бути _writing buddy_ (помічника з написання); натомість команда Release Comms може призначити члена команди, який допоможе спрямовувати вашу роботу.

Слід виконати [squash](https://www.k8s.dev/docs/guide/pull-requests/#squashing) комітів у вашому pull request; якщо ви не знаєте, як це зробити, цілком нормально попросити допомоги в Release Comms або команди блогу.

За умови, що вашу статтю позначено як чернетку (`draft: true`) у [front matter](https://gohugo.io/content-management/front-matter/), PR можна злити в будь-який час протягом циклу випуску.

## Публікація {#publication}

Перед самим випуском команда Release Comms перевіряє, який вміст готовий (якщо його не готово до встановленого терміну і ви не отримали винятку, анонс не буде включено). Вона складає графік статей, які вийдуть, і відкриває нові pull request, щоб перевести ці статті з чернеток в опубліковані.

{{< caution >}}
Усі ці pull request для фактичної публікації статей після випуску **мають** бути затримані (команда Prow `/hold`), доки випуск фактично не відбудеться.
{{< /caution >}}

Затверджувачі команди блогу все одно дають остаточну згоду на переведення вмісту з чернетки до прийнятого для публікації. Напередодні дня випуску PR (або кілька PR) для публікації цих анонсів мають мати мітки LGTM (“looks good to me”, «на мою думку, усе добре») та approved, а також мітку **do-not-merge/hold**, щоб PR не злили зарано.

Після цього Release Comms / команда випуску може _зняти hold_ з цього PR (або набору PR), щойно Git-репозиторій вебсайту буде розморожено після фактичного випуску.

У день, коли кожна стаття запланована до публікації, автоматизація запускає збірку вебсайту, і стаття стає видимою.
