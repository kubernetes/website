Разом із [відповідальними за PR](/docs/contribute/participate/pr-wranglers) офіційні затверджувачі, рецензенти та члени SIG Docs по черзі тижневими змінами займаються [розглядом і категоризацією тікетів](/docs/contribute/review/for-approvers/#triage-and-categorize-issues) у репозиторії.

<!-- body -->

## Обовʼязки {#duties}

Кожного дня тижневої зміни відповідальний за тікети має:

- Щодня розглядати нові тікети й позначати їх мітками. Настанови щодо того, як SIG Docs використовує метадані, див. у [Класифікація та категоризація проблем](/docs/contribute/review/for-approvers/#triage-and-categorize-issues).
- Стежити за застарілими (stale) і покинутими (rotten) тікетами в репозиторії kubernetes/website.
- Підтримувати [дошку тікетів](https://github.com/orgs/kubernetes/projects/72/views/1).

## Вимоги {#requirements}

- Бути активним членом організації Kubernetes.
- Щонайменше 15 [нетривіальних](https://www.kubernetes.dev/docs/guide/pull-requests/#trivial-edits) внесків у Kubernetes (певна частина з яких має стосуватися kubernetes/website).
- Уже неофіційно виконувати цю роль.

## Корисні команди Prow для відповідальних за тікети {#helpful-prow-commands-for-wranglers}

Нижче наведено деякі команди, які часто використовують відповідальні за тікети:

```bash
# повторно відкрити тікет
/reopen

# перенести тікети, які не підходять для k/website, до іншого репозиторію
/transfer[-issue]

# змінити стан покинутих (rotten) тікетів
/remove-lifecycle rotten

# змінити стан застарілих (stale) тікетів
/remove-lifecycle stale

# призначити тікету SIG
/sig <sig_name>

# додати конкретну область
/area <area_name>

# для тікетів, що підходять для початківців
/good-first-issue

# тікети, що потребують допомоги
/help wanted

# позначити тікет як запит на підтримку
/kind support

# прийняти тікет за результатами розгляду
/triage accepted

# закрити тікет, над яким ми не працюватимемо і який ще не виправлено
/close not-planned
```

Щоб знайти більше команд Prow, зверніться до документації [Command Help](https://prow.k8s.io/command-help).

## Коли закривати тікети {#when-to-close-issues}

Для успіху проєкту з відкритим кодом дуже важливо добре керувати тікетами. Але не менш важливо закривати тікети, щоб підтримувати репозиторій і чітко спілкуватися з учасниками та користувачами.

Закривайте тікети, коли:

- Про схожу проблему повідомлено більше одного разу. Спочатку позначте тікет як `/triage duplicate`, повʼяжіть його з основним тікетом, а потім закрийте. Також варто спрямувати користувачів до оригінального тікета.
- З наданою інформацією дуже важко зрозуміти й розвʼязати проблему, описану автором. Однак заохочуйте користувача надати більше подробиць або повторно відкрити тікет, якщо він зможе відтворити проблему пізніше.
- Та сама функціональність уже реалізована деінде. Цей тікет можна закрити й спрямувати користувача в потрібне місце.
- Проблема, про яку повідомлено, наразі не запланована або не відповідає цілям проєкту.
- Якщо тікет виглядає як спам і явно не стосується теми.
- Якщо проблема повʼязана із зовнішнім обмеженням чи залежністю і проєкт не може на неї вплинути.

Щоб закрити тікет, залиште в ньому коментар `/close`.
