На цій сторінці показано, як створити нову тему для документації Kubernetes.

## {{% heading "prerequisites" %}} {#before-you-begin}

Створіть форк репозиторію документації Kubernetes, як описано в [Створення pull request](/docs/contribute/new-content/open-a-pr/).

<!-- steps -->

## Вибір типу сторінки {#choosing-a-page-type}

Готуючись писати нову тему, подумайте, який тип сторінки найкраще підійде для вашого вмісту:

{{< table caption = "Настанови з вибору типу сторінки" >}}
Тип | Опис
:--- | :----------
Concept | Сторінка концепції пояснює певний аспект Kubernetes. Наприклад, сторінка концепції може описувати обʼєкт Kubernetes Deployment і пояснювати його роль як застосунку під час розгортання, масштабування та оновлення. Зазвичай сторінки концепцій не містять послідовностей кроків, натомість надають посилання на завдання або підручники. Приклад теми-концепції див. у <a href="/docs/concepts/architecture/nodes/">Вузли</a>.
Task | Сторінка завдання показує, як зробити щось одне. Ідея в тому, щоб дати читачам послідовність кроків, які вони можуть виконувати під час читання сторінки. Сторінка завдання може бути короткою або довгою, якщо вона зосереджена на одній темі. На сторінці завдання можна поєднувати короткі пояснення з кроками, які потрібно виконати, але якщо потрібне докладне пояснення, його слід навести в темі-концепції. Повʼязані теми завдань і концепцій мають посилатися одна на одну. Приклад короткої сторінки завдання див. у <a href="/docs/tasks/configure-pod-container/configure-volume-storage/">Налаштування Podʼа для використання тому для зберігання</a>. Приклад довшої сторінки завдання див. у <a href="/docs/tasks/configure-pod-container/configure-liveness-readiness-probes/">Налаштування проб життєздатності та готовності</a>
Tutorial | Сторінка підручника показує, як досягти мети, що поєднує кілька можливостей Kubernetes. Підручник може містити кілька послідовностей кроків, які читачі можуть виконувати під час читання сторінки. Або ж він може пояснювати повʼязані фрагменти коду. Наприклад, підручник може містити покроковий розбір прикладу коду. Підручник може коротко пояснювати можливості Kubernetes, які в ньому поєднуються, але для докладних пояснень окремих можливостей має посилатися на відповідні теми-концепції.
{{< /table >}}

### Створення нової сторінки {#creating-a-new-page}

Використовуйте [тип контенту](/docs/contribute/style/page-content-types/) для кожної нової сторінки, яку пишете. Сайт документації надає шаблони, або [архетипи Hugo](https://gohugo.io/content-management/archetypes/), для створення нових сторінок вмісту. Щоб створити сторінку нового типу, виконайте `hugo new` зі шляхом до файлу, який хочете створити. Наприклад:

```
hugo new docs/concepts/my-first-concept.md
```

## Вибір заголовка та імені файлу {#choosing-a-title-and-filename}

Виберіть заголовок із ключовими словами, за якими пошукові системи мають знаходити сторінку. Створіть імʼя файлу зі слів заголовка, розділених дефісами. Наприклад, тема із заголовком [Використання HTTP-проксі для доступу до Kubernetes API](/docs/tasks/extend-kubernetes/http-proxy-access-api/) має імʼя файлу `http-proxy-access-api.md`. Не потрібно додавати "kubernetes" в імʼя файлу, бо "kubernetes" уже є в URL теми, наприклад:

       /docs/tasks/extend-kubernetes/http-proxy-access-api/

## Додавання заголовка теми до front matter {#adding-the-topic-title-to-the-front-matter}

У своїй темі додайте поле `title` до [front matter](https://gohugo.io/content-management/front-matter/). Front matter — це блок YAML між рядками з трьох дефісів на початку сторінки. Ось приклад:

    ---
    title: Using an HTTP Proxy to Access the Kubernetes API
    ---

## Вибір теки {#choosing-a-directory}

Залежно від типу сторінки, розмістіть ваш новий файл у підтеці однієї з тек:

* /content/en/docs/tasks/
* /content/en/docs/tutorials/
* /content/en/docs/concepts/

Ви можете розмістити свій файл у наявній підтеці або створити нову підтеку.

## Розміщення теми в змісті {#placing-your-topic-in-the-table-of-contents}

Зміст будується динамічно на основі структури тек вихідного коду документації. Теки верхнього рівня в `/content/en/docs/` створюють навігацію верхнього рівня, а кожна підтека має записи в змісті.

Кожна підтека має файл `_index.md`, який є «домашньою» сторінкою для вмісту цієї підтеки. `_index.md` не потребує шаблону. Він може містити оглядовий вміст про теми в підтеці.

Інші файли в теці стандартно сортуються за алфавітом. Це майже ніколи не найкращий порядок. Щоб керувати відносним порядком тем у підтеці, задайте ключу front matter `weight:` цілочислове значення. Зазвичай ми використовуємо числа, кратні 10, щоб можна було додавати теми пізніше. Наприклад, тема з вагою `10` буде перед темою з вагою `20`.

## Вбудовування коду у вашу тему {#embedding-code-in-your-topic}

Якщо ви хочете включити код у тему, його можна вбудувати безпосередньо у файл за допомогою синтаксису блоку коду markdown. Це рекомендовано в таких випадках (список не вичерпний):

* Код показує вивід з команди, наприклад `kubectl get deploy mydeployment -o json | jq '.status'`.
* Код недостатньо загальний для того, щоб користувачі могли його випробувати. Наприклад, ви можете вбудувати YAML файл для створення Pod, який залежить від конкретної реалізації [FlexVolume](/docs/concepts/storage/volumes/#flexvolume).
* Код є неповним прикладом, оскільки його мета — виділити частину більшого файлу. Наприклад, описуючи способи налаштування [RoleBinding](/docs/reference/access-authn-authz/rbac/#role-binding-examples), можна навести короткий фрагмент безпосередньо у файлі теми.
* Код не призначений для того, щоб користувачі його випробовували з інших причин. Наприклад, коли ви описуєте, як новий атрибут має бути доданий до ресурсу за допомогою команди `kubectl edit`, ви можете надати короткий приклад, який містить лише атрибут для додавання.

## Включення коду з іншого файлу {#including-code-from-another-file}

Інший спосіб включити код у тему — створити новий повний файл прикладу (або групу файлів прикладів), а потім посилатися на приклад зі своєї теми. Використовуйте цей метод для включення прикладів YAML, коли приклад загальний і придатний для повторного використання, і ви хочете, щоб читач спробував його сам.

Додаючи новий окремий файл прикладу, як-от файл YAML, розмістіть код в одній з підтек `<LANG>/examples/`, де `<LANG>` — мова теми. У файлі теми використовуйте shortcode `code_sample`:

```none
{{%/* code_sample file="<RELPATH>/my-example-yaml>" */%}}
```

де `<RELPATH>` — шлях до файлу, який потрібно включити, відносно теки `examples`. Такий shortcode Hugo посилається на файл YAML, розташований у `/content/en/examples/pods/storage/gce-volume.yaml`.

```none
{{%/* code_sample file="pods/storage/gce-volume.yaml" */%}}
```

## Як показати створення обʼєкта API з файлу конфігурації {#showing-how-to-create-an-api-object-from-a-configuration-file}

Якщо вам потрібно продемонструвати, як створити обʼєкт API на основі файлу конфігурації, розмістіть файл конфігурації в одній з підтек у `<LANG>/examples`.

У вашій темі вкажіть цю команду:

```
kubectl create -f https://k8s.io/examples/pods/storage/gce-volume.yaml
```

{{< note >}}
Додаючи нові файли YAML до теки `<LANG>/examples`, переконайтеся, що файл також включено до файлу `<LANG>/examples_test.go`. Travis CI для вебсайту автоматично запускає цей тест під час подання PR, щоб переконатися, що всі приклади проходять тести.
{{< /note >}}

Приклад теми, яка використовує цей прийом, див. у [Запуск одноекземплярного застосунку зі збереженням стану](/docs/tasks/run-application/run-single-instance-stateful-application/).

## Додавання зображень до теми {#adding-images-to-a-topic}

Розмістіть файли зображень у теці `/images`. Бажаний формат зображень — SVG.
