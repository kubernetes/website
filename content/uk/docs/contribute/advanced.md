На цій сторінці передбачається, що ви вже знаєте, як [робити внесок у новий вміст](/docs/contribute/new-content/) і [рецензувати роботу інших](/docs/contribute/review/reviewing-prs/), і готові дізнатися про інші способи участі. Для деяких із цих завдань потрібно використовувати клієнт командного рядка Git та інші інструменти.

## Пропонування покращень {#propose-improvements}

[Члени](/docs/contribute/participate/roles-and-responsibilities/#members) SIG Docs можуть пропонувати покращення.

Після того, як ви деякий час робите внесок у документацію Kubernetes, у вас можуть зʼявитися ідеї щодо покращення [Посібника зі стилю](/docs/contribute/style/style-guide/), [Посібника з вмісту](/docs/contribute/style/content-guide/), набору інструментів для збирання документації, стилю вебсайту, процесів рецензування та злиття pull request або інших аспектів документації. Для максимальної прозорості такі пропозиції потрібно обговорювати на зустрічі SIG Docs або в [списку розсилки kubernetes-sig-docs](https://groups.google.com/forum/#!forum/kubernetes-sig-docs). Крім того, перш ніж пропонувати масштабні зміни, корисно мати певний контекст щодо того, як усе працює зараз і чому в минулому було ухвалено ті чи інші рішення. Найшвидший спосіб отримати відповіді на запитання про те, як зараз працює документація, — запитати в Slack-каналі `#sig-docs` на [kubernetes.slack.com](https://kubernetes.slack.com).

Після обговорення, коли SIG дійде згоди щодо бажаного результату, ви можете працювати над запропонованими змінами у найдоречніший спосіб. Наприклад, оновлення посібника зі стилю або функціональності вебсайту може передбачати відкриття pull request, а зміна, повʼязана з тестуванням документації, — співпрацю з sig-testing.

## Координація документації для випуску Kubernetes {#coordinate-docs-for-a-kubernetes-release}

[Затверджувачі](/docs/contribute/participate/roles-and-responsibilities/#approvers) SIG Docs можуть координувати документацію для випуску Kubernetes.

Кожен випуск Kubernetes координує команда людей, які беруть участь у групі за інтересами (SIG) sig-release. До команди випуску також входять загальний керівник випуску, представники sig-testing та інші. Щоб дізнатися більше про процеси випуску Kubernetes, див. [https://github.com/kubernetes/sig-release](https://github.com/kubernetes/sig-release).

Представник SIG Docs для конкретного випуску координує такі завдання:

- Стежити за таблицею відстеження можливостей щодо нових або змінених можливостей, які впливають на документацію. Якщо документація для певної можливості не буде готова до випуску, цю можливість можуть не допустити до випуску.
- Регулярно відвідувати зустрічі sig-release і повідомляти про стан документації для випуску.
- Рецензувати та редагувати документацію можливостей, підготовлену SIG, відповідальною за реалізацію можливості.
- Зливати pull request, повʼязані з випуском, і підтримувати Git-гілку можливостей для випуску.
- Наставляти інших учасників SIG Docs, які хочуть у майбутньому навчитися виконувати цю роль. Це називається «shadowing».
- Публікувати зміни документації, повʼязані з випуском, коли публікуються артефакти випуску.

Координація випуску зазвичай потребує 3–4 місяців, і цей обовʼязок по черзі виконують затверджувачі SIG Docs.

## Виконання обовʼязків New Contributor Ambassador {#serve-as-a-new-contributor-ambassador}

[Затверджувачі](/docs/contribute/participate/roles-and-responsibilities/#approvers) SIG Docs можуть бути New Contributor Ambassador.

New Contributor Ambassador вітають нових учасників у SIG-Docs, пропонують їм PR і наставляють їх під час перших кількох поданих PR.

Обовʼязки New Contributor Ambassador включають:

- Стеження за [Slack-каналом #sig-docs](https://kubernetes.slack.com) щодо запитань від нових учасників.
- Співпраця з відповідальними за PR для визначення [good first issues](https://kubernetes.dev/docs/guide/help-wanted/#good-first-issue) для нових учасників.
- Наставництво нових учасників під час їхніх перших кількох PR до репозиторію документації.
- Допомога новим учасникам у створенні складніших PRʼів, необхідних їм для того, щоб стати членами Kubernetes.
- [Поручительство за учасників](/docs/contribute/advanced/#sponsor-a-new-contributor) на їхньому шляху до членства у Kubernetes.
- Проведення щомісячної зустрічі для допомоги та наставництва нових учасників.

Поточних New Contributor Ambassador оголошують на кожній зустрічі SIG-Docs і в [каналі Kubernetes #sig-docs](https://kubernetes.slack.com).

## Поручительство за нового учасника {#sponsor-a-new-contributor}

[Рецензенти](/docs/contribute/participate/roles-and-responsibilities/#reviewers) SIG Docs можуть бути поручителями нових учасників.

Після того, як новий учасник успішно подав 5 змістовних pull request до одного або кількох репозиторіїв Kubernetes, він може подати заявку на [членство](/docs/contribute/participate/roles-and-responsibilities/#members) в організації Kubernetes. Членство учасника мають підтримати два поручителі, які вже є рецензентами.

Нові учасники документації можуть знайти поручителів, запитавши в каналі #sig-docs у [Kubernetes Slack](https://kubernetes.slack.com) або в [списку розсилки SIG Docs](https://groups.google.com/forum/#!forum/kubernetes-sig-docs). Якщо ви впевнені в роботі заявника, зголосіться бути його поручителем. Коли заявник подасть заявку на членство, дайте на неї відповідь "+1" і поясніть, чому вважаєте заявника гарним кандидатом на членство в організації Kubernetes.

## Виконання обовʼязків співголови SIG {#serve-as-a-sig-co-chair}

[Члени](/docs/contribute/participate/roles-and-responsibilities/#members) SIG Docs можуть один термін бути співголовою SIG Docs.

### Передумови {#prerequisites}

Щоб бути співголовою, член Kubernetes має відповідати таким вимогам:

- Розуміти робочі процеси та інструменти SIG Docs: git, Hugo, локалізацію, підпроєкт блогу
- Розуміти, як інші SIG Kubernetes та репозиторії впливають на робочий процес SIG Docs, включаючи: [команди в k/org](https://github.com/kubernetes/org/blob/main/config/kubernetes/sig-docs/teams.yaml), [процеси в k/community](https://github.com/kubernetes/community/tree/main/sig-docs), втулки в [k/test-infra](https://github.com/kubernetes/test-infra/), та роль [SIG Architecture](https://github.com/kubernetes/community/tree/main/sig-architecture). Крім того, розуміти, як працює [процес випуску документації Kubernetes](/docs/contribute/advanced/#coordinate-docs-for-a-kubernetes-release).
- Отримати схвалення спільноти SIG Docs безпосередньо або через lazy consensus (мовчазну згоду)
- Приділяти цій ролі щонайменше 5 годин на тиждень (і часто більше) протягом щонайменше 6 місяців

### Обовʼязки {#responsibilities}

Роль співголови — це служіння: співголови нарощують спроможність учасників, займаються процесами й політиками, планують і проводять зустрічі, складають графік відповідальних за PR, відстоюють інтереси документації в спільноті Kubernetes, забезпечують успіх документації в циклах випусків Kubernetes і тримають SIG Docs зосередженою на ефективних пріоритетах.

Обовʼязки включають:

- Тримати SIG Docs зосередженою на максимальному задоволенні розробників завдяки відмінній документації
- Бути прикладом дотримання [кодексу поведінки спільноти](https://github.com/cncf/foundation/blob/main/code-of-conduct.md) і вимагати його дотримання від членів SIG
- Вивчати та встановлювати найкращі практики для SIG, оновлюючи настанови щодо внеску
- Планувати та проводити зустрічі SIG: щотижневі оновлення статусу, щоквартальні ретроспективи/планування та інші за потреби
- Планувати та проводити спринти документації на заходах KubeCon та інших конференціях
- Залучати людей і представляти інтереси SIG Docs перед {{< glossary_tooltip text="CNCF" term_id="cncf" >}} та її платиновими партнерами, зокрема Google, Oracle, Azure, IBM і Huawei
- Забезпечувати безперебійну роботу SIG

### Ефективне проведення зустрічей {#running-effective-meetings}

Щоб планувати й проводити ефективні зустрічі, дотримуйтеся цих настанов: вони показують, що робити, як і чому.

**Дотримуйтесь [кодексу поведінки спільноти](https://github.com/cncf/foundation/blob/main/code-of-conduct.md)**:

- Проводьте шанобливі, інклюзивні дискусії, використовуючи шанобливу, інклюзивну мову.

**Встановіть чіткий порядок денний**:

- Складіть чіткий порядок денний із тем
- Опублікуйте порядок денний заздалегідь

Для щотижневих зустрічей скопіюйте нотатки попереднього тижня в розділ "Past meetings" нотаток

**Спільно ведіть точні нотатки**:

- Записуйте обговорення зустрічі
- Подумайте про те, щоб доручити комусь вести нотатки

**Чітко й точно призначайте завдання**:

- Записуйте завдання, відповідального за нього та очікувану дату виконання

**Модеруйте за потребою**:

- Якщо обговорення відходить від порядку денного, поверніть учасників до поточної теми
- Залишайте простір для різних стилів обговорення, тримаючи фокус і поважаючи час учасників

**Поважайте час учасників**:

Починайте і закінчуйте зустрічі вчасно.

**Ефективно використовуйте Zoom**:

- Ознайомтеся з [настановами щодо Zoom для Kubernetes](https://github.com/kubernetes/community/blob/main/communication/zoom-guidelines.md)
- Займіть роль ведучого (host) під час входу, ввівши ключ ведучого (host key)

  <img src="/images/docs/contribute/claim-host.png" width="75%" alt="Отримання ролі ведучого в Zoom" />

### Запис зустрічей у Zoom {#recording-meetings-on-zoom}

Коли ви готові розпочати запис, натисніть "Record to Cloud".

Коли ви готові зупинити запис, натисніть "Stop".

Відео автоматично завантажується на YouTube.
