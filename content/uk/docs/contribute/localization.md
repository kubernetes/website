На цій сторінці показано, як [локалізувати](https://blog.mozilla.org/l10n/2011/12/14/i18n-vs-l10n-whats-the-diff/) документацію іншою мовою.

<!-- body -->

## Внесок у наявну локалізацію {#contribute-to-an-existing-localization}

Ви можете допомогти додати або покращити вміст наявної локалізації. У [Kubernetes Slack](https://slack.k8s.io/) є канал для кожної локалізації. Також є загальний [Slack-канал SIG Docs Localizations](https://kubernetes.slack.com/messages/sig-docs-localizations), де можна привітатися.

{{< note >}}
Подробиці про внесок у конкретну локалізацію шукайте в локалізованій версії цієї сторінки.
{{< /note >}}

### Визначте дволітерний код вашої мови {#find-your-two-letter-language-code}

Спершу зверніться до [стандарту ISO 639-1](https://www.loc.gov/standards/iso639-2/php/code_list.php), щоб знайти дволітерний код мови вашої локалізації. Наприклад, дволітерний код корейської мови — `ko`.

Деякі мови разом із кодом мови використовують код країни в нижньому регістрі за ISO-3166. Наприклад, код бразильської португальської — `pt-br`.

### Зробіть форк та клонуйте репозиторій {#fork-and-clone-the-repo}

Спершу [створіть власний форк](/docs/contribute/new-content/open-a-pr/#fork-the-repo) репозиторію [kubernetes/website](https://github.com/kubernetes/website).

Потім клонуйте свій форк і перейдіть у нього (`cd`):

```shell
git clone https://github.com/<username>/website
cd website
```

Тека вмісту вебсайту містить підтеки для кожної мови. Локалізація, з якою ви хочете допомогти, розташована в `content/<two-letter-code>`.

### Пропонуйте зміни {#suggest-changes}

Створіть або оновіть вибрану локалізовану сторінку на основі англійського оригіналу. Докладніше див. [Локалізація вмісту](#localize-content).

Якщо ви помітили технічну неточність або іншу проблему в upstream-документації (англійською), спершу виправте upstream-документацію, а потім повторіть таке саме виправлення, оновивши локалізацію, над якою працюєте.

Обмежуйте зміни в pull request однією локалізацією. Рецензувати pull request, які змінюють вміст у кількох локалізаціях, проблематично.

Щоб запропонувати зміни до цієї локалізації, дотримуйтеся сторінки [Пропозиції щодо покращення вмісту](/docs/contribute/suggesting-improvements/). Процес подібний до пропонування змін до upstream-вмісту (англійською).

## Створення нової локалізації {#start-a-new-localization}

Якщо ви хочете, щоб документацію Kubernetes було локалізовано новою мовою, ось що потрібно зробити.

Оскільки учасники не можуть затверджувати власні pull request, щоб почати локалізацію, потрібно _щонайменше двоє учасників_.

Усі команди локалізації мають бути самодостатніми. Вебсайт Kubernetes радо розмістить вашу роботу, але перекладати її й підтримувати наявний локалізований вміст актуальним — ваше завдання.

Вам потрібно знати дволітерний код своєї мови. Щоб знайти дволітерний код мови вашої локалізації, зверніться до [стандарту ISO 639-1](https://www.loc.gov/standards/iso639-2/php/code_list.php). Наприклад, дволітерний код корейської мови — `ko`.

Якщо мовою, для якої ви починаєте локалізацію, розмовляють у різних місцях і варіанти суттєво відрізняються, можливо, варто поєднати код країни ISO-3166 у нижньому регістрі з дволітерним кодом мови. Наприклад, бразильська португальська локалізована як `pt-br`.

Коли ви починаєте нову локалізацію, вам потрібно локалізувати [мінімально необхідний вміст](#minimum-required-content) перед тим, як проєкт Kubernetes зможе опублікувати ваші зміни на сайті.

SIG Docs може допомогти вам з роботою в окремій гілці, щоб ви могли поступово працювати для досягнення цієї мети.

### Пошук спільноти {#find-community}

Повідомте Kubernetes SIG Docs, що ви хочете створити локалізацію! Приєднайтеся до [Slack-каналу SIG Docs](https://kubernetes.slack.com/messages/sig-docs) і [Slack-каналу SIG Docs Localizations](https://kubernetes.slack.com/messages/sig-docs-localizations). Інші команди локалізації радо допоможуть вам почати й відповідять на ваші запитання.

Також подумайте про участь у [зустрічі підгрупи локалізації SIG Docs](https://github.com/kubernetes/community/tree/main/sig-docs). Місія підгрупи локалізації SIG Docs — працювати разом із командами локалізації SIG Docs над визначенням і документуванням процесів створення локалізованих посібників для учасників. Крім того, підгрупа локалізації SIG Docs шукає можливості створювати спільні інструменти для команд локалізації й ділитися ними, а також визначає нові вимоги для керівництва SIG Docs. Якщо у вас є запитання щодо цієї зустрічі, поставте їх у [Slack-каналі SIG Docs Localizations](https://kubernetes.slack.com/messages/sig-docs-localizations).

Ви також можете створити канал Slack для своєї локалізації в репозиторії `kubernetes/community`. Приклад додавання каналу Slack див. у PR, що [додає канал для перської мови](https://github.com/kubernetes/community/pull/4980).

### Приєднуйтесь до організації Kubernetes на GitHub {#join-the-kubernetes-github-organization}

Коли ви відкриєте PR локалізації, ви можете стати членами організації Kubernetes на GitHub. Кожен член команди має створити власний [запит на членство в організації (Organization Membership Request)](https://github.com/kubernetes/org/issues/new/choose) у репозиторії `kubernetes/org`.

### Додайте свою команду локалізації на GitHub {#add-your-localization-team-in-github}

Далі додайте свою команду локалізації Kubernetes до [`sig-docs/teams.yaml`](https://github.com/kubernetes/org/blob/main/config/kubernetes/sig-docs/teams.yaml). Приклад додавання команди локалізації див. у PR, що додає [іспанську команду локалізації](https://github.com/kubernetes/org/pull/685).

Члени `@kubernetes/sig-docs-**-owners` можуть затверджувати PR, які змінюють вміст у межах (і лише в межах) теки вашої локалізації: `/content/**/`. Для кожної локалізації команда `@kubernetes/sig-docs-**-reviews` автоматизує призначення рецензентів для нових PR. Члени `@kubernetes/website-maintainers` можуть створювати нові гілки локалізації для координації перекладу. Члени `@kubernetes/website-milestone-maintainers` можуть використовувати [команду Prow](https://prow.k8s.io/command-help) `/milestone`, щоб призначати milestone тікетам або PR.

### Налаштування робочого процесу {#configure-the-workflow}

Далі додайте мітку GitHub для вашої локалізації в репозиторії `kubernetes/test-infra`. Мітка дає змогу фільтрувати тікети та pull request для вашої мови.

Приклад додавання мітки див. у PR, що додає [мітку італійської мови](https://github.com/kubernetes/test-infra/pull/11316).

### Зміна конфігурації сайту {#modify-the-site-configuration}

Вебсайт Kubernetes використовує Hugo як вебфреймворк. Конфігурація Hugo вебсайту розташована у файлі [`hugo.toml`](https://github.com/kubernetes/website/tree/main/hugo.toml). Щоб підтримати нову локалізацію, потрібно змінити `hugo.toml`.

Додайте блок конфігурації для нової мови до `hugo.toml` під наявним блоком `[languages]`. Наприклад, блок для німецької мови виглядає так:

```toml
[languages.de]
title = "Kubernetes"
languageName = "Deutsch (German)"
weight = 5
contentDir = "content/de"
languagedirection = "ltr"

[languages.de.params]
time_format_blog = "02.01.2006"
language_alternatives = ["en"]
description = "Produktionsreife Container-Orchestrierung"
languageNameLatinScript = "Deutsch"
```

Панель вибору мови показує значення `languageName`. Присвойте `languageName` значення "назва мови її власним письмом і мовою (назва мови англійською латиницею)". Наприклад, `languageName = "한국어 (Korean)"` або `languageName = "Deutsch (German)"`.

`languageNameLatinScript` можна використовувати, щоб отримати назву мови латиницею й використати її в темі. Присвойте `languageNameLatinScript` значення "назва мови латиницею". Наприклад, `languageNameLatinScript ="Korean"` або `languageNameLatinScript = "Deutsch"`.

Параметр `weight` визначає порядок мов у панелі вибору мови. Менша вага має пріоритет, тож така мова показується першою. Призначаючи параметр `weight`, важливо переглянути наявний блок мов і скоригувати їхні ваги, щоб вони були впорядковані відносно всіх мов, зокрема щойно доданої.

Докладніше про підтримку багатомовності в Hugo див. "[Multilingual Mode](https://gohugo.io/content-management/multilingual/)".

### Додавання нової теки локалізації {#add-a-new-localization-directory}

Додайте підтеку для мови до теки [`content`](https://github.com/kubernetes/website/tree/main/content) у репозиторії. Наприклад, дволітерний код німецької мови — `de`:

```shell
mkdir content/de
```

Також потрібно створити теку всередині теки `i18n` для [локалізованих рядків](#site-strings-in-i18n); перегляньте наявні локалізації для прикладу.

Наприклад, для німецької мови рядки розташовані в `i18n/de/de.toml`.

### Локалізуйте кодекс поведінки спільноти {#localize-the-community-code-of-conduct}

Відкрийте PR до репозиторію [`cncf/foundation`](https://github.com/cncf/foundation/tree/main/code-of-conduct-languages), щоб додати кодекс поведінки вашою мовою.

### Налаштуйте файли OWNERS {#set-up-the-owners-files}

Щоб задати ролі кожного користувача, який робить внесок у локалізацію, створіть усередині підтеки мови файл `OWNERS` з такими полями:

- **reviewers**: перелік команд kubernetes з роллю рецензента, у цьому випадку
  - команда `sig-docs-**-reviews`, створена на кроці [Додайте свою команду локалізації на GitHub](#add-your-localization-team-in-github).
- **approvers**: перелік команд kubernetes з роллю затверджувача, у цьому випадку
  - команда `sig-docs-**-owners`, створена на кроці [Додайте свою команду локалізації на GitHub](#add-your-localization-team-in-github).
- **labels**: перелік міток GitHub, які автоматично додаються до PR, у цьому випадку — мітка мови, створена на кроці [Налаштування робочого процесу](#configure-the-workflow).

Докладніше про файл `OWNERS` див. [go.k8s.io/owners](https://go.k8s.io/owners).

[Файл OWNERS іспанської локалізації](https://git.k8s.io/website/content/es/OWNERS) з кодом мови `es` виглядає так:

```yaml
# See the OWNERS docs at https://go.k8s.io/owners

# This is the localization project for Spanish.
# Teams and members are visible at https://github.com/orgs/kubernetes/teams.

reviewers:
- sig-docs-es-reviews

approvers:
- sig-docs-es-owners

labels:
- area/localization
- language/es
```

Після додавання файлу `OWNERS` для мови оновіть [кореневий файл `OWNERS_ALIASES`](https://git.k8s.io/website/OWNERS_ALIASES), додавши нові команди Kubernetes для локалізації — `sig-docs-**-owners` і `sig-docs-**-reviews`.

Для кожної команди додайте в алфавітному порядку список користувачів GitHub, запитаних на кроці [Додайте свою команду локалізації на GitHub](#add-your-localization-team-in-github).

```diff
--- a/OWNERS_ALIASES
+++ b/OWNERS_ALIASES
@@ -48,6 +48,14 @@ aliases:
     - stewart-yu
     - xiangpengzhao
     - zhangxiaoyu-zidif
+  sig-docs-es-owners: # Admins for Spanish content
+    - alexbrand
+    - raelga
+  sig-docs-es-reviews: # PR reviews for Spanish content
+    - alexbrand
+    - electrocucaracha
+    - glo-pena
+    - raelga
   sig-docs-fr-owners: # Admins for French content
     - perriea
     - remyleone
```

### Відкрийте pull request {#open-a-pull-request}

Далі [відкрийте pull request](/docs/contribute/new-content/open-a-pr/#open-a-pr) (PR), щоб додати локалізацію до репозиторію `kubernetes/website`. Перш ніж PR можна буде затвердити, він має містити весь [мінімально необхідний вміст](#minimum-required-content).

Приклад додавання нової локалізації див. у PR, що вмикає [документацію французькою](https://github.com/kubernetes/website/pull/12548).

### Додайте локалізований файл README {#add-a-localized-readme-file}

Щоб допомогти іншим учасникам локалізації, додайте новий [`README-**.md`](https://help.github.com/articles/about-readmes/) у корінь [kubernetes/website](https://github.com/kubernetes/website/), де `**` — дволітерний код мови. Наприклад, файл README німецькою буде `README-de.md`.

Спрямовуйте учасників локалізації в локалізованому файлі `README-**.md`. Додайте туди ту саму інформацію, що й у `README.md`, а також:

- Контактну особу проєкту локалізації
- Будь-яку інформацію, специфічну для локалізації

Після створення локалізованого README додайте посилання на нього в головний англійський `README.md` і вкажіть контактну інформацію англійською. Ви можете вказати ідентифікатор GitHub, адресу електронної пошти, [канал Slack](https://slack.com/) або інший спосіб звʼязку. Ви також маєте надати посилання на локалізований Кодекс поведінки спільноти.

### Запуск вашої нової локалізації {#launch-your-new-localization}

Коли локалізація відповідає вимогам щодо робочого процесу та мінімального обсягу, SIG Docs робить таке:

- Вмикає вибір мови на вебсайті.
- Оголошує про доступність локалізації через канали [Cloud Native Computing Foundation](https://www.cncf.io/about/) (CNCF), зокрема [блог Kubernetes](/blog/).

## Локалізація вмісту {#localize-content}

Локалізація _всієї_ документації Kubernetes — величезне завдання. Цілком нормально почати з малого й розширюватися з часом.

### Мінімально необхідний вміст {#minimum-required-content}

Як мінімум, всі локалізації мають містити:

Опис | URL
-----|----------
Документація | [Усі заголовки та підзаголовки](/docs/home/)
Початок роботи | [Усі заголовки та підзаголовки](/docs/setup/)
Навчальні матеріали | [Основи Kubernetes](/docs/tutorials/kubernetes-basics/), [Привіт Minikube](/docs/tutorials/hello-minikube/)
Рядки сайту | [Усі рядки сайту](#site-strings-in-i18n) у новому локалізованому файлі TOML
Випуски | [Усі заголовки та підзаголовки](/releases)

Перекладені документи мають розташовуватися у власній підтеці `content/**/`, але в іншому дотримуватися того самого шляху URL, що й англійське джерело. Наприклад, щоб підготувати навчальний матеріал [Основи Kubernetes](/docs/tutorials/kubernetes-basics/) до перекладу німецькою, створіть підтеку в теці `content/de/` і скопіюйте англійське джерело або теку:

```shell
mkdir -p content/de/docs/tutorials
cp -ra content/en/docs/tutorials/kubernetes-basics/ content/de/docs/tutorials/
```

Інструменти перекладу можуть пришвидшити процес перекладу. Наприклад, деякі редактори пропонують втулки для швидкого перекладу тексту.

{{< caution >}}
Машинного перекладу самого по собі недостатньо. Локалізація потребує ретельного рецензування людиною, щоб відповідати мінімальним стандартам якості.
{{< /caution >}}

Щоб забезпечити точність граматики та змісту, члени вашої команди локалізації мають ретельно рецензувати всі машинні переклади перед публікацією.

### Локалізація зображень SVG {#localize-svg-images}

Проєкт Kubernetes рекомендує за можливості використовувати векторні (SVG) зображення, оскільки командам локалізації набагато легше їх редагувати. Якщо ви знайшли растрове зображення, яке потрібно локалізувати, спершу подумайте про те, щоб перемалювати англійську версію як векторне зображення, а потім локалізувати його.

Перекладаючи текст усередині зображень SVG (Scalable Vector Graphics), важливо дотримуватися певних рекомендацій, щоб забезпечити точність і підтримувати однорідність між різними мовними версіями. Зображення SVG часто використовуються в документації Kubernetes для ілюстрації концепцій, робочих процесів та схем.

1. **Визначення тексту для перекладу**:
   Почніть з ідентифікації текстових елементів всередині SVG-зображення, які потрібно перекласти. Зазвичай до цих елементів входять мітки, підписи, анотації чи будь-який текст, що передає інформацію.

1. **Редагування файлів SVG**: файли SVG базуються на XML, тобто їх можна редагувати текстовим редактором. Однак важливо зазначити, що в більшості зображень документації Kubernetes текст уже перетворено на криві, щоб уникнути проблем сумісності шрифтів. У таких випадках для редагування рекомендовано використовувати спеціалізоване програмне забезпечення для SVG, як-от Inkscape: відкрийте файл SVG і знайдіть текстові елементи, які потрібно перекласти.

1. **Переклад тексту**: замініть оригінальний текст перекладом потрібною мовою. Переконайтеся, що переклад точно передає задуманий зміст і вміщується у вільне місце на зображенні. Для мов, що використовують латинський алфавіт, слід використовувати сімейство шрифтів Open Sans. Завантажити шрифт Open Sans можна тут: [Open Sans Typeface](https://fonts.google.com/specimen/Open+Sans).

1. **Перетворення тексту на криві**: як уже згадувалося, щоб уникнути проблем сумісності шрифтів, рекомендовано перетворювати перекладений текст на криві або контури. Перетворення тексту на криві гарантує, що остаточне зображення правильно покаже перекладений текст, навіть якщо в системі користувача немає саме того шрифту, який використано в оригінальному SVG.

1. **Перевірка та тестування**: після перекладу й перетворення тексту на криві збережіть і перегляньте оновлене зображення SVG, щоб переконатися, що текст правильно показується й вирівняний. Див. [Попередній локальний перегляд змін](/docs/contribute/new-content/open-a-pr/#preview-locally).

### Вихідні файли {#source-files}

Локалізації мають базуватися на англійських файлах конкретного випуску, на який орієнтується команда локалізації. Кожна команда локалізації може вирішити, на який випуск орієнтуватися; нижче він називається _цільовою версією_.

Щоб знайти вихідні файли для цільової версії:

1. Перейдіть до репозиторію вебсайту Kubernetes за адресою https://github.com/kubernetes/website.

1. Виберіть гілку для своєї цільової версії з такої таблиці:

Цільова версія | Гілка
-----|-----
Остання версія | [`main`](https://github.com/kubernetes/website/tree/main)
Попередня версія | [`release-{{< skew prevMinorVersion >}}`](https://github.com/kubernetes/website/tree/release-{{< skew prevMinorVersion >}})
Наступна версія | [`dev-{{< skew nextMinorVersion >}}`](https://github.com/kubernetes/website/tree/dev-{{< skew nextMinorVersion >}})

Гілка `main` містить вміст поточного випуску `{{< latest-version >}}`. Команда випуску створює гілку `{{< release-branch >}}` перед наступним випуском: v{{< skew nextMinorVersion >}}.

### Рядки сайту в i18n {#site-strings-in-i18n}

Локалізація має включати вміст [`i18n/en/en.toml`](https://github.com/kubernetes/website/blob/main/i18n/en/en.toml) у новому файлі для відповідної мови. Наприклад, для німецької мови: `i18n/de/de.toml`.

Додайте нову теку для локалізації та файл до `i18n/`. Наприклад, для німецької мови (`de`):

```bash
mkdir -p i18n/de
cp i18n/en/en.toml i18n/de/de.toml
```

Перегляньте коментарі вгорі файлу й адаптуйте їх до своєї локалізації, а потім перекладіть значення кожного рядка. Наприклад, ось німецький текст-заповнювач для форми пошуку:

```toml
[ui_search]
other = "Suchen"
```

Локалізація рядків сайту дає змогу налаштовувати текст і можливості всього сайту, наприклад текст про авторські права в нижньому колонтитулі кожної сторінки.

### Посібник з локалізації для конкретної мови {#language-specific-localization-guide}

Як команда локалізації, ви можете формалізувати найкращі практики своєї команди, створивши посібник з локалізації для своєї мови.

Наприклад, див. [посібник з локалізації корейською](/ko/docs/contribute/localization_ko/), який охоплює такі теми:

- Частота спринтів та релізи
- Стратегія створення гілок
- Робота з pull request
- Посібник зі стилю
- Глосарій локалізованих та нелокалізованих термінів
- Конвенції Markdown
- Термінологія обʼєктів Kubernetes API

### Зустрічі в Zoom для обговорення локалізації відповідною мовою {#language-specific-zoom-meetings}

Якщо проєкту локалізації потрібен окремий час для зустрічей, звʼяжіться зі співголовою SIG Docs або Tech Lead, щоб створити нову регулярну зустріч у Zoom і запрошення в календар. Це потрібно лише тоді, коли команда достатньо велика, щоб підтримувати окрему зустріч і потребувати її.

Відповідно до політики CNCF команди локалізації мають завантажувати записи своїх зустрічей у плейлист SIG Docs на YouTube. Співголова SIG Docs або Tech Lead може допомагати з цим процесом, доки SIG Docs його не автоматизує.

## Стратегія створення гілок {#branch-strategy}

Оскільки проєкти локалізації — це значною мірою спільна робота, ми заохочуємо команди працювати в спільних гілках локалізації — особливо на початку, поки локалізація ще не опублікована.

Щоб співпрацювати в гілці локалізації:

1. Член команди [@kubernetes/website-maintainers](https://github.com/orgs/kubernetes/teams/website-maintainers) відкриває гілку локалізації з вихідної гілки на https://github.com/kubernetes/website.

   Затверджувачі вашої команди приєдналися до команди `@kubernetes/website-maintainers`, коли ви [додали свою команду локалізації](#add-your-localization-team-in-github) до репозиторію [`kubernetes/org`](https://github.com/kubernetes/org).

   Ми рекомендуємо таку схему найменування гілок:

   `dev-<source version>-<language code>.<team milestone>`

   Наприклад, затверджувач німецької команди локалізації відкриває гілку локалізації `dev-1.12-de.1` безпосередньо в репозиторії `kubernetes/website` на основі вихідної гілки для Kubernetes v1.12.

1. Окремі учасники відкривають гілки змін (feature branches) на основі гілки локалізації.

   Наприклад, учасник німецької команди відкриває pull request зі змінами до `kubernetes:dev-1.12-de.1` з `username:local-branch-name`.

1. Затверджувачі рецензують і зливають гілки змін у гілку локалізації.

1. Періодично затверджувач зливає гілку локалізації з її вихідною гілкою, відкриваючи й затверджуючи новий pull request. Перед затвердженням pull request обовʼязково обʼєднайте (squash) коміти.

Повторюйте кроки 1–4 за потреби, доки локалізацію не буде завершено. Наприклад, наступні гілки німецької локалізації будуть такими: `dev-1.12-de.2`, `dev-1.12-de.3` тощо.

Команди мають зливати локалізований вміст у ту саму гілку, з якої його було взято. Наприклад:

- Гілку локалізації, створену з `main`, потрібно злити в `main`.
- Гілку локалізації, створену з `release-{{% skew "prevMinorVersion" %}}`, потрібно злити в `release-{{% skew "prevMinorVersion" %}}`.

{{< note >}}
Якщо вашу гілку локалізації створено з гілки `main`, але її не злито в `main` до створення нової гілки випуску `{{< release-branch >}}`, злийте її і в `main`, і в нову гілку випуску `{{< release-branch >}}`. Щоб злити гілку локалізації в нову гілку випуску `{{< release-branch >}}`, потрібно переключити upstream-гілку вашої гілки локалізації на `{{< release-branch >}}`.
{{< /note >}}

На початку кожного milestone команди корисно відкривати тікет із порівнянням upstream-змін між попередньою і поточною гілками локалізації. Для порівняння upstream-змін є два скрипти.

- [`upstream_changes.py`](https://github.com/kubernetes/website/tree/main/scripts#upstream_changespy) корисний для перевірки змін, внесених у конкретний файл. А
- [`diff_l10n_branches.py`](https://github.com/kubernetes/website/tree/main/scripts#diff_l10n_branchespy) корисний для створення переліку застарілих файлів для конкретної гілки локалізації.

Хоча лише затверджувачі можуть відкривати нові гілки локалізації та зливати pull request, будь-хто може відкрити pull request до нової гілки локалізації. Спеціальні дозволи не потрібні.

Докладніше про роботу з форків або безпосередньо з репозиторію див. ["Зробіть форк та клонуйте репозиторій"](#fork-and-clone-the-repo).
